# 输电项目全流程管理系统：六项正式设计裁决

- 状态：**已确认（Approved）**
- 裁决日期：**2026-10-29**
- 裁决来源：用户审核上一轮代码审计中列出的六项规则，并全部答复“同意”。
- 适用范围：本仓库及后续所有分支、前后端、SQLite 迁移、接口、导入导出、浏览器 UI 和验收。
- 优先级：若旧实现、旧说明或测试与本裁决冲突，业务约束以本裁决为准；**不能据此推断所有实现已经完成**。
- 变更原则：后续需要改变六项规则时须重新取得业务裁决；实现细节中仍未明确的问题先分析、列出备选与影响，不擅自定案。

## C01 分次执行结束后的剩余工作量

**裁决：同意。** 一批执行结束，计划但未实际确认完成的剩余数量不继续永久占用批准工作范围，应可由后续执行批次重新安排。

必须满足：
1. 同一批准范围的有效已完成数量与有效未执行预留数量分别统计；不能把“全部历史计划数量”永久当作占用。
2. 计划中、执行中的预留，已结束批次的实际完成，以及已取消批次的撤销量分别处理；项目批准总范围不得超分配、超完成。
3. 关闭批次时对未完成部分记录明确处置和审计依据，不删除原计划和已完成记录。零完成、有真实费用的情况不能伪造成实施。
4. 并发预留与完成确认在数据库事务内校验，幂等重试不能重复分配或重复确认。

**验收例：** 需求批准 2 套，E1 计划 2 套、确认 1 套后正常结束；E2 应可以再安排剩余 1 套；E1 历史计划 2 套及实际完成 1 套仍可追溯。

**待细化（不改变本裁决）：** 关闭时未完成量是否允许选择“继续实施/取消/转移”，各选择的审批权限及原因字段；有发生费用、返工、验收撤回的后续处理。

## C02 物理杆塔整体更换与单回路关联纠错严格分离

**裁决：同意。** 整基实体塔更换须核对所有共塔逻辑回路的受影响范围；仅纠正单条线路关联的情况只能作为关联纠错，不能冒充整塔更换。

必须满足：
1. 实体资产稳定 ID 与各线路逻辑节点稳定 ID 分离；一座物理塔可以对应多个逻辑节点。
2. 整塔更换前完整列出当前共塔关联，明确哪些逻辑节点受实际工程影响；对受影响关系使用同一业务事务更新，记录变更原因、前后实体、有效历史和操作者。
3. 单回路数据纠错只能调整被核实的逻辑节点，明确标记为 `correction`；实际实体更换标记为 `replacement`，不静默修改其他回路。
4. 已核实需求、项目入库/立项快照、历史执行和结算仍能追溯当时的实际位置；必要时启动重新核实/项目变更，禁止历史事实静默漂移。

**验收例：** A、B 两条线路共同引用 P1。登记整塔 P1→P2 时必须展示 A/B 的关联与影响确认并保存历史；单改 A 的关联纠错不得悄悄迁移 B。

**待细化：** 存在部分回路仍沿用旧实体、历史换位或迁改过渡时的完整流程；是否由系统自动选择全部关联回路或必须逐个确认（不得未经核实自动更改）。

## C03 正式入库必须达到业务完整性门槛

**裁决：同意。** 项目储备草稿可逐步完善，但**正式入库**至少必须有项目类别、有效需求、明确工作量及有依据的初步估算。允许个别单价“待核”，不能将未知价格当作零价。

必须满足：
1. 入库前核实项目类别有效，关联需求已核实且范围/数量有效，入库范围没有冲突。
2. 存在可检查的初步估算依据；缺价以“待核价/金额未知”记录并在入库快照显式表示，不以 0 元伪装完整估算。
3. 入库形成不可覆盖的项目范围和估算快照，保留确认人、日期及依据。正式立项仍须消除关键缺价、绑定唯一有效协议并确认批准预算。
4. 不能让未达到门槛的草稿通过直调 API 绕过入库校验。

**验收例：** 缺类别、缺有效需求、缺工作量或完全没有估算依据时拒绝入库；仅部分单价待核时可入库但不能直接立项为完整预算。

**待细化：** 物资明细是否必须在入库前逐项编制、无物资作业如何标记不适用；初步估算最低字段、人工机械及税费依据、不同项目类别的差异门槛。

## C04 疑似重复需求跨批次提示，必须人工判定

**裁决：同意。** 同一实体/逻辑位置、对象及作业在不同时间或不同来源重复出现时，系统给出疑似重复提示，由核实人员决定是追加已有需求来源，还是登记确属复发/独立范围的新需求；**不得自动合并或自动重复计量**。

必须满足：
1. 检测跨批次历史需求；展示候选需求编号、当前状态、关联位置、作业类型、具体部位和历史依据。
2. 明确选择“归并来源/关联已存在需求”或“确认为新需求并说明差异”。处理前保留待核状态，不静默新增重复有效工作量。
3. 多来源事实独立保存、引用同一需求时不复制工作量；复发问题另建需求并说明时间/对象差异。
4. 对共塔实体公共作业与各回路独立作业分别判定，不能单凭同一物理塔自动合并线路侧需求。

**验收例：** 第二批录入与第一批同塔同部位同操作，系统提供历史候选并要求人工确认；追加来源后原需求工作量不翻倍；确为复发时可留依据新建。

**待细化：** 候选匹配规则及阈值、被退回/取消历史的提示范围、审核角色和人工覆核的界面细节。

## C05 项目编制与正式入库、立项确认权限分离

**裁决：同意。** 编制人员可以创建和编辑储备；**正式入库**及**立项批准**必须由分别具备对应确认权限的人员明确操作，不能用普通编辑权限自然继承这两项审批权。

必须满足：
1. 服务端独立校验“储备编制”“入库确认”“立项批准”的授权能力，不能仅隐藏前端按钮。
2. 提交人、确认人、确认时间、结论及审批依据进入不可覆盖的阶段事件和审计轨迹。
3. 无权限的 `editor` 不得通过旧接口、直接请求或导入路径绕过正式确认。
4. 已确认阶段的变更/撤销遵循正式流程，不能使用普通数据编辑覆盖审批。

**验收例：** 仅有编制权限的账户可编辑储备，但执行入库或立项端点被拒绝；有相应权限的审核账户才能确认，且记录审核身份。

**待细化：** 是否设置不同的入库/立项审批岗位、是否禁止同一人自编自审、是否支持多级审批及代岗、权限如何与现有四角色兼容。未确定前不得自行假定审批流级数。

## C06 立项后范围与预算的调整必须使用变更单和新批准版本

**裁决：同意。** 立项后增加、减少、替换需求范围，改变核定工作量、价格/物资方案或批准预算，不能直接覆盖原批准记录；必须通过正式变更单形成新有效批准版本。

必须满足：
1. 变更单具备稳定编号、原批准版本、拟修改事项、原因及证据、调整前后量价与金额差异、审核结论和操作者。
2. 新增范围须引用有效需求及明确未承接部分；缩减不能抹去已安排、已完成、已发生费用或已结算事实。
3. 批准后产生新的有效项目范围/预算版本，旧版本及其事件保留；**每一个执行批次明确引用自己采用的批准版本**，不随项目最新版本漂移。
4. 超预算、取消和冲销须保留完整对应关系，框架与协议额度和实际资金归集按有效版本/有效事实重新计算，不重复累计历次预算。
5. 未完成正式变更审批时，继续拒绝通过普通编辑绕过范围冻结。

**验收例：** 立项 B1 后创建 E1；变更单批准生成 B2，再创建 E2。E1 始终引用 B1，E2 引用 B2；审计与结算能追溯各自依据。

**待细化：** 变更审批角色、变更类型与预算额度预占规则、在途执行如何处理变更、执行已开始但未完成时的范围释放及差额处理。

## 开发门禁及实施顺序

- **立即生效的规则**：上述 C01～C06 全部为已确认的目标业务规则，后续所有新实现必须符合；已有代码不符合者记为待整改，**不能描述为已实现**。
- **优先修正**：C01 完成量/释放算法及历史；C02 统一实体/逻辑塔写入规则和共塔换塔；C05 将正式审批从普通编辑权限拆开。均须增加后端隔离集成测试和浏览器端到端验收。
- **后续业务构建**：C03 入库门槛及估算明细；C04 历史需求重复核实；C06 变更单、批准版本和执行绑定。C06 与实际费用/结算关系一并设计，不得先将旧版本静默覆盖。
- **统一写入规则**：新线路工作台、旧台账 API、Excel 导入及批量接口必须使用一致的核心不变量；不能让某个入口绕过审批/历史/数量校验。
- **数据迁移**：现有真实数据必须迁移保留；禁止未授权清库、重置稳定 ID 或覆盖入库/立项/执行历史。先使用隔离测试数据库验证。
- **验收与发布**：除新增场景外，已有测试必须通过；目标运行环境为 Windows 10 x64 便携 ZIP，PowerShell 5.1 中文脚本继续保持 UTF-8 BOM。Win10 实机通过之前不得宣称实机验收完成。
- **未决定内容**：以上各节的“待细化”不是拒绝执行已批准原则。开发人员先整理可选方案、影响和推荐理由供用户审定，不得默认创造正式审批政策或业务规则。
