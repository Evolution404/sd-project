# 子项目全生命周期统一治理方案（2026-11-13）

> 项目：`sd_project-rewrite`，基线 `78e9ef5`。本次为**只读业务代码审计与实施方案**，未据此直接更改子项目生命周期服务或Schema。审计时 Windows 打包规则另按用户授权修改。全部演示和反例仅在临时隔离库中执行。

## 一、最终业务裁决与原则

1. 项目底层正式阶段仅 `reserve / stocked / approved / closed`；用户唯一可见「项目状态」为**储备、已入库、立项中、已批准、变更中、已结项**。其中「立项中」和「变更中」由有效审批草稿派生，不另存状态或另一列办理进度。
2. **一条需求只能完整承接**：单个子项目对需求内全部位置、确切数量整体采用；不支持承接比例。需要只实施部分时先正式修订/拆分需求，剩余工作如仍有效须另存独立需求。允许一个项目只选择若干条完整需求。
3. 正式批准范围、预算、采用的需求版本、位置数量及物资均有不可变历史。变更中仍以**上一正式批准版**办理费用、分次结算和统计；草稿不改动有效事实。
4. 已批准项目**不可通过普通关联/批量关联增加需求**。新增与移出需求一律经正式范围变更；变更草稿候选需求不应提前占用独占归属。正式变更批准时，统一事务完成需求独占检查、项目绑定、移出处理、版本冻结和变更决定。
5. 已结项保留全部批准/结算/费用及需求关联历史，不得普通新增费用、关联、结算、批准或修改。只有明确授权的独立纠错/补录流程才能追加合法纠正事实，**不得直接切换阶段复活**。
6. 子项目必须属于年度框架，可以直接归属框架，不强制执行协议。入库后框架不可直接改；协议是可选关联及独立历史，不与正式批准预算或实际结算混账。
7. 分次施工与分次结算继续支持；预算、参考价、真实费用、结算金额及已解决工作量独立。未完工、超量或费用差额允许在核对后正式结项，不能造假凑齐100%。

## 二、已确认的缺陷与证据

| 等级 | 现象/实际测试 | 根因/位置 | 治理方向 |
|---|---|---|---|
| P0 | **已批准项目仍能新关联完整需求**，未进正式批准范围；隔离测试验证绑定数量增加、正式范围不变 | `projects/service.ts::preflightLink` 仅阻止closed/deleted；`ProjectPage.vue` 范围页同样只禁closed；SQL `project_demand_scope_current_owner_insert` 未限制approved | 普通新增关联只限储备/已入库且无活动草稿；新增需求仅作为变更草稿意向，批准事务才创建绑定 |

| P1 | 结项检查未显式逐项核对**已有审核通过结算上的未提交新修订草稿**；需要复现并补测 | `project_close_guard` 查最新正式结算版本和审核动作，未直接查 `settlement_drafts` | 增加未完成草稿与审核事件的统一检查；给出未结事项清单，避免结项后草稿悬挂 |
| P1 | 当前参考价仍是人工试算/确认、批准页「按承接范围核价」，与最新“需求属性自动计价”裁决不一致 | `PricingQuoteDialog`、`projects/ProjectPage.vue`、计价服务 | 后续专项重构：自动、可解释、完整计价；保留当前价与批准快照隔离，去除人工确认 |
| P2 | 生命周期的6态相关SQL和前端状态、操作矩阵散落多个组件和服务 | `project-display-status.ts`、`actions.ts`、`finance/service.ts`、Schema触发器 | 共用一套纯业务决策策略和测试契约；数据库仅做不可绕过的不变量兜底 |

说明：数据库已实现批准版本不可覆盖、位置数量完整承接、独占需求、已批准需求不能直接解绑、正式结算版本审核及结项历史不可覆盖等强保护；**应保留，不做全量推倒**。档案的结项后管理计划修改已有数据库约束拦截，本轮未列为已复现缺陷。

## 三、六状态准入矩阵（推荐唯一契约）

| 可见状态 | 需求关联 | 需求移出 | 正式批准 | 费用/结算 | 档案/资金 | 结项 |
|---|---|---|---|---|---|---|
| 储备 | 普通表格批量关联；只承接完整需求 | 可显式解绑；留审计 | 不可建批准草稿 | 仅允许准备费用科目；实际费用必须按明确业务规则 | 框架、协议、档案可改 | 不可 |
| 已入库 | 可普通关联完整需求 | 可解绑未批准需求 | 可以编制首次立项草稿 | 尚未正式批准，不可正式结算 | 框架锁定，协议依版本规则变更 | 不可 |
| 立项中 | 原则上在立项草稿统一选择或移除整条需求；不允许普通关联绕过草稿 | 草稿中移出，正式归属按决议处理 | 可以批准或撤销立项草稿 | 不可正式结算 | 不能修改会导致草稿依据失效的字段 | 不可 |
| 已批准 | **不可普通关联新增需求**，须编制正式变更 | 须通过正式变更后原子移出 | 可以编制正式变更 | 可依最新有效批准版本新增费用、分次结算、核对 | 允许不影响批准事实的版本化维护；协议按正式历史 | 满足结项检查可办 |
| 变更中 | 草稿中的新增需求仅为意向，不抢占其他项目归属 | 原正式范围仍有效，不能先解绑 | 可批准/撤销变更；重核验全部需求版本和并发 | 依**上一有效批准版**继续办理 | 涉及草稿基线的关键字段冻结或重新核对 | 不可 |
| 已结项 | 不可 | 不可（含最新批准范围） | 不可 | 普通新建/更正/结算应冻结，例外须专门经批准纠错 | 只读，正式历史完整 | 不重复结项 |

其中“是否允许储备阶段录入预计费用科目”与“是否允许入库前产生实际费用”要以真实业务明确划界，不应简单把全部财务对象一概限制到批准以后；但**已结项普通写入必禁**。

## 四、执行方案

### P0：统一状态准入与兜底（先做）

- 建立 `ProjectLifecyclePolicy`（纯函数/领域模块），以正式阶段、最新批准、有效草稿、需求归属、用户权限为输入，返回许可动作及禁止原因。服务端每个写用例强制校验；HTTP只是接入，前端动作区直接使用服务端能力集合。
- `link/linkMany/createFromDemand` 重复采用同一完整需求检查；要求项目储备或已入库、无活动立项/变更草稿；单批原子成功/回滚和冲突码409。
- `approvalDraft` 校验首次立项必须 `stocked`、正式变更必须 `approved` 且存在上一已批准版，禁止储备、结项、交叉多草稿；SQL做同样的阶段断言。
- 冻结结项项目的普通 `node/cost/settlementDraft/reconciliation` 及所有间接写入口；对旧事实仅允许授权的历史追溯，不删除。结项后纠错是否需专门流程，另行独立裁决和实现。
- 错误提示明确“项目状态、被阻止的操作、可行的前置步骤”，不要显示 SQLite traceback。

### P1：重构“关联”与“批准范围”的边界

- 储备/已入库继续复用已经上线的表格跨页多选器，保留真实需求编号、操作类型、线路、数量、位置及详情；只关联完整需求。
- 已批准项目「编制正式变更」内使用同样的表格多选器，同时直观展示**原批准保留 / 新增候选 / 待移出 / 需求新版差异**。新增候选放变更草稿意向，不提前生成 `project_demand_link_events`。
- 批准时事务性复核：当前项目有效批准版本、需求active和完整定义、需求并发版本、唯一归属、材料及计价依据、预算差异；随后新建新增需求关联、冻结最新版批准范围，移出的需求写释放事件，记录授权人与批准时间。任何失败全事务回滚。
- 数据层建议在现有 `project_change_orders` 基础上引入**类型化变更候选明细**，区分待批准提案与正式绑定/已生效范围；不可将未批准候选伪装为正式 `project_demand_scopes`。复用现有不可变版本和审计事实，不另存第二个项目状态。
- 已批准项目变更中，有旧结算的已移出需求必须保留结算历史关系，产生受影响清单；不能自动抹去实际发生金额和解决数量。

### P2：项目档案与资金收敛

- 统一 `ProjectManagement` 命令与协议选项资格校验，删除独立 `fund` 写入分支；保留已有资金版本表作历史事实。
- 直接归年度框架必须是正常合法的完成态；协议可选、必须同一框架且有效。入库后年度框架冻结；协议改动明确展示已采用历史及对费用、结算使用的资金版本影响。
- 初步估算、批准预算、规则参考价、实际费用、结算金额不得互相覆盖或假定相等；协议剩余额度提示不当成硬阻断。

### P3：正式批准与需求版本

- 一条需求完整采用，准确等于每个正式位置的原始数量；调整需求必须先在专业需求模块修订或拆分，并在新批准版引用新的需求版本。
- 对变更差异按需求新增/移出/版本更换、位置、物资、批准预算自动形成变更摘要；审核人可查看清晰的差异表和证据，不必手动比对两张全量表。
- 计价以需求**自动计算参考价**为当前展示事实；批准时冻结所采用的规则与计算轨迹。费用类型支持逐位置、批次、项目三个作用域，未计价绝不伪装为零元；移除“确认正式报价”交互作为后续单独计价重构任务。

### P4：费用、结算、结项闭环

- 实际费用与结算单各自保存身份和不可变正式版本；批准后可分批结算；允许0新增解决量的纯财务更正/结算，但不能伪造施工进度。
- 每次结算只引用当时有效的正式批准范围；在变更中持续使用上一批准版。已确认历史及费用核对不可随变更发生漂移。
- 结项前生成**未完成需求、超量施工、实际费用/已结算差额、核对差额、未审核单据和未提交草稿**列表。业务允许不足或超量结项，但待审批的立项/变更、结算正式草稿和审核中的单据必须清楚地被处理。
- 结项事务生成完整差额快照和状态事件，自动审查并锁住后续普通写入。正式纠错若将来授权，需新型纠错决定、独立审批和前后报表连续追溯，不能改原结项版本。

### P5：统一用户体验、性能和权限

- 顶部仅显示一个项目状态与适用于该状态的主操作；详情按“项目概览—需求与范围—批准与变更—费用与结算—完整历史”组织。禁用按钮同时给出有效原因与下一步入口。
- 大型业务对象选择统一为可搜索/筛选/排序/分页、跨页多选并可查看详情的表格；小型字典和枚举可保留下拉。整条需求选择不能滑回“纯编号下拉”。
- 角色分开验证编辑、入库、正式立项批准、变更批准、费用确认、结算审核、结项、管理员删除权限；服务端独立核权，不依赖 UI 禁用。
- Portfolio 查询批量获取最新状态、批准和财务汇总，避免列表N+1；沿用当前Schema113专用Repository与数据库统一访问模块，不产生第二套通用SQL路径。

## 五、必须新增的验收旅程

1. 储备项目可关联完整需求，不允许部分数量或位置。
2. 储备项目直接编制批准草稿返回业务错误，入库后才可编制。
3. 入库、立项中、批准、变更中、结项六种状态前后端完全一致。
4. 已批准项目普通单条和批量关联均拒绝，新需求保持未被占用。
5. 变更草稿中新增多条候选需求，撤销后无任何关联及金额污染。
6. 正式变更批准同时完成新增关联、移出解绑、完整批准和审计；中间任一步冲突整批回滚。
7. 需求版本发生并发更改，变更不能带着旧工作量直接批准。
8. 需求拆分前不能部分承接；拆分后不同完整需求可分别关联不同项目。
9. 变更草稿存在期间，旧批准仍可正常结算，新的未批准需求不能提前发生结算。
10. 项目已结项后，费用科目、新实际费用、结算草稿、费用确认、需求关联及项目批准全部禁止普通新增。
11. 已结项项目不得解绑最新批准范围；历史查询、费用结算和台账快照继续可读。
12. 实际金额和解决量不足/超量时，显示差额并能合规结项。
13. 未审核结算、未提交修订草稿、立项/变更草稿阻止结项并说明具体来源。
14. 直接归属框架与选择协议两条合法资金路径，以及储备/入库后归属边界。
15. 已提交与历史正式批准版本不可覆写，费用、结算、需求和权限全留痕。
16. 同时点两个客户端对同一需求关联/变更时，只有一个成功；409和刷新入口正确。
17. Excel导入或其他服务写入路径不能绕过项目生命周期门禁。
18. Windows Demo离线包中覆盖储备、入库、立项中、批准、变更中、结项，以及完整需求、八种计价模型和多次结算，且不污染正式数据。

每阶段必须验证：严格TypeScript、`npm run check`、`npm run check:schema`、专用API/DB边界、关键浏览器流程、`npm run test:performance`、发布打包与Mac宿主验证、Git提交；Windows实机验证另列明确证据，不把Mac模拟当实机通过。

## 六、执行顺序及验收出口

**P0安全门禁 → P1正式变更与需求归属原子化 → P2项目档案/资金统一 → P3批准范围与自动参考价联动 → P4财务与结项冻结 → P5全角色体验及整包回归。**

P0必须先收口三项已复现可绕行缺陷，再改变变更流程。P1应作为核心架构任务，不接受只禁用按钮、继续让服务端绑定的“修补式完成”。整个方案要求应用层只有一条写入命令路径、数据库只承担稳定不变量、不新增冗余状态、不重新引入独立检修计划/施工或领料流水。
