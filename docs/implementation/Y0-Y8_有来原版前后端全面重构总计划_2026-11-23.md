## 1. 总体设计与不可谈判约束

目标：原版有来作为唯一前端应用主干，在上游 Layout、Theme、Pinia、Router、CrudPage/CrudSearch/CrudTable/CrudForm、Pagination、TagsView、User/Role/Menu 管理页面的基础上接入 12 个输电业务入口。**不制作自有仿造 UI，不通过改写 theme.css 模拟有来。** 保持原版布局和主题，必要适配须独立封装、记录 diff 和原因。

后端允许对应重构：**统一在 Node 24.x + TypeScript 6 运行**的模块化单体、统一 API/DTO、权限和业务命令；数据库使用 SQLite Schema113 为现有业务基线，确有必要才形成受控后续权威 DDL。不得为有来模板迁移到其他后端框架、引入多租户/Redis、复刻模板演示数据表、恢复已取消实体。业务事实、正式版本、审计、身份、附件与备份恢复继续完整保留。

架构：有来原版前端 → typed API adapter/契约 → Controller → Application Service → 领域校验 → 专用 Repository → SQLite。独立系统，无 PMS 兼容。金额整数分，数量整数乘 10000，采用冻结计量单位 0—4 位精度。所有业务写入仍以服务端事务、授权、幂等、乐观冲突为权威。

## 2. 技术风险优先勘察（Y0/Y1 阻断项）

上游所见 4.13.0 使用 Vue 3、Element Plus、Pinia 4、Vue Router 5、Vite 8、UnoCSS、SCSS、pnpm 10.34.5；package.json 声明 Node ^24.0.0。当前仓库为 Node 26、Vue Router 4 与 npm package-lock、Windows 离线 Node26。**不能直接假定版本兼容**。

**2026-11-23 最新用户裁决：不再在 Node26+旧 npm 与上游运行环境之间二选一，统一采用有来原版运行环境。** 在独立临时目录先验证原工程 Node24、pnpm 10.34.5 的 install、type-check、build 和浏览器启动；然后将原项目后端从 Node26 迁移至受控 Node24，验证 Node API、SQLite、Excel、Playwright、备份恢复和 Windows 离线 runtime，保留实际测试日志。在完成验证和 Windows 打包修订前旧脚本 Node26 的固定检查仍作为旧版本基线门禁，不得提前删除。最终仓库只保留 pnpm 一套包管理工具与 pnpm-lock.yaml 一份权威锁文件，迁移正式完成后移除旧 package-lock.json。

上游包含工作流、租户、代码生成、通知、富文本、表单设计器、VXE Table 等可选依赖；在离线环境按实际引用核查保留，**未使用的插件不因上游有就盲目引入运行时**。官方 HTML、布局、主题及必要组件本体必须真实运行，不能仅存文件在 docs/vendor。

## 3. 前端目录与迁移方式

过渡期在同一 Git 仓库内采用 web-next/ 放置完整上游前端应用（布局、主题、状态、通用组件、路由、设置、原版样板），现有 web/ 作为只读业务实现参考与迁移来源。避免第二仓库和第二套持久生产界面。新代码落地后一次性切换到正式 web/，删除被替换的旧 Layout、NavigationMenu、自有 CRUD/主题覆盖和无调用的兼容 API，仍输出 dist/web，不改变 Windows 包目录契约。

需要直接复用：BaseLayout、Left/Top/Mix/Double 的上游布局能力（产品默认 LeftLayout）、LayoutLogo、LayoutNavbar、LayoutToolbar、LayoutSidebar、LayoutMain、LayoutTagsView、LayoutSettings、Breadcrumb、CommandPalette、CrudPage/CrudSearch/CrudTable/CrudForm、Pagination、usePageTable、useTableSelection、TableSelect、DictSelect/DictTag、IconSelect/Upload/ECharts。原版 Dashboard 页面结构用于真实业务工作台。每项“采用/暂不采用/须适配”见同日《有来上游能力复用与差距审计》。

新前端只允许全局主题通过上游配置参数调整，不进行手工颜色、间距、圆角补丁式视觉仿写；复杂业务组件仅在其独立业务区域允许定制逻辑。专业数据编辑使用已授权 Tabulator 6.x 及 BusinessDraftGrid 行为契约；官方 CRUD 承担外围工具栏、筛选区、查看态、表单与分页；避免两个数据网格争夺排序、选区、剪贴板和 Undo 状态。

## 4. 后端 API 重构

单体服务内部继续分为 platform/http/auth/audit/files，modules/dashboard/demands/projects/funding/finance/equipment/materials/standards/pricing/dictionaries/system，domain，database/repositories、queries、schema，shared/contracts。

API 设计：DTO 显式类型；只为分页接口采用统一 PageQuery/PageResult（pageNum/pageSize/list/total），筛选、排序按公开字段白名单与多字段优先级适配；详情和表单回填分别使用 Detail/Form；标准 CRUD 接口与领域命令分开，不能让通用 store.update 绕过正式批准业务。服务端可生成 OpenAPI 契约及 TS 类型，字段一致性作为 CI 门禁。

保留同源 HttpOnly SameSite Cookie（现有 sd113 会话）、IP 限制、登录限流、服务端鉴权、Idempotency-Key 与 409 版本冲突；在 HTTPS 下 Cookie Secure，写入请求检查来源/CSRF 策略。前端对上游 Token Store 必须改为 Cookie 会话适配，禁止用浏览器长期保存 token。用户/角色/菜单接口按 Y2 方案调整。查询性能通过集合查询、索引及按需 DTO 改善；不得产生 N+1 或大表加载全部历史。

## 6. 执行阶段与退出门禁

### Y0 — 保护基线与来源
审计新分支的全部先前 WIP，保留结算工作表、测试和已知失败记录；备份演示库，记录当前监听进程/版本；核验原版 MIT、Skill、依赖和运行环境。禁止覆盖 data/demo。退出：一份可复原快照、所有未提交文件归属清楚、分支及依赖固定。

### Y1 — 原版前端真正启动
在 web-next 原生落地有来，不手写布局；完成 Login/Session、Layout、菜单、标签栏、搜索、主题及 12 个路由占位（占位不等于模块完成）。对照原版截图 1440/1280/960/760 两主题，必须是真正的原版原件在运行，且账号可登录。退出：UI 源码差异清单和结构视觉检查均通过。

### Y2 — 后端 API、账号模型和组织权限
先实施同日《账号角色权限与组织重构设计》。系统管理员角色默认全权限且后续可编辑，单账号多角色、多组织关联，菜单/动作/数据范围分别控制；用户禁用、会话撤销、权限变更实时生效；保持系统管理员对全部新权限的默认授予策略可配置和审计，避免特殊 ROOT 静默放行。统一 API DTO、权限映射、登录/个人中心。退出：越权、跨角色、最后有效管理员、Cookie/CSRF、安全事件、冲突和数据范围测试通过。

### Y3 — 四个功能与视觉样板
工作台、物资列表、需求详情、结算草稿先完成。工作台必须使用有来原 Dashboard 实际结构、真实统计；物资普通列表使用 Crud/Table 原版能力；结算借助原生外围与 Tabulator 工作表。退出：源码实际引用、真实业务持久化、同窗口对照截图、非假数据、无需自制主题，均通过。

### Y4 — 迁移剩余 8 模块
按需求→项目→框架协议→费用结算→设备物资→标准价格→基础数据系统管理完成 12 入口。逐模块做 CRUD、详情/办理、权限角色、历史、Excel 和冲突验收；若样板已覆盖模块，则在此完成剩余子页签。退出：无旧 UI 主框架对外运行，全部页面有真实交互截图。

### Y5 — 14 条业务旅程与数据事实闭环
覆盖需求确认/修订、项目承接/立项/变更、分期结算/退回重提/正式替代、费用核定、对账、结项差额及释放、跨项目接续、原始单位精度、设备关系、Excel 5000 单据/25000 明细、不同角色及并发重试。退出：新前端操作后服务端事实与独立接口/SQL核验一致。

### Y6 — 删除技术双轨及架构审计
完成唯一 web 交付、拆除旧 UI 组件和旧 API、缩减无用上游演示/租户/工作流等依赖；评估前端体积、首屏延迟、数据库索引/N+1、无用字段和异步请求竞态。退出：没有重复前端系统，没有后台并行复制事实。

### Y7 — 全量功能、视觉、性能门禁
正式切换后严格通过 pnpm run check、pnpm run check:schema、pnpm run test:browser、pnpm run test:performance（迁移前现役 npm 等价门禁同样不可放宽）和针对上游源码真实性、Token/Cookie、TagsView/KeepAlive、编辑撤销及键盘的新增测试；必要时执行独立三项 Python Schema 验收。截图必须显示 12 个入口的常态、详情、正式办理和复杂错误态；验收不可只看是否有 Vue DOM。

### Y8 — Windows 正式/演示版本、Git收口
在受控源码不变条件下生成 dist/web + dist/server，执行 pnpm run package:win、pnpm run test:package、pnpm run package:win:demo、pnpm run test:package:demo、pnpm run report:delivery；校验 Node 24 Windows x64、生产依赖离线安装、演示库安全标记、包内清单和两个 ZIP 的 SHA256；Mac 验证与 Windows 物理实机证据分别记录。按阶段提交 Git，未经另行授权不推送。

## 7. 上线/回滚与风险

- 在开发期新旧前端允许共存于同一仓库的临时目录；生产/演示服务只采用验收后唯一前端，禁止重复业务写入或双数据库事实。
- 当前演示 DATA_DIR = data/demo；任何测试须使用临时隔离 DATA_DIR；修改 Schema 先在副本验证，不能直接修改活动演示库。
- 视觉基线失败、权限越权、业务正式事实漂移、Windows 离线包不启动、任一关键浏览器/Schema 门禁失败均阻断交付；保留上一稳定发行包供恢复。
- 一项失败不得删除测试、放宽阈值或宣称完成；持续使用 docs/implementation 下的阶段验收矩阵记录状态、日志、截图、Git SHA。
