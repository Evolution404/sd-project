## 业务修复

- 已批准项目的普通单条和批量需求关联均返回业务冲突。新增需求在正式变更草稿的完整快照中保存候选定义，正式批准时重新核对版本、状态、日期、物资版本和独占归属，原子建立新增关联并释放本版移出的旧范围。撤回草稿保留不可变审计，候选仍可由其他项目合法承接。
- 变更候选参与参考价格完整性判断。候选缺价时总参考价格为 NULL，保留已计价小计和明确缺价需求。
- 执行协议维护复用项目档案的唯一写入路径，保留采用中的类别及组织正式版本，单独换协议不会生成无关档案版本。
- 初次立项草稿必须先完成入库。服务端、工作流操作提示、前端和 SQLite 使用一致阶段约束。
- 正式批准前核对需求完整正式版本，数量、位置、预计解决时间等任何修订均要求重编草稿。历史批准继续采用原冻结版本。
- 结项后的普通费用科目、真实费用、结算及费用核对写入冻结，API 和 SQLite 双重保护，界面禁用相关操作和结算导入。最新版批准范围内需求继续禁止解绑。
- 尚有未提交结算或已批准结算的修订草稿时，结项操作提前给出原因并禁用。服务端在创建结项事实前复检，数据库最终拒绝非法关闭。
- 执行协议的独立命令复用项目档案保存事务和校验，协议版本写入集中在同一函数。
