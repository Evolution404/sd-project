# 专业需求独占、逐位置结算与结项接续｜实施与验收

日期：2026-11-23
范围：Schema113、需求、项目批准、结算、结项、Excel、桌面端及训练检查

## 最终业务裁决

1. 一条专业需求同一时点最多有一个当前承接子项目，不允许多个未结项项目并行承接。
2. 初次承接采用全部有效位置数量；先前项目正式结项且仍有未完成量后，接续项目采用**原需求**的所有未解决位置及对应剩余数量。不能按人意选择部分位置、减少或重复接续；需求编号不变。
3. 项目执行期间分次结算，逐位置登记有效解决量。只有已审核且当前有效的结算版本计入累计完成；结算金额与解决数量独立。
4. 已批准项目不允许通过范围变更提前移出已批准需求。项目结项可以不足量，也可以超量，真实差异保留。
5. 项目正式结项时，先冻结每个已批准位置的批准量、项目累计实际解决量、尚未完成量及需求整体剩余量，再追加 `released` 关联事件；所有步骤在同一个写事务中完成。**仅未完成需求释放当前承接资格**，已全部解决的不允许新项目接续。
6. 历史项目、正式批准、历史关联事件、已审核结算及结项快照均不得删除或改写。后续项目在原需求上新增独立 scope/正式批准，账目按项目、位置及结算有效版本累加。
7. 正式需求位置使用 `位置类型:真实设备身份` 跨版本稳定标识，不能以需求版本内行序号跨版本核算。需求修订不得将其他位置的已完成量误算进当前剩余。
8. 用户可见状态「待确认／已退回／待承接／已承接／已解决／已取消」由现有正式生命周期、当前独占归属和各位置剩余量派生，不存重复状态。

## 实际变更点

- `server/database/schema/schema113.sql`：稳定位置标识、逐位置未解决视图、逐位置结算约束、独占与结项释放事务约束、正式批准接续范围校验；旧结构不升级正式数据库（纯开发测试阶段）。
- `server/modules/projects/service.ts` 与项目仓储：禁止并行承接、首次/接续完整剩余范围、在办不得提前释放；项目候选逐位置剩余量使用**单查询批量读取**，避免N+1。
- `server/modules/finance/*`：结算按正式批准位置逐项确认，历史批准版本及计量精度不可漂移；同单同位置禁止重复。
- `server/modules/projects/closure.ts` 及结项仓储：逐位置核对、结项事务自动释放未完成归属、历史批准完全保留。
- `server/modules/demands/*` 及业务列表：逐位置解决与剩余数量、已解决状态、已完成需求从候选清单剔除。
- `web/src/modules/projects/*`、`web/src/modules/finance/FinancePanel.vue`、`web/src/modules/demands/DemandPage.vue`：批准采用剩余位置、结算位置选择、结项位置核对、需求位置已解决和剩余数量。
- `server/modules/exchange/*`：结算Excel支持不可伪造的批准位置隐藏身份和可读位置标签；同名歧义拒绝；导出逐位置解决量。
- `server/database/repositories/training.ts`：学员已成功办理的签署和归属事实不会因结项合法释放而从课程验收中消失。

## 关键自动化场景

`tests/api/closeout-continuation.test.mjs`：三位置需求、项目A部分结算、A未结项前B独占冲突、A结项释放未完成位置、B只能批准全部剩余位置、B继续结算完成、全部解决不重复释放、历史批准及SQLite完整性。

既有结算、变更、解绑、Excel、Demo、P10及多次结算用例已同步升级真实批准位置与最新业务约束，**没有**采用“缺失位置默认为第1位置”的生产兼容分支。仅测试合成样本显式补齐其唯一测试位置。

## 执行环境与交付边界

- 开发与测试使用 Node 26；并行进行的 Node26发布流程修改保留在原开发目录，本工作树不覆盖。
- 原目录存在并行开发及未提交文件，本任务在隔离Git工作树实施和验证，不可未经合并直接宣称已进入原目录。
- 代码分支、Git提交及最终门禁通过情况以交付时报告为准。
- Windows正式版/演示版、Windows10实机安装和升级验证不在这项需求的业务功能验收之内；若需发布，使用发布任务的 Node26 配置并重新打包。
