# 专业需求预计解决时间治理实施记录

## 业务裁决

- 中文名称「预计解决时间」，唯一技术字段沿用 `expected_on`；不得新增 `expected_resolution_on` 或其他重复日期字段。
- 日期 `YYYY-MM-DD`；需求首次录入、储备项目、已入库项目、立项/变更草稿允许为空。
- 第一次正式批准及后续正式变更批准：**全部当前有效绑定的专业需求**日期必填。即使某条需求并未纳入当次批准范围，仍必须填写，否则整次审批拒绝；错误提示列出缺失的需求编号。
- 项目正式批准后，可在专业需求模块独立修改预计解决日期并生成不可变正式需求修订版本，保留审批时的旧需求版本及快照；仅修改该字段无需触发项目正式变更，不改变正式批准预算、结算及实际工作量。
- **草稿日期新鲜度**：正式批准时，所选择批准范围内每条需求的预计解决时间必须与编制草稿时冻结的需求快照一致（包括原为空、后来补填）。需求日期发生变化后，旧草稿必须撤销并重新编制；新草稿冻结最新日期。未被纳入当次批准范围的关联需求只校验当前日期必填，补填不强制重编批准草稿。
- 已批准或变更中（底层仍为approved）禁止清空当前绑定需求日期；已结项项目关联需求禁止普通修订。
- 为防旧API绕过，已批准项目直接关联的无日期需求亦被服务及SQLite阻止；更全面的「已批准不能通过普通关联新增需求」仍属于已制定的独立P0生命周期治理任务，不能因本次日期约束声称全部完成。

## 代码职责

- `server/modules/projects/service.ts::approve` 在同一事务内批量查询当前绑定的全部需求日期并校验，缺失返回422和需求编号；先检验后提交正式变更决定。
- `server/database/repositories/projects.ts` 提供单次SQL查询缺日期需求，`projectScopes` 投影用于项目列表/明细的日期信息。
- `outdatedApprovalExpectedDates` 对正式批准候选中含完整需求快照的每条范围执行日期新鲜度复查；应用层返回409和需要重新编制的需求编号；SQLite批准触发器双重保护。独立的Schema验收人工构造 `{}` 价格快照保持原契约，不用新增冗余字段。
- `server/modules/demands/service.ts` 使用专用Repository查询当前绑定项目的正式阶段，禁止批准后将日期清空，禁止结项后普通编辑。
- `server/database/schema/schema113.sql` 的项目批准终结触发器复核全部绑定的最新需求日期；需求正式版本插入及关联事件触发器防止直接SQL制造无日期的已批准关联关系。**不增表、不增加冗余持久字段、不修改原expected_on合法日期的结构约束**。
- Vue需求编辑、列表、详情、项目范围列表及关联需求表格使用统一中文名称；Excel字段映射 `expected_on` 不变，只调整中文显示及报表标题。
- Demo种子版本升级为V5，给已批准和待批准项目示例补齐日期，保留待确认需求日期可选。
- 专项测试包括未批准可空、草稿可空、全部关联验证、草稿范围原空日期补齐与非空日期改变造成旧草稿过期、SQL绕过拒绝、批准后日期修订独立于项目批准、结项冻结、Demo、Schema和全套回归。

## 交付规则

`npm run build`、`npm run check`、`npm run check:schema`、`npm run test:browser`、`npm run test:performance`、Git提交及Windows demo/formal包验收完成后，逐项记录结果。工作区可未提交打包，但发布清单必须准确标示源码指纹和Git基线，Windows真实电脑验收另行记录。
