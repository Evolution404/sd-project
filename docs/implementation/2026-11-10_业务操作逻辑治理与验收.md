## 本轮范围与原则

基线 `8c7bf52`。根据实际用户业务流“设备台账→操作类型/价格特征→需求确认→项目储备和入库→立项审批→执行协议/费用→分期结算→结项”治理 P0/P1 操作风险。正式历史保留、费用与参考价独立、不可用静默清空解决版本问题。此次代码继续采用 Vue3/Element Plus，未引入新的 UI 组件体系，也未在业务应用层加入 SQL。

## 一、正式参考报价：必须与用户预览结果一致

- `server/application/pricing.mjs` 计算结果附带 `preview_hash`，涵盖需求及其版本、批准范围、日期、全部位置的匹配规则版本及金额、显式选价依据与费率基数。
- `web/src/components/PricingQuoteDialog.vue` 保存试算时参数快照；任何影响计价的日期、规则选择、选择依据、基数变动即提示“计价条件已修改”，禁用“确认正式报价”，必须再次试算。
- `server/http/server.mjs` 对**HTTP 正式确认**强制提交有效 64 位十六进制预览指纹；不提供者返回422，过期/内容不一致返回409。内部可信服务调用保持兼容已有正式事务。
- 使用 `tests/api/approval-change-protection.test.mjs` 验证 API 试算→HTTP 无指纹拒绝/不匹配拒绝/匹配确认、确认金额与预览完全一致。浏览器测试验证更改价格日期后按钮变灰及重新试算恢复。

## 二、正式变更：继承既有批准事实并明确审核差异

- `server/application/projects.mjs` 在批准记录读取时由物资关联实体恢复真实的 `material_id`（展示用，不写入重复身份字段），供 UI 正确带入原批准物资。
- `web/src/pages/ProjectPage.vue` 编制变更默认继承原批准预算、作业位置、批准数量、物资 ID 和批准数量；新增关联需求默认不纳入。
- 对预算、纳入范围、作业位置/数量、物资及数量、需求正式版本变化做变更比较；要求用户核对并确认；服务端要求 `confirm_changes=true`，缺失直接拒绝保存有差异的草稿。原批准版仍完整保留。未经确认不得以省略物资的方式静默归零。
- `tests/api/approval-change-protection.test.mjs` 通过隔离演示库验证：原5套物资由新版继承、删掉物资却不确认被服务端拒绝、明确同意后可以创建正式变更且旧版仍不变。旧正式变更测试更新为显式差异确认。
- 用户主动变更批准数量/物资是允许的，不做不合理的“金额必须与预算相等”限制。

## 三、需求与操作：入口提前说明审批前置条件

- `server/application/projects.mjs` 子项目关联需求展示当前需求状态。
- `web/src/pages/ProjectPage.vue` “关联需求”默认展示已确认有效需求；可选“显示待确认需求（仅能关联储备）”，并说明暂不能立项；编制立项时拒绝无有效需求，未确认的需求默认不纳入批准。
- `web/src/pages/DemandPage.vue` 切换操作类型时，原自动验收标准被新标准替换；用户自行编辑的验收标准保留并显示核对警告，避免错误套用新旧规则。

## 四、工作台与确认：由数据查看转为实际办理

- 工作台指标可以打开需求、待确认需求（已筛选）、子项目。
- 工作台项目表增加“进入办理”，预警带稳定 `project_id` 并增加“处理预警”；`/projects?project=<id>` 直接打开对应子项目详情，浏览器已验证。
- 项目入库、正式批准、撤销草稿、结项弹窗采用不同标题，展示项目名称及具体业务后果、批准预算/需求数等，不再统一提示“确认执行此次正式操作”。
- 核心保存反馈改为收到成功响应即告知“已保存，正在同步/刷新列表”，保留操作期间的防重复提交锁，避免出现提交成功但尚在等待刷新时用户误以为没保存。

- 自动化通过不等于业务操作员主观体验验证结束；首轮真实用户使用时建议重点确认跨需求版本变更、物资核定和预算差异的文案是否清楚。
