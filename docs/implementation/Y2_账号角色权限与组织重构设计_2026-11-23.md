# Y2 账号、可编辑角色权限、组织和会话重构设计（2026-11-23）

> 用户已确认的唯一角色默认裁决：**系统管理员默认授予全部权限，后续这些权限可以编辑**。禁止把“ROOT/管理员”实现为永远绕过权限表的硬编码特例。
> 当前只是已批准设计，不代表新权限表或前端页面已完成。实施分支 codex/youlai-fullstack-rebuild-20261123。

## 一、原模型事实审计

- server/database/schema/schema113.sql 的 users = id/username/password_hash/role/status/created_at，role CHECK 仅 admin/editor/verifier/viewer。sessions 以 token_hash 保存会话；role_permissions 以 role 文本作主键；permission_definitions 仅列七项正式业务审批权限。
- server/platform/auth/service.ts: actor() 根据 user.role 拼接 read、write、admin 和 role_permissions；authorize(write/admin)仍硬编码角色；用户只有单角色，saveUser 修改后撤销其全部 sessions。
- server/database/repositories/identity.ts：users()、role 权限和 session 持久化均集中；server/modules/management/service.ts 管用户与审计/访问策略。
- 现有项目 organizational_units / organizational_unit_versions 是独立正式组织版本，不与 users 当前所属组织建立正式多对多关联；不可重新创建一份互相竞争的部门树。
- 有来上游 UserInfo/RoleForm/数据范围和 RBAC UI 可以复用，但它的 utils/permission.ts 按 ROOT 角色永远放行，需替换成服务端返回的实际权限集合而非仅更名 ROOT；Cookie 会话不等于上游 token/refresh token。

## 二、新模型及权限语义

身份 User 与 Credential 分开，登录名可改但 users.id 不变；User 可有多角色、多组织关联及首要组织；联系方式可选，手机号不作为必须提供的验证渠道；默认登录继续用户名+密码。新增用户显示姓名、岗位、工号（有值时唯一）、头像、邮箱/手机号（可选）、状态、创建/更新时间、最后登录。

Role 是可自定义管理对象，包含 id、code（稳定）、name、status、sort_order、system_seed、auto_grant_new_permissions、created_by/updated_by、version；**system_seed 仅是来源标签，不意味着不可编辑**。初始化模板：系统管理员（初始拥有全部已定义菜单/动作权限）、业务编制、业务审核、只读、审计等；系统可另建自定义角色。用户可多选角色。

Permission 是服务端代码定义的稳定动作资源：code、name、category(menu/action)、description、module、risk_level。面向用户的角色页面允许修改角色与 permission 的关联，**不允许通过 UI 创造未经过服务端注册的任意业务命令**；新动作权限注册应有显式默认授权审计策略。系统管理员角色新增权限的 auto_grant_new_permissions 默认为 true、可由授权管理员配置；手工撤销现有权限不会被后续部署自动补回。模板中的新权限出现后处理要有回归与审计。

角色权限支持按模块树、页面、操作分别勾选；权限可读范围不等于业务动作权限。菜单树负责 UI 可见和路由入口；业务动作必须先由服务端凭有效会话检查权限，然后按对象状态、正式版本、业务范围和审批资格判定。前端不可仅根据菜单存在放行。

多个角色的操作权限取并集，但数据范围只取**授予该操作的那些角色**的数据范围并集，防止把“全局只读”和“局部审批”拼接成“全局审批”。数据范围模式：全部、本人、指定组织、组织及下级、自定义组织集合，选用组织的稳定 ID/历史关系，不通过当前组织名称/层级自动重写已有项目归口单位。组织范围只限制已有明确归属语义的业务模块；无法定义归属的模块先使用现有授权范围，禁止自创关联字段。

默认系统管理员可执行全部授权操作，包括业务审核；用户没有授权改变“管理员自审”的业务规则，是否禁止自己审核自己的提交应单列待确认业务裁决，未经决定**不擅自新增此限制**。

## 三、数据库目标（按权威 Schema 维护，不增加双轨）

| 目标表 | 核心字段与用途 | 注意 |
| --- | --- | --- |
| users | id/username/display_name/employee_no?/primary_org_id?/status/created_at/updated_at/version | 稳定 user.id，业务审计继续引用 |
| user_credentials | user_id/password_hash/algorithm/password_changed_at/require_change | 仅认证模块读取 |
| roles | id/code/name/status/version/auto_grant_new_permissions | 可自定义；系统管理员角色也可修改权限 |
| permission_definitions | code/title/module/kind/risk | 扩展现有权威定义，勿复制第二张 permissions |
| user_roles | user_id/role_id/assigned_by/assigned_at | 多对多，支持取消授权 |
| role_permissions | role_id/permission_code/granted_by/granted_at | 替代当前固定角色字符串主键 |
| user_organizations | user_id/org_id/is_primary/assigned_at | 复用原组织稳定 ID |
| role_data_scopes | role_id/permission_code?/scope/organization_ids_json?/version | 与动作角色绑定，防权限跨角色提升 |
| sessions | token_hash/user_id/created/expires/revoked/last_seen/device/ip 等最小必要字段 | 会话失效可立即控制；敏感字段限授权 |
| security_events | user_id?/actor_id?/event/ip/created_at/metadata | 登录与凭据类安全事件，正式业务审计仍用 audit_events |

若决定对个人进行权限例外，优先通过自定义角色来组合，首版不新增 user_permission_overrides，避免 deny/allow 两套优先级和审计复杂度。无正式生产数据的开发期可调整 Schema，但严格使用隔离测试 DATA_DIR，**不能静默操作正在使用的 data/demo**。

## 四、管理 UI/接口

直接复用上游 src/views/system/user/index.vue、role/index.vue、menu/index.vue、dept/index.vue 的结构与 CrudPage/CrudTable/CrudForm、TableSelect/Dict 等组件；适配现有业务 API 和组织正式版本，不搬有来演示的租户表/部门表。系统管理包含：用户管理、角色权限、菜单授权、组织成员、安全会话、IP/访问日志和审计。个人中心支持修改密码与查看会话。

最小接口：GET /api/session（含 users.id、显示名、roles[]、permissions[]、菜单能力、权限版本）；GET/POST /api/users、PATCH /api/users/:id、POST /api/users/:id/disable、POST /api/users/:id/reset-password；CRUD /api/roles、PUT /api/roles/:id/permissions（带 expectedVersion）；GET /api/permissions；用户角色与组织关联管理 API；GET /api/me、POST /api/me/password、GET/DELETE /api/me/sessions、GET /api/navigation。实际命名在 OpenAPI/TS 契约评审时固化，不保留不必要的旧 API 双轨。

权限变更成功后由服务端统一版本化撤销受影响用户现有会话或让其下次受保护请求立即重算权限；路由/标签/缓存重新校正以避免残留过时可见按钮。权限管理 API 禁止依赖前端传入的自称 admin 标识。

## 五、系统管理员初始全权且可编辑的安全边界

- 初始化时给系统管理员角色授予 permission_definitions 中当时全部已定义的菜单/操作权限，**数据范围默认全部数据**；以上每项及数据范围均允许之后通过授权界面修改。新权限按 auto_grant_new_permissions 明确规则授予，记录授权审计。**角色默认全权不是不可撤销的永恒特权**。
- 修改、取消或禁用最后一个能够管理用户/角色/授权的有效账号时，服务端事务内拒绝并返回可解释的冲突，不在浏览器硬编码；检查多角色合成后的实际权限、账号状态和角色状态。
- 安全恢复只允许主机管理员在本机受控环境通过有审计的恢复流程重新授予管理角色；不提供隐藏 HTTP 后门，不因“ROOT” 字符串自动放行。
- 更改角色授权必须有预览（当前影响用户数、关键权限、会话影响）、确认和 expectedVersion 冲突保护；修改成功保留变更者、前后权限快照、时间与理由（管理员理由可空）。
- 密码管理：加盐密码哈希保留算法版本，新增账号临时初始密码且首登改密，密码变更/账号禁用立即吊销会话，限流包含来源 IP 与账号维度；Cookie HttpOnly、SameSite，HTTPS Secure，受保护写入来源/CSRF 策略。无需第三方短信服务，也不强制手机号。
- 现有访问策略开启时仅白名单和回环可访问；关闭仅放宽 IP 条件，不取消认证和授权；本机无外网仍可用。

## 六、阶段门禁与验收用例

1. 角色和账号：新建、编辑、禁用、逻辑删除历史、角色多选、组织多选、最后管理能力保护；多角色并集、已撤销权限不因新权限发布被悄悄恢复；系统管理员可主动去掉 project.approve 等业务权限并在该命令收到 403。
2. 权限范围：只读全部 + 局部审核不能组合出跨组织审核；菜单可见但命令无权必须被服务端拒绝；修改后缓存、标签、会话立即更新。
3. 安全：口令错误限流、Cookie 属性、伪造权限、CSRF/Origin、权限修改并发 409、被禁用用户旧会话 401、用户重置密码、最后有效管理员保护、审计动作完整。
4. 业务：需求确认、项目批准、结算批准、费用核定、数据范围、导入、离线 Windows 运行等完整跨模块权限矩阵；非标准业务权限仍由正式服务端约束。
5. 数据结构：正式用户 ID、审计事件 actor_id、项目相关 changed_by、既有组织版本引用稳定，不出现第二套用户、组织或审批账本。

## 七、仍待明确、不擅自实施的新规则

- 是否要求编制者与审批者必须为不同自然人、是否允许系统管理员本人审核；用户本轮只确认“默认全部权限，随后可编辑”，并未确认新增职责分离硬约束。
- 用户多组织时组织范围默认按主要组织还是逐角色的组织范围计算；建议按逐角色授权范围，业务预览说明。
- 是否启用动态菜单编辑器修改导航位置与路由显示；原则上可以编辑显示与授权，但不能通过 UI 注入任意前端组件路径或新业务 API。
