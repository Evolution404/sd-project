# sd_project｜UI全操作复审、缺陷收口与业务待裁决（2026-11-12）

## 一、本轮范围与结论口径

- 用户最新要求：**暂停P10新开发**，优先收口现有实现，复审全部主入口的增删改查、操作前置条件、状态迁移、权限提示、异常处理、列表筛选、弹窗及跨模块跳转。
- 本文审查的是可见的正式业务UI及其服务端约束，不以帮助登记、操作锚点数或测试数量代替可用性验收。未对P10注册、课程、训练功能进行扩展。
- 12个正式导航入口：工作台、专业需求、子项目管理、年度框架、执行协议、费用与结算、输电设备台账、物资管理、作业标准、参考价格、基础数据、系统管理。Excel/证据附件属于横切操作。
- 审计方式：逐文件审视关键流程、按钮回调、禁用条件、权限、数据库状态约束，对照自动化浏览器回归（包括四角色、列表、空库、版本、结算与Excel）。**这不等于对所有控件的每一种角色、状态、窗口尺寸完成逐一人工点击**；未覆盖的组合不宣称通过。

## 二、确认并治理的UI缺陷

| 优先级 | 入口/问题 | 原因与影响 | 本轮处理 |
| --- | --- | --- | --- |
| 高 | 专业需求→关联子项目，分页异常 | 服务端已分页后又在浏览器过滤“已结项”，导致每页数量与总数不一致，某页可能全部空白 | 保留服务端原页；已结项项目标明不可选；选择及提交双重检查 |
| 高 | 专业需求→关联子项目，隐式串选 | 换页或搜索后仍保留之前选中的不可见项目ID，可能错误提交 | 每次检索/换页清空选择，提交前核对所选项目必须属于当前有效候选页 |
| 高 | 子项目→批准与变更，重复草稿 | 存在未批准草稿时“编制正式变更/立项范围”仍可点击，但服务端明确拒绝 | 有草稿时禁用并解释需先处理，匹配服务端唯一草稿规则 |
| 高 | 专业需求→已删除记录仍出现可办理动作 | 已删除详情沿用生命周期按钮判定，仅靠后端最终阻止 | 将删除状态纳入确认、关联、修订、状态变更、来源更正/删除的禁用条件 |
| 高 | 专业需求→已关联需求仍可点“取消” | 数据库禁止已关联需求取消，但按钮未解释前置的“显式解绑” | 对已关联需求禁用取消并提示前置操作；退回的后果文案明确说明不会自动解绑 |
| 高 | 需求、项目未满足删除条件仍可点“删除” | 需求需先取消；已正式批准项目需先结项；原UI仅判断管理员 | 按服务端状态和现有关联禁用删除，说明操作前置条件 |
| 中 | 费用→撤销费用 | 取消和服务端失败没有捕获，成功后父级统计未通知刷新；已撤销记录仍可重复点 | 捕获异常、通知父组件刷新并对已撤销状态禁用 |
| 中 | 附件→删除、列表读取 | 取消或网络失败存在未处理拒绝；读取异常可能沿用旧附件列表 | 增加异常反馈、清空失败列表、编码参数 |
| 中 | 公共行操作→弹出更多操作 | 动作打开模态框后下拉菜单关闭态偶发不同步，第二次点击“更多”可能反而关闭菜单 | 执行动作前显式关闭菜单，增加树形费用作废及行操作回归 |
| 中 | 需求→批量添加预计物资 | 循环逐个更新需求表单，后一个物资单位读取失败会造成“部分已添加” | 先并行完成所有单位精度读取，全部成功后才更新父表单，避免部分写入 |
| 中 | 需求→操作属性及物资搜索 | 异步返回可能覆盖后来选择的正式版本；请求失败未被捕获 | 添加请求序号隔离、错误反馈、失败时重置待选列表 |
| 低 | 费用与结算跨项目查询显示未批准预算 | 尚未批准的null金额使用普通数字格式可能被误解为0 | 未核定或未批准时显式显示“尚未批准/—”，不改变原有金额精度显示 |

## 三、仍需用户裁决的操作含义（不擅自变更）

1. **已承接的有效需求能否“退回”？** 当前数据库禁止“已承接→取消”，但允许“已承接→退回”；退回不会自动解绑，项目可能仍持有一个不再有效的需求。两种可选口径：
   - A：已承接后禁止直接退回，先正式调整/解除项目范围并显式解绑；规则最清晰。
   - B：允许原关联保留，显示异常和后续恢复确认的闭环，项目新的正式批准必须严格阻止无效需求。
   建议A，但涉及业务政策，**未授权不得直接修改状态流转**。
2. **结算“退回”后与“编制/修订”的关系。** 目前退回、修订、再次提交存在不同入口，需决定退回是否必须填写退回意见、是否冻结原提交版本、在哪一步重新产生审核序号；现有权限和多次结算保留。不得直接把退回当作删除。
3. **真实费用“撤销”与“删除”的业务区别。** 两个动作并存、均可能影响汇总，但用户需能一眼理解适用情形：建议“撤销=该笔原费用无效；删除=从正常清单移除且保留事实历史”，对是否可以撤销后再删除、对既有核对的影响增加明确结果预览。当前不自行改变服务端约束。
4. **批准范围编辑与参考价格“新增批次/项目参考费用”的前置关系。** 当前按钮在批准页保持可见，但缺少对“有无当前草稿、旧批准是否已生效、参考价重算及失效”的同屏解释。建议按状态明确提示“计价依据归属于哪次批准草稿”，对旧价格保留历史而不偷换新批准。
5. **关闭/删除项目与“显式解绑”流程。** 现有历史逻辑允许结项后显式释放需求供其他子项目承接，但用户尚需确认：结项时是否主动提示剩余量/未解决需求和可释放范围，是否要求新的项目沿用原需求身份或另建需求。不能由界面暗中自动解绑。

## 四、现有设计需要继续关注但不能冒充Bug的事项

- 专业需求多位置需要准确区分“对象位置”与“归属单元”；通道不等于档距，档距只作为具体点位信息。
- 子项目的需求、批准范围、实际费用、独立结算、正式核对各有独立历史及权限；金额可超预算，结算可分多次，不得由UI强制数额相等。
- 各正式对象的“停用”“删除”“撤销”“取消”“退回”不同；明确权限不足时禁用并说明原因，不能显示为同一效果。
- 来源更正目前借用“修订需求”整体表单；对单条来源的编辑效率仍有优化空间，但需要在版本保持/单条增删的合同下设计，而非无依据快捷改写。
- 参考价规则与额外计价属性、Excel多Sheet稳定身份、表格排序/列宽/持久化已纳入既有回归，但仍需要业务人员用真实防鸟清单审阅误操作风险。
