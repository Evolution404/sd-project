## 二、已经确定的架构

- 本地服务器 + SQLite + 本地附件存储，浏览器通过局域网访问统一Web入口。
- 前端建议Vue 3 + TypeScript，后端建议Node.js + TypeScript，单体应用按业务模块分层；具体框架、驱动及版本可合理选择并记录，不必为普通技术选择反复询问。
- SQLite数据库放服务器本地磁盘，不由用户浏览器或网络共享文件直接访问。附件、数据库、备份与程序目录分离。
- Excel只是导入、导出交换格式，不能成为业务对象层级或录入前置条件。
- 实时状态与费用汇总属于首期，自动定时提醒后续实现为可配置模块；不要提前搭建空提醒中心或将调度器作为业务运行依赖。运维备份与业务提醒分开。

## 三、不可改变的业务关系

### 1. 管理归属与项目流程

框架1:N执行协议，执行协议1:N子项目，子项目1:N执行批次。

一个已立项子项目只属于一个执行协议，框架从协议取得。储备阶段可暂待落实协议，立项前必须绑定唯一有效协议。已有事实后不能通过普通编辑静默改挂。

同一个项目从“储备 → 入库 → 立项 → 多次执行 → 结算/结项”沿用同一业务ID。从储备阶段就关联需求，入库及立项分别保存依据与版本。不再使用“一次项目级出库后执行”作为前置模型，项目入库也不是物资仓库入库。

每次执行明确解决哪些需求范围、完成多少工作量、使用哪些物资及发生哪些费用；结算按执行需求明细对应，不能只在项目上登记无依据总金额。

### 2. 物理杆塔与逻辑杆塔

- 物理杆塔是实际资产；逻辑杆塔是该资产在某条线路上的身份及命名。
- 线路1:N逻辑杆塔，物理杆塔1:N逻辑杆塔。一个启用逻辑节点关联一条线路和一基实体，同塔多回共享实体，不能复制成多基资产。
- 电压等级来自线路，塔型/坐标等来自实体，线路杆塔号和沿线顺序属于逻辑节点。
- 稳定ID与可修改名称分开，逻辑顺序独立于编号，支持命名历史及实体关联历史。
- 需求引用逻辑位置，并保留当时核实实体和名称快照；更名、纠错、换塔不能改写既有实施和结算依据。
- SQL草案没有完整保证历史区间不重叠、当前值与历史一致、父对象状态、全部权限和并发。实际实现必须在事务与服务端补齐，每个SQLite连接启用外键。

### 3. 需求批量创建

单条需求的核算粒度是“线路 + 逻辑杆塔 + 操作 + 具体处理对象/范围”，但录入必须支持一次批量创建。

支持逐基多选、筛选全选、按真实线路顺序选择杆段、跨线路追加；切换线路保留已选位置，重叠勾选去重，不按编号连续性猜测杆塔。

共同填写操作、每项默认数量/单位、部位、完成标准、问题说明和来源，再逐项调整数量、部位或排除行。单独修改的行不能被共同默认值覆盖。

例如选择30基，每基安装2套防鸟装置，应生成30条独立需求，总工作量60套。共同来源记录一次后关联多条需求。工作量、物资数量和整批总量分别表达。

同塔线路侧设备作业分别保留。公共实体同一部位作业要由用户核对后合并或区分对象，不能单凭共塔自动合并；合并不重复累加工程量及费用。

保存草稿允许缺项；提交核实先逐项校验并进入待核实，核实确认后才是有效需求。提交可幂等重试，大批数据可以分片暂存，但不能静默跳过问题行、重复生成或暴露半批完成。

### 4. 业务选项必须可持续维护

操作类型、单位、来源类型、优先级、类别等由系统管理维护，提供新增、修改名称/编码、排序、启停；操作可配置适用对象、默认单位/数量、完成标准及字段模板。

正式选项与模板存入SQLite，刷新和服务重启后仍保留。设计稿中的数组只是示例，不能复制为生产页面写死的业务规则。

引用稳定选项ID、采用版本及名称快照。配置修改后新录入可使用；旧需求可编辑/修订，但不能被静默重解释。已引用选项停用仍保留历史，当前草稿遇到失效选项要明确提示，不自动换成其他值。

### 5. 估算、执行费用与结算

估算由需求范围、核定工作量、物资/施工量、价格/定额、日期、税口径及公共费用分摊形成，入库/立项保存版本。缺价不是零价。

执行需求明细连接批准范围、实际完成、物资使用、费用分摊与结算。共同费用分摊合计等于原额；各上级合计从有效明细计算，不重复录账，不因多表关联重复放大。

预算、预算发生、实际费用、结算和付款分别存储和统计。实际费用确认/冲销后立即沿执行→项目→协议→框架归集，不依赖定时任务。

结算需明确范围和对应费用；一单限同一项目，可覆盖多次执行，每次执行也可分次结算。记录“对应发生费用份额、核定结算额、差额原因、是否最终核对”。发生6000元、最终结算5800元且已核减200元，不应把200元误算为待结算费用。

实施和结算独立，保留有明确依据的提前结算，不伪造实施或费用；四状态自动计算，同时显示部分进度。需求整体范围是分母，最终结算范围与金额比例不同。

## 四、实施顺序与第一轮可验收结果

整体目标是完成主设计文档中的首期范围，请按可运行、可验证的阶段推进。

第一轮优先跑通“真实基础台账 + 系统字典 + 批量需求创建与核实”这一纵向链路：

1. 建立可启动的前后端及SQLite工程，提供统一开发/检查入口、配置说明、首个管理员初始化与真实登录，不设置公开固定生产密码。
2. 实现电压、线路、实体塔、逻辑塔的维护、同塔关联、历史和权限。
3. 实现操作、单位、来源、优先级等字典及模板的后端持久化、管理页和表单联动。
4. 实现批量位置选择、共同字段、逐行差异、来源关联、草稿、提交核实及确认，使用真实API和数据库。
5. 提供需求列表、详情、修订、筛选及Excel导入导出；按完整授权筛选结果导出，不拿当前页冒充全量。
6. 启动系统并通过浏览器完成实际操作，刷新/重启后确认数据、选项、关联及状态仍然正确。

随后继续完成储备及估算、入库与立项、执行批次、费用、结算、实时汇总、报表、分类及年度事项，按主文档A01—A36验收。不要把第一轮完成表述成整个系统完成，也不要只做登录页、菜单和假数据看板就停止。

## 五、实现与验证要求

- 金额使用整数分，数量/单价用定点精度；金额分摊及尾差有明确规则。
- 关键写入在SQLite事务中保持事实、关联、审计一致，实施幂等键、版本检查及并发冲突处理。
- 数据权限和业务校验放在后端；前端禁用控件不算校验完成。
- 为金额/数量守恒、批量重试、并发占用、历史关联、停用选项及四状态编写有意义的测试。运行类型检查、构建、集成及关键浏览器验收。
- 测试使用隔离数据库与合成数据，示例台账不要自动混入正式业务；程序升级不能覆盖数据目录。
- 使用SQLite一致性备份方式，并实际验证数据库与附件恢复，不能把只复制运行中的主文件当作完整备份。
- 对资金使用口径、真实价格、类别及年度事项等尚未核定内容，区分文档建议和正式事实。支持配置并标明当前口径；普通实现选择自主推进，重大业务歧义单独列出，不编造原始资料，也不阻塞无关模块。
- 当前飞书表格未核对，不要宣称复刻其真实字段或公式。不要将旧项目生产状态当作新系统验收结果。
- 交互参考中的`window.openai`状态、示例选项和预览结果只服务设计演示；正式应用应使用自己的服务端、SQLite、会话及附件管理。
