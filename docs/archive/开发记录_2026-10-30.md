## 本轮开发范围

本轮在现有开发分支上完成代码整改，未建立演示数据，也未覆盖原本地数据库。

### 1. 变更审批生效闭环

- 变更单支持新建草稿、编辑员提交、管理员批准或驳回。
- 批准操作全部封装在 SQLite `BEGIN IMMEDIATE` 单事务内，重验基线版本、项目状态、有效需求、工作量承接上限、协议预算上限、历史完成量、关联执行状态与净结算；非法情况整体回滚。
- 可通过变更单修改数量与价格、新增需求、停用范围、再次纳入曾被移除的需求。
- 批准生成新的、不可覆盖的 `project_approval_versions` 快照；项目有效预算只取最新版本，不重复累计历次预算。
- 计划或在途执行关联的范围在完成或取消前不可变更。已完成批次历史计划与实际完成量保持原值。
- 执行明细保存其批准版本时点的需求、量价快照，旧执行不漂移；新的执行采用当前最新版本，旧版本计划不允许在新批准版本生效后继续追加。
- 服务端权限：`editor` 可提交，`admin` 暂时可正式批准或驳回。实际审批岗位/是否禁止自编自审仍需业务裁定。

### 2. 结算凭证与四种工作反馈状态

- 新增独立的 `project_settlement_entries` 结算凭证流水。
- 结算凭证具有不可重复的外部编号、正向结算类型（预付/进度/终结）、真实金额、日期、依据、所属项目范围、批准版本和登记人。
- 支持通过新的冲销记录抵减原凭证，不能直接修改或删除原记录；累计冲销不超过正向结算金额。
- 每条有效需求范围的实际实施量只来自执行完成记录，已结算金额只来自结算凭证的净额，两者互不替代；可产生“未实施未结算、未实施已结算、已实施未结算、已实施已结算”四种组合状态。
- 超项目预算、超本范围金额的结算登记被拒；正式终结结算要求存在已结束执行批次的验收事实。
- 变更批准不能压低预算至已登记净结算以下，也不能直接删除存在未冲销结算的范围。
- 当前仅管理员可登记结算凭证；此为开发阶段的能力控制，不代表财务部门的真实签审流程。尚未接入财务系统或核验外部付款真伪。

### 3. 技术债清理

- 移除 v1–v12 增量迁移脚本、运行时逐版本升级代码和相关遗留夹具。
- 将最新完整 SQLite DDL 合并到 `server/schema.sql`，建库标记为 v101。首次启动一次性创建 37 张业务表及完整索引、外键、审计保护触发器和字典**类别**；不填充模拟业务记录。
- 旧结构不会自动清库，也不会执行兼容升级；版本冲突会 fail-closed，并提示使用新的数据目录。
- 默认 `make dev` 使用独立的 `.local-test-data/current-101`，不复用旧开发数据库。
- 金额转整数分、以万分位工作量计算金额、金额安全求和统一收敛到 `server/money.mjs`，避免项目、审批和结算分别实现计算口径。
- 审批版本、完成记录、结算凭证、审计事件均以数据库触发器禁止原地修改和删除（冲销应新增对应事实）。

## 验收范围

- `npm run check`：TypeScript 编译、Vite 打包、隔离 SQLite 测试，包括 C06 基线版本、E1/B1→E2/B2、额度冲突、在途防绕过、驳回、回滚、权限隔离、来源重复等。
- `npm run test:browser`：Chromium 正式界面从登录、台账、批量需求、入库、立项、变更单草稿、提交、批准，到结算凭证登记及四状态；另含审计、LAN HTTP、表单校验和移动端布局。
- Windows 10 x64 发行 ZIP 重新打包并校验官方 Node.js SHA256，**不代表 Windows 10 实机验收**。
