# 项目开发约束

## 2026-11-09 最新字段清理与受控升级授权

用户要求删除字段时，当前模型应完整删除，不在历史表保留废弃字段。本轮已完全删除线路架设方式的当前列、历史列、API、界面、Excel与查询校验。杆塔性质作为物理杆塔的独立正式属性，使用“直线／耐张”下拉，逻辑杆塔从关联实物取得，同塔多回复用同一事实，既有未知值保持空。

用户已明确授权“允许备份后受控升级”。本轮维护只接受原Schema113的确定结构指纹，执行完整备份、副本演练、事务升级及77表其余字段事实SHA256复核，保留所有其他身份、版本、关联、金额和审核事实。正常启动仍拒绝不匹配结构，不隐式执行升级。升级及回执见2026-11-09后续实施验收记录。

所有业务表头连续点击只在升序与降序间循环。操作类型维护保留真实的三个编辑页签，删除只有说明文字的“影响与预览”。Excel下载采用中文文件名和中文表头，新增必填与条件必填在字段名上方显示，字段绑定由工作簿元数据承担。


## 2026-11-09 最新交互与同号杆塔裁决

- 所有查看与业务详情统一使用模态框，保留背景列表、查询、分页和选中状态。模块与分类可使用正式路由，查看操作不跳转地址。本条覆盖历史的详情文档流和详情独立路由要求。

- 物理杆塔列表不用折叠行展示同塔多回，在查看模态框直接展示关联逻辑杆塔及其线路、杆号和状态。

## 2026-11-09 最高优先级永久裁决：不关联 PMS、用户不填技术编码

**用户最终确认：系统与 PMS 完全无关。** 不考虑任何 PMS 编码、数据结构、一次性导入、同步、映射、别名或兼容。旧版所有相反想法均作废，后续不得再次提出或恢复。普通 Excel 仅接收本系统的业务事实。

**线路 line_code、物理杆塔 tower_code、逻辑杆塔 logical_code 等内部身份不能让用户填写。** Schema113 创建入口统一由服务端生成这些身份，表单和新建 Excel 只采集真实业务事实。系统在受控事务中自动赋予身份或审计后精简冗余；其他主数据内部编码亦然。普通杆塔用户只选线路、填杆塔号和必要事实；同塔多回明确关联已有实物，歧义不静默关联。禁止改写已有正式历史及用户数据。

本条覆盖本文件所有历史条款中的 PMS 导入/测试、外部编码及手工编码要求。现行实现已纳入 `check:independent-input`、API、Excel 和真实浏览器防回归，后续变更必须保留这些门禁。详细见 docs/decisions/2026-11-09_系统独立_自动编码_最少录入.md。

## 2026-11-08 Schema 113 第十六轮最新裁决：操作类型、需求多位置与参考价格统一计价（当前最高优先级）

- **三方同源、一体计价但不混合业务身份**：`work_objects` 标准作业对象（例如绝缘子串、防鸟装置）与具体 `materials`/`material_versions` 型号规格必须分开；`operation_versions` 每版固定唯一作业对象、计量单位与允许的位置类型，不得直接存单价。`operation_versions.pricing_features_json` 声明每种操作需要哪些 `price_factor` 正式特征版本、来源和必填性，需求实际值和价目适用条件统一使用**同一套特征字典**，零物资的业务需求合法。
- **一条需求一种操作类型，允许多作业位置**：`demands.initial_work_locations_json` 保存原始多位置清单，`demand_versions.snapshot_json.work_locations` 保存每版完整正式定义；`demand_version_work_locations` 自动原子投影强类型位置、各位置数量、停电方式、现场特征、位置快照并锁定，不允许外部假造补行，不能重复列入同一塔/档距。版本总数量必须等于位置合计；多位置变化生成新需求版本。
- **项目只承接需求的部分位置和数量**：`project_approval_work_locations` 明确本项目批准的哪些位置及每位置数量；正式立项确认前必须与该批准需求范围总数量一致，不能按原需求整体参考价的数量比例分摊每位置基费。第十五轮“需求同一时点只能关联一个子项目，显式解绑才能转承”仍强制。
- **参考价规则版本化计价模型**：`reference_price_versions` 新增 `pricing_scope=work_location/work_batch/project`、结构化 `calculation_params_json`、不可变 `fee_components_json`，支持 `fixed/per_unit/base_plus_unit/quantity_bracket/progressive_bracket/group/rate/composite` 8 种规则，最低价/封顶、作业方式及正式特征字典匹配。物理塔的基费按位置一次，批次/项目级费用由 `project_reference_price_charges` 独立记一次。严格避免同位置综合参考价与人工材料等分项重复计算。
- **逐需求/项目正式计价结果有独立历史**：`reference_price_evaluations` 和 `reference_price_evaluation_lines` 锁定正式价格规则版本、逐位置数量和费用覆盖、计算参数、金额与引擎版本。`project_approval_scope_prices` 引用项目本次批准范围对应的完整已确认报价，未计价是 `NULL` 而不是0；旧 `project_demand_scopes.reference_price_version_id` 已删除（无法表达多规则），手工拟承接预算仍独立。`v_demand_reference_quote_current`、`v_project_approval_reference_basis_current` 是纯事实投影，不生成报告/金额汇总。
- **总参考价格必须完整且独立**：只有全部批准需求都选用完整正式报价时，应用才能计算 `Σ批准需求报价明细＋Σ不重复的批次/项目费用`；缺价须显示“未完整计价”，不可把已计价小计当作完整项目总价。`approved_budget_fen`、项目真实费用和分次结算独立，允许参考价与批准预算/实际费用不同。金额公式计算、Decimal舍入、条件优先级、价格匹配和应用权限**必须在未来应用层实现，不得塞入 SQLite 触发器**。
- **当前候选规模和验收**：77 STRICT 表、27 个非统计事实视图、249 个触发器、74 个显式索引、734 字段；**472/472 隔离 SQLite 契约通过**。最新设计报告 `docs/architecture/Schema113_第十六轮_操作类型_需求多位置_参考价格统一计价模型_2026-11-08.md`。**运行仍是 Schema112**，仅 Schema113 候选 SQL/验收/设计文档变更，严禁提前修改真实运行数据、前后端或实行业务迁移。

## 2026-11-08 Schema 113 第十五轮历史裁决：需求与子项目独占关联、明确解绑（仍有效但由第十六轮补充）

- **需求只有四种生命周期状态**：`pending`（待确认）、`active`（有效）、`returned`（退回）、`cancelled`（取消终态）。`v_demand_current.status` 从 `demand_lifecycle_events` 唯一推导。不要把“已关联子项目”伪造成第五种需求状态。
- **关联时立即独占**：任何子项目一旦添加 `project_demand_scopes`，自动在 `project_demand_link_events` 写入首条 `linked` 事件；同一专业需求同一时刻只能有一个当前关联子项目。其他项目在**添加关联时**就拒绝（不仅是正式立项时），直到原子项目明确 `released`。`v_project_demand_binding_current` 是唯一当前需求归属投影。子项目关闭不会自动释放需求，手动正式解绑是必须的。
- **解绑要保留正式历史**：`project_demand_link_events` 的关联/解绑事件连续、不可回写或删除，必须有真实操作人/时间；管理员原因可留空。项目尚未批准可直接释放无草稿的关联；项目当前批准范围仍包含该需求时必须先正式变更移出，或等项目正式关闭后再明确解绑；草稿仍引用需求时先移出草稿。原项目旧批准和结算历史不删除，新项目正式承接后各自分开计算真实需求解决数量。
- **不要永久封锁历史需求**：`project_demand_exclusive_approval` 仅审核**当下该需求是否仍由本项目关联**，不再用“历史上曾由别的项目批准”永久拒绝新的合法承接。`approval_scope_link_guard` 阻止新草稿引用已解绑需求，`demand_adopted_cancel_guard` 阻止仍被项目关联的需求直接取消。`cancelled` 需求不可新关联或旧关联重新激活。
- **无冗余状态**：已删除 `project_demand_scopes.proposal_status` 及重复的旧删除触发器，当前项目关联不能再在需求根或项目范围根存第二份可变状态。项目范围根固定项目、需求和关联创建人身份；取消关联只能写历史事件，不能改挂根身份。
- **第十五轮历史规模快照**：71 STRICT 表、25 个事实视图、224 个触发器、71 个显式索引、681 字段；**432/432 当轮 SQLite 数据库契约通过**。最新报告 `docs/architecture/Schema113_第十五轮_需求状态与子项目独占关联_显式解绑及重新承接_2026-11-08.md`。运行 Schema112 及实际应用文件和用户数据不得因为候选 Schema113 改动提前修改。

## 2026-11-08 Schema 113 第十四轮业务裁决（当前受第十五轮覆盖的历史裁决）

- **同基塔多套防鸟装置的真实数量计价**：`reference_price_versions` 的 `pricing_mode` 支持 `per_unit`、`base_plus_unit`、`quantity_bracket`；一笔基位费只针对当前作业位置计一次，件数任意；`base_fee_fen`、`unit_price_fen`、`quantity_brackets_json` 构成正式版本化价格条件，不把同一基塔的基础费重复乘以安装数量。其他电压等级、塔型、地形等匹配继续由参考价规则承担，金额计算和选择由应用层完成。
- **立项必须有有效需求，结算必须有本次解决的需求和数量**：项目立项 `project_approval_finalize_guard` 原本已强制至少一条已确认需求的批准范围；现在每张非注销的正式结算单版本必须有 `settlement_scope_results`（本期关联需求及新增实际解决数量，允许 0 表示仅补结原有工作费用），同需求的材料/人工费重复收费明细不得重复累计完成量。现行结果只能通过 `v_effective_demand_resolutions` 取各独立结算单当前已批准的有效版本；历史结算修改/注销保留旧事实。
- **需求、费用、结算均允许未完或超过软基线**：批准需求数量、项目预算和真实实际数量不强制相等。`project_closures` 是对项目真实需求解决和资金差异的一次**可审核的正式关闭决定**，`project_close_guard` 不再要求每笔实际费用和所有结算金额都达到100%核对，也不要求需求全部完成；仍不得绕过未结束的正式审批或重复核算同笔费用。关闭快照由应用自动计算并冻结差异，不新增余额累计表。
- **管理员任何操作不要求输入理由**：在候选 SQLite 中所有 `reason` 列缺省 `''`，`change_reason`、`decision_reason`、`addition_reason` 同样可留空。版本序列、实体外键、审批操作者、时间、真实变化和必要证据仍必需；不能以“必须填写原因”阻止管理员正常维护。非管理员解释性输入的提示规则属于服务端/UI 权限策略，数据库不根据伪造登录角色判权。
- **第十四轮历史快照**：70 张 STRICT 表、24 个事实视图、217 个触发器、71 个显式索引、674 个字段，**406/406** 当轮 SQLite 契约通过。设计及边界见 `docs/architecture/Schema113_第十四轮_防鸟装置数量计价_需求完成与结算关联_弹性结项_管理员理由可选_2026-11-08.md`。当前运行仍是 Schema112，仅修改候选 SQL/验收/设计文档，不动真实数据、前后端或附件。

## 2026-11-08 Schema 113 第十三轮业务裁决（覆盖旧轮次冲突内容）

- **该轮“一次性清洗导入”的设想现已被2026-11-09裁决完全废止**：正式业务完全不保留外部编码别名、映射、同步、专用导入表及索引；业务来源只记录用户提供的本系统事实依据。旧版专用数据导入脚本属于已删除的历史工具，禁止再作为任何产品功能依据或恢复。
- **同塔多回独立退运**：`physical_towers.status` 是物理实体独立状态（`active/inactive/retired`）；`transmission_lines.status` 独立支持 `active/inactive/retired`（退役须先处理本线路在运档距/逻辑杆塔），`logical_towers.status` 是每回逻辑杆塔独立状态（`draft/active/inactive/retired`）。某一回退役不得自动影响共塔其他在运回路；在运逻辑杆塔只可关联在运物理杆塔，仍承载任何在运逻辑回路的物理杆塔不得停用或退役。相关档距状态需先合法变更。
- **运维班组标准名称**：`logical_towers.operations_team` 及 `logical_tower_history.operations_team` 是按回路维护的**运维班组**，不可与子项目 `managing_unit_id`（归口单位）混淆。设备状态或班组变更须完整、连续历史和操作者/时间；管理员不需要写理由。
- **多因素参考价格**：`operation_versions` 保留唯一作业定义、单位、位置，不直接保存参考价格；`reference_price_versions` 精确引用操作定义版本，按电压等级、塔型、作业方式及可扩展 `additional_conditions_json` 描述适用性；扩展因素从现有版本化字典 `price_factor` 获取并锁定因子定义版本。数据库守护因素身份和类型，应用层负责价格条件匹配、时间筛选、重叠冲突和选择依据；不同操作版本不得私自共用未匹配的价目。
- **最新候选数量**：69 STRICT 表、23 视图、213 触发器、70 显式索引、664 字段；382/382 SQLite 契约通过。所有更旧轮次的统计属于历史快照。新裁决见 `docs/architecture/Schema113_第十三轮_一次性清洗导入_设备独立退役_参考价格多因素_2026-11-08.md`。运行 Schema112、前后端、用户真实数据均不得因候选调整直接改写。

- **最新物资业务裁决 A：不需要独立领料、退料流水。** Schema 113 只保留统一物资主数据及完整版本、需求预计物资清单、项目批准物资快照，以及费用树材料费和每次结算核对；禁止恢复已删除的物资领退表、查询、证据外键或虚构实物流转。
- **费用树为唯一费用科目口径**：实际费用/各期结算记录固定引用该子项目的末级 `project_cost_nodes`，历史记录锁定 `project_cost_node_versions` 具体版本；不再存储 `cost_versions.category_id/category_snapshot` 或维护平行的费用字典。父级只在应用层汇总，历史科目版本不可覆盖、倒序、空改版或引用未来定义；根身份和父子层级不可直接修改。**任一祖先停用时整棵子树禁止新建费用、结算明细和子项；既有历史必须保留，祖先恢复启用后才允许新记录。**最新专项报告 `docs/architecture/Schema113_第十轮费用树唯一科目与历史版本治理_2026-11-07.md`。


- **费用金额归属必须唯一**：真实费用记录在 `cost_versions`，每张独立结算单只保存本次审核金额 `settlement_item_versions`，正式对应份额及最终审核只记录在 `cost_reconciliation_versions`。禁止恢复 `cost_allocations`、`cost_allocation_versions` 和 `v_cost_allocation_current` 的第二份“已分摊金额”，也不能把草稿分配作为已结算。旧结算单修订/注销后原核对不可计入当前余额，但必须允许以保持上一版本原费用、结算明细及双金额的 `voided` 正式历史撤销；禁止首次伪造撤销、重复撤销、倒签时间或偷改金额。

- **项目主数据必须版本化且不重复**：`projects` 只负责稳定项目编码、所属框架和阶段投影，禁止再添加可变项目名称、项目类别或最近阶段时间；`project_management_versions` 是完整档案历史，包含名称、类别具体字典版本、负责人、组织责任版本、计划期间及估算。初始项目根和完整 V1 档案必须在同一事务中创建，未建档不得正式入库。
- **子项目“责任单位”的最终语义为“归口单位”**：Schema 113 字段使用 `project_management_versions.managing_unit_id`、`managing_unit_version_id`；一个完整项目管理版本最多一个归口管理组织（可暂未指定），变更须新增历史版本。**这不是施工单位、现场执行单位、供应商、协议对方或结算单位**，绝不能从此字段推导实际作业者或结算收款方，也不另建平行归口表。
- **组织身份与定义严格分离**：`organizational_units` 保存稳定编码，`organizational_unit_versions` 连续保存名称、上级和启停正式定义；项目责任必须引用组织根 + 具体历史版本，不得在根上直接改名、改层级或重写旧项目使用的组织名称。
- **全主数据历史守序**：框架/协议/资金、项目批准/项目责任、费用/结算审核、字典/操作/作业对象/参考价等不得倒签、不得早于根身份；对有明确完整事实的版本禁止制造无变化假版本。预算只是软基准，不参与真实费用硬限制。
- **必要审计记录不可回写**：疑似重复需求决定应追加复核，不改删既有决定；接口幂等收据必须是 SHA256 + 真正操作人外键 + JSON，已确认不可更改。电压等级编码和名称禁止无痕改写。
- **每次候选 Schema113 数据库调整完成时都运行** `python3 -B docs/architecture/schema113_database_acceptance.py`、`python3 -B docs/architecture/schema113_export_dictionary.py`、`python3 -B docs/architecture/schema113_structure_audit.py` 和 `npm run check`；69/70 张表等历史规模不可作为当前固定期望，严格以候选 SQL 与最新审计矩阵核对。

## 2026-11-05 用户操作最简化（新批准的全局约束）

**核心要求：尽可能减少用户输入、重复选择和人为理解数据库字段的负担。** 数据库保持严格关系、审计与数据完整性，界面只要求用户提供系统无法可靠推导的真实事实和必须由人作出的业务判断。任何新增字段/弹窗/步骤，都必须说明为什么不能自动推导、继承或按需显示；不得为了映射数据库表而增加无意义操作。

- 业务表单遵循“**选择做什么 → 选择具体设备位置 → 填写做多少**”的最短主路径；在此基础上按业务阶段补足必需的来源、事实、证据和审批，不得为缩短流程伪造缺失事实。
- 选定操作类型后，系统自动获取 **固定计量单位、唯一作业对象、允许定位类型、默认录入模板、操作定义版本**；用户不再重复选单位或作业对象。位置类型仅在确有多个合法候选且无法从入口或所选设备推导时展示。
- “作业位置”在数据层是**关联的真实杆塔/档距/物理杆塔**，不是每次都让用户填写的字典选项。对单一位置类型的操作，直接出现正确的设备选择器；不能出现“已选择杆塔、实际关联档距”的矛盾数据。
- 设备名称、电压等级、所属线路、编号等由唯一设备 ID 的关联关系得到；确需历史追溯时独立保存不可变版本/快照，不将这些历史字段作为额外用户输入。系统预填默认处理部位、完成标准、建议数量时允许逐项核对与修改，不应静默替代现场事实。
- 同一子项目的多张独立结算单应复用已确认的需求范围、物资主数据和费用科目，不得复制专业需求或建立检修计划/施工记录；自动核算批准预算、实际费用、已最终核对份额、每张单据本次金额和待结差额。重复需求只提示并要求人工判定，不自动归并或重复计量。
- 采用“**必填直接展示、可推导自动隐藏、异常按需展开**”三类交互。批量操作、智能默认值和 Excel 模板均必须走同一套服务端约束；前端隐藏字段不等于降低数据库约束或服务端校验。
- 不能自动代用户决定入库确认、立项批准、预算核定、费用确认、结算更正、重复需求合并等需授权的决定；保留明确审批、必要依据、可撤销/更正与历史。尚未裁决的跨子项目例外、付款等规则不得自行推断。
- 新的数据模型和业务接口应存储**最小权威事实集合**，计算/展示字段尽量由关系推导；不保存可与关联主数据相矛盾的重复当前状态。金额存整数分、工作量存四位小数缩放整数，变更有事务、幂等及不可变历史。
- 每个核心流程提供简化操作的自动化及真实浏览器验收，统计必须人工输入、重复输入、步骤数量并说明业务必要性，不得单纯以字段齐全或 SQL 测试通过作为交互验收。

- `server/database/schema/tables.sql`：独立 `operations`+`operation_versions`，普通 `dictionary_items` 不含业务操作字段；`demands` 只允许逻辑杆塔、共用物理杆塔、档距三者之一，`location_kind` 是生成列，不接受直接写入；档距需求严禁重复保存一个起点杆塔 ID。
- 操作类型每项固定一个有效计量单位、一个作业对象和合法定位范围；单位、类型、位置由选择操作定义和真实设备关联自动生成，**不能增加用户必须手填的字段**。物理杆塔共享回路时上下文线路 `context_line_id` 属于价格/电压归属依据，自动选定，不是重复的定位外键。
- 支线第一档允许从其所属主线已确认的 `junction_tower_id` 接至支线杆塔；其他任意跨线路档距在数据库层一律拒绝。不得再引入“所有档距端点必须同属支线”这种过度限制。
- 框架/协议复合外键、预算/项目批准版本归属、检修计划/需求范围归属、费用分摊/核对/结算范围、不可变审核历史均需通过 SQLite FK/CHECK/trigger 与 API/业务规则共同保护；不能为迁就 UI 绕过关系约束。
- 只用隔离新库验证 Schema 112；拒绝旧版本 109—111 隐式升级和自动清库。根 `dist/` 放 Windows 发布包，运行生成的数据库/WAL/日志/备份/附件全部在根 `data/`。详细的验证与仍需实机验收项见 `docs/architecture/数据库V2_Schema112_结构优化验收_2026-11-06.md`。
