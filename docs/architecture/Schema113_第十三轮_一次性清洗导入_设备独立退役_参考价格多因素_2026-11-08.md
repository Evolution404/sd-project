# Schema 113 第十三轮：一次性清洗导入、共塔独立退役与多因素参考价格

> **历史关联条款废止声明（2026-11-09）** 本文中涉及 PMS、一次性专用导入、外部编码、映射或兼容的设想全部废止，仅作为历史审计记录。现行系统独立管理业务，技术编码由服务端生成，执行 docs/decisions/2026-11-09_系统独立_自动编码_最少录入.md。

> 2026-11-08；本文件代表本轮新增裁决的当前设计，覆盖先前第十二轮相冲突的 PMS 持续映射与价格条件限制。**仅候选数据库，Schema 112 运行服务和用户真实数据未修改。**

## 1. 用户裁决和数据库边界

1. **一次性清洗导入**：设备、物资在外部清洗确认后一次性导入本系统，不连接或持续同步 PMS。完全删除 `line_source_aliases`；删除 `material_versions.pms_material_code` 及唯一性映射规则和索引；来源 `source_records.source_system` 不再接受 `pms`。保留来源文件、工作表、行号、原始编号和哈希等**一次性导入的内部追溯证据**，不新增 PMS ID 对照表、同步任务或同步状态。
2. **设备实体和线路回路状态独立**：`physical_towers.status` 继续支持 `active / inactive / retired`；`logical_towers.status` 现支持 `draft / active / inactive / retired`。同塔多回时，一个回路可单独退役，不改变其他回路或共享物理杆塔的在运状态。相应逻辑杆塔若是仍在运档距的端点，须先处理该档距的正式版本，再办理退役。
3. **运维班组统一名称**：`logical_towers.operations_team`、`logical_tower_history.operations_team` 代替原 `maintenance_team`，语义是该回线路的运维班组，**不同于项目管理档案的归口单位 `managing_unit_id`**；字段目前为文本，用户通过有责任人、理由、递增版本号和时点的合法台账维护记录调整，历史不可覆盖。
4. **双向在运一致性**：在运逻辑杆塔必须关联在运物理杆塔；仍有任何在运逻辑杆塔引用的物理杆塔，不能先改为停用或退役。直到所有相关回路完成合规退运，才可调整物理杆塔状态。这不意味着各回路必须同时退运，也不在状态修改时无痕改写兄弟回路。
5. **操作类型与多因素参考价格**：原来已经通过 `operation_id + operation_version` 关联准确操作定义及默认计量单位；保留此复合 FK，不把具体价格写入操作模板。每一条价格版本固定金额、税务口径、生效日期及完整适用条件。

## 2. 设备状态及维护

| 业务对象 | 状态代码 | 说明 |
| --- | --- | --- |
| 物理杆塔 | `active`、`inactive`、`retired` | 实体是否在运、停用、退役；不存在无需的物理草稿值 |
| 逻辑杆塔 | `draft`、`active`、`inactive`、`retired` | 每回线路自己的建档、在运、停用、退役 |
| 输电线路 | `active`、`inactive`、`retired` | 线路本体可独立退役，但须先处理本线路在运档距和逻辑杆塔 |

在候选 SQLite 中状态由受控 UPDATE 维护，历史自动追加；前端操作入口、操作权限与实际退役审批属于**尚待新应用实现的能力**。`retired` 的业务语义是退役，但本轮**没有未经用户明确裁决而引入绝对不可逆的退役终态审批制度**，历史始终不可覆盖。

### 同塔多回示例

物理杆塔 P 对应 A 线逻辑杆塔 LA、B 线逻辑杆塔 LB，均为 `active`：
- LA 单独正式退役为 `retired`，其关联在运档距先完成必要的版本化退运；随后 A 线本体也可正式 `retired`；**B 线、LB 和 P 继续 `active`**。
- P 在 LB 仍为 `active` 时改为 `inactive` 或 `retired` 会被拒绝。
- LB 后续也完成退运后，P 才能正式退役；三者各自有独立历史和操作人。

## 3. 参考价：操作模板与“带条件的报价规则”分层

### 3.1 稳定对象

`operations` / `operation_versions` 只回答**做什么、作用对象、默认单位、允许位置**。它**不存价格**。

`reference_price_catalog` 是一条可独立命名的参考价格规则身份，可以有无限多个规则对应同一个操作类型和单位；`reference_price_versions` 是该规则连续的不可变正式版本。每次引用 `operation_id, operation_version`，其 `unit_id, unit_version` 需与该操作定义的单位一致。版本固定具体 `unit_price_fen`、`price_source`、`price_date`、`effective_on` 和 `basis`。

### 3.2 主要适用条件：强类型字段

| 字段 | 业务意义 | 未限定值 |
| --- | --- | --- |
| `operation_id` + `operation_version` | 哪一种操作类型及定义版本 | **必须指定** |
| `unit_id` + `unit_version` | 价格的计量单位及正式定义版本 | **必须指定** |
| `voltage_level_id` | 线路电压等级，真实 FK | `NULL` = 不限制电压等级 |
| `tower_type` | 清洗后设备台账采用的标准塔型代码 | `NULL` = 不限制塔型 |
| `work_mode` | `outage` / `non_outage` / `both` | `both` = 两种作业方式均可 |
| `specification` | 规格或操作说明 | 空字符串代表不附加该文字条件 |

**价格条件并不要求每个操作都填写所有因素**。例如某类工作对塔型不敏感，`tower_type` 可为空；不能人为建立所有电压等级 × 所有塔型 × 所有地形的笛卡尔规则表。

### 3.3 其他可扩展因素：使用已有版本化字典，而非无限加列

`reference_price_versions.additional_conditions_json` 是一个不可变 JSON **对象**，每个 key 是 `dictionary_items(type_id='price_factor')` 中的稳定因素代码，引用的具体定义版本由该 key 对应对象中的 `factor_version` 显式指定。

价格因素类别 `dictionary_types.id=`price_factor` 在建库时已内置，不要求用户手动创建类别；具体价格因素通过现有字典维护。价格因素共用已有的 `dictionary_item_versions` 正式定义，`fields_json.kind` 的受支持格式为：
- `{"kind":"enum"}`：例如地形类型、运输方式、现场施工难度等级。价格条件只支持 `{"factor_version":1,"op":"eq","value":"mountain"}`。
- `{"kind":"number","unit":"mm"}`：例如塔高、运距、海拔、其他可计量环境属性。价格条件支持 `{"factor_version":1,"op":"range","min":30000,"max":50000}`。`min`、`max` 均为整数并且 `min <= max`；单位含义由因素正式定义版本固定。

样例（同一条正式价格版本的完整扩展条件）：

`{"terrain":{"factor_version":1,"op":"eq","value":"mountain"},"height_mm":{"factor_version":1,"op":"range","min":30000,"max":50000}}`

数据库拒绝未知价格因素、没有正式定义的版本、已停用定义、错误数据类型、非法数值范围、重复键及不存在的因素定义版本；任何因素正式定义版本也不能来自价格版本登记时间之后。规则版本一经建立不能修改、删除，改变适用条件必须增加真实的新规则版本。

无需为“山区”“平原”“吊装高度”等每个因素设计额外业务表，新增因素用现有字典类型添加一个正式定义即可。价格因素定义变更不会重新解释已经发布的旧价格规则。

### 3.4 价格选择和冲突处理（应用层职责）

应用层按照实际需求作业位置推导**准确的线路电压等级、物理塔型及其他上下文**：
1. 按操作身份/正式定义版本、计量单位与业务生效日期过滤规则，禁用规则不参与新增报价；当前启用的规则所使用因素定义必须可以被解释。
2. 核对电压等级、塔型、作业方式和所有已声明的扩展因素；`NULL`/`both` 表示相应维度不限定，**缺少某个必要现场事实时不能假定匹配**。
3. 返回全部匹配规则，按条件精确程度、来源依据及生效时间提示；**对存在重叠或相同优先级的规则，不静默选最低价或最后一条，要求使用者明确选择或调整规则定义**。
4. 在拟承接范围 `project_demand_scopes.reference_price_version_id` 锁定本次采用的价格完整版本，保存实际确定单价、来源和日期；正式批准后由 `project_approval_scope_versions` 保存实际通过的金额快照。参考价只是建议值，预算、正式批准和实际费用均不是它的强制运算结果。
5. 未来真实应用需要实现价格适用性检查、重叠检测、因素配置 UI 和报价解释；**本轮完成的是候选数据库可表达和约束的事实模型，不虚报价格自动匹配引擎已完成**。

**注意**：价格版本可以提前登记未来生效日期，按某一过去日期查询可用参考价时必须使用相应历史规则和 `effective_on` 比较，而非直接把 `v_reference_price_current` 中最新版本等同于任何日期的报价。

## 4. 结构变化与验收

本轮候选库规模：**69 张 STRICT 表、23 个只读事实视图、213 个触发器、70 个显式索引、664 个字段（含虚拟生成列）**。

- 删除一张无业务价值的外部线路别名表（3 字段）；删除物资外部 PMS 映射字段（1 字段）和专属索引；移除来源 `pms` 类型。
- 逻辑杆塔增加 `retired` 允许值，`maintenance_team` → `operations_team`，当前及完整历史同步改名，无新增冗余存储。
- 在物理/逻辑杆塔状态一致性上新增 2 个触发器、线路独立退役 1 个触发器，并扩展原物理塔退役守卫覆盖 `inactive`。
- 参考价增加 2 个真正必要的适用条件字段：`tower_type`、`additional_conditions_json`；新增 1 个扩展价格因素完整性守卫。没有另建扩展价格表或明细分摊账。
- 全量 SQLite 独立契约 **382/382** 通过；新增测试包含共塔单回和整条线路独立退役、物理塔停用约束、活跃逻辑杆塔不能使用退役实物、完整历史、同操作不同电压/塔型/地形报价、多因素版本修改及错误因素类型拒绝。全结构矩阵、FK、所有视图和索引互相校验通过。
- 待新版落地验收：一次性导入真实台账的字段映射与质量门槛；Windows 多用户并发、权限；参考价规则自动匹配和冲突解释；真实附件及备份联合恢复。

**代码范围**：只改 `docs/architecture` 中候选 Schema113 SQL、专项回归测试和权威说明/字典/结构审计，及仓库级开发裁决文本；运行 Schema112 的代码、用户资料和真实 SQLite 均未修改。
