## 一、候选结构的业务对象清单与权威来源

| 领域 | 稳定身份 / 完整定义及业务事实 | 只读当前口径 |
| --- | --- | --- |
| 输电设备 | `transmission_lines` / `physical_towers` / `logical_towers` + 各自完整设备历史；`line_spans` + `line_span_history` | 最新设备状态和真实档距拓扑 |
| 配置和主数据 | `voltage_levels`、`dictionary_items`、`operation_versions`、`work_object_versions`、`reference_price_versions`；**`materials` 无版本表** | 当前定义从历史版本读取，物资编码直接来自唯一 `materials` |
| 来源追溯 | `source_records`、`demand_batches`、`demand_sources` | 原始 PMS/Excel 来源与批次关联；不重复建批次-需求-来源三元表 |
| 专业需求 | `demands` 业务身份、`demand_versions` 完整定义、`demand_material_version_items` 版本化预计物资、`demand_lifecycle_events` 状态 | `v_demand_current`、`v_demand_material_current` |
| 框架及子项目 | `framework_versions`、`agreement_versions`、`projects`、`project_stage_events`、`project_management_versions`、`project_funding_versions` | `v_framework_current`、`v_agreement_current`、`v_project_management_current`、`v_project_funding_current` |
| 项目正式批准 | `project_demand_scopes` 为承接身份和初始候选量；`project_approval_versions`、`project_approval_scope_versions`、`project_scope_materials`、`project_approval_material_items` | 最新审核生效的项目预算、范围、物资；不回退到草稿预计 |
| 结算 | `settlements`、`settlement_items` 为稳定身份；`settlement_versions`、`settlement_item_versions` 为完整正式结算，`settlement_review_events` 审核 | `v_settlement_effective_versions`、`v_effective_settlement_items` |
| 实施和财务 | `completion_records` + 修订、`settlement_material_consumptions` + 修订、`cost_versions`、`cost_allocation_versions`、`cost_reconciliation_versions` | 实际工程量、用料、发生费用、内部费用分摊与核对分别统计 |
| 审计和附件 | `users`、`permission_definitions`、`role_permissions`、`audit_events`、`evidence_files`、`evidence_links` | 内容寻址证据文件和强类型业务版本证据 |

**模型原则**：业务身份只定位对象；版本表记住当时事实；已审核金额和数量来自正式批准版本；实际记录独立于预计；当前汇总通过视图推导，不保存第三套手工累计数字。

## 二、本轮实修的问题

1. **需求增量修订不再迫使复制完整字段**：原 `demand_revision_publish` 用补丁本身读取全部结构化字段，但正式定义却使用 `json_patch` 合并版本，造成“只改描述”的合法修订被拒。现在先合并前版完整定义，再从合并结果生成结构化列和不可变正式快照。若修订不含物资则继承上版整份物资清单；需要变更物资时明确提交新全量清单，历史不会被覆盖。
2. **核对历史不可移花接木**：`cost_reconciliation_versions.record_id` 的新版本以前可直接改挂到另一费用 `cost_entry`。现要求同一核对业务编号的版本始终属于原实际费用身份和原结算明细身份；同一笔实际费用的 `cost_version_id` 合法更正仍可通过，防止错用一个历史核对编号转移财务事实。
3. **导入批次一旦提交即为证据**：`demand_batches` 改成严格 JSON、可校验摘要和草稿编辑版本。正式 `submitted` 后禁止改回草稿、覆盖源数据或删除。旧原始来源单据及 `demand_sources` 的保护继续保留。
4. **项目审批总预算不等于全部项目范围直接相加**：新增 `v_project_approved_amount_comparison`，显示已定价范围合计、未定价范围数、总批准预算和差额。`NULL` 未核定金额不得回退成候选预算；两数不同是需说明的统计结果，**不设拒绝真实超额的硬约束**。
5. **正式业务附件可关联细粒度历史**：`evidence_links` 现在通过真实 FK 支持需求完整版本、该版具体物资、需求状态事件、项目阶段、项目管理与资金版本、项目批准物资、费用分摊版本及档距历史。复合身份与一对一业务目标数量均由 DB `CHECK` + FK 保障，不能填不存在的版本号、只填半个复合身份或同时填两个目标。

## 三、冗余治理规则

| 同名/同值现象 | 处理结论 |
| --- | --- |
| `demands`、`demand_versions` 都涉及需求核心属性 | 初始 `demands` 保留冻结的原始录入事实；当前有效需求必须读 `v_demand_current`，由最新完整版本和生命周期事件推导。禁止把初始根字段当作当前最新定义 |
| 项目承接候选量、正式批准量 | 不是一份业务事实：`proposed_*` 是立项前候选；正式值只能来自最新 approved 项目批准版本 |
| 物资主数据与批准物资历史快照 | `materials` 单表可更新基础描述；历史批准的名称、规格、数量与单位快照是批准当时的证据，不能删 |
| 框架协议额度与真实结算成本 | 不可合并；额度是软规划，实际可超过，视图显示超出额 |
| 需求来源与导入批次 | `demands.batch_id` 是来源批次身份，`demand_sources` 是来源文档/记录关系；不另建可重复的 `batch_demand_sources` |
| 结算、实际费用、费用分摊、财务核对 | 各是不同经济事实，不得因字段同为金额而合并或反复累计；核对更正必须保持原成本/结算身份 |

## 四、测试及数据库边界

当前数据库候选结构：

- **73 张 STRICT 数据表，35 个只读视图，217 个触发器，67 个显式索引**。
- **193 项数据库设计契约测试通过**，新增了需求单字段更新、费用核对身份不可改挂、提交批次不许篡改、最新批准金额未知值、版本物资附件 FK 等回归用例。
- `PRAGMA integrity_check=ok`、`foreign_key_check` 无异常，所有视图可解析；无完全重复等价索引。
- 此为隔离 SQLite 结构和契约验收，不代表生产服务并发吞吐、真实附件哈希与文件系统断电恢复、访问授权渗透测试、全量 PMS 数据导入验收已完成。

## 五、需要持续保持边界明确的业务事项

- 项目剩余需求**跨子项目正式移交**、已关闭子项目的**正式重新授权开启**：尚未批准完整业务流程，不用编造无依据的迁移/重开事件；当前禁止静默绕过。
- 银行付款、发票明细、采购/仓储库存：不等同于当前结算或物资实际消耗事实。是否扩展需要新的业务范围裁决。
- `evidence_links` 当前覆盖核心项目、需求、结算、费用和档距历史；完整设备版本（线路/物理塔/逻辑塔）证据关联若需要独立管理，可以另作设备证据专题，不宜无条件继续膨胀一张通用附件关系表。
- 当前运行数据库仍为 Schema 112；新 Schema 113 **未进入实际生产运行**。后续前后端重写应以当前唯一权威候选规范而非历史文档为模型基础。

**本轮治理结论**：已消除新发现的部分结构冗余与历史关系缺口，保留项目真实业务事实和可靠 FK；仍不将单一 SQLite 设计验收等同于已完成生产级业务验收。
