## 一、通过项

- 候选 SQL 可创建 52 张表、5 个视图、65 个触发器、49 个索引；`PRAGMA integrity_check=ok`，`foreign_key_check=0`。
- 已确定主链路：年度框架 → 子项目 → 批准版本 → 结算单 → 结算明细 → 完成量、物资消耗、实际费用、分摊及核对；**无检修计划和计划预算实体**。
- 项目协议可选；操作绑定标准作业对象；需求物资 0:N；档距长度不设字段；完成和结算状态分开推导；关闭记录及未完成量处置有专门实体。
- 正常正例：无协议项目合法批准、多材料、部分完成/结算及冲销、关闭前缺少剩余量处置被拒；这些成功不代表非法路径已全部受控。

## 三、P1：定版前必须统一的语义与复核

1. **费用核对金额累计口径**：目前逐条比较一个核对额不超过结算明细净额，但多个费用版本对同一结算明细的有效核对可能重复占用。应按结算明细总有效核对额做限额，并在冲销后使受影响核对重新审核。
2. **终结结算条件**：当前要求终结结算单自己包含实际完成记录，若项目早已在此前的进度结算中完成，纯财务尾差的终结结算无法确认。建议核项目累计验收量和未完成处置，不强迫重复录入验收。
3. **版本连续性**：`cost_versions` 等允许直接插入版本 999，建议要求版本连续递增并校验上一版本确认状态；追加不可改，避免并发造成断链。
4. **批准价格未知值**：`approved_amount_fen` 允许 NULL，但结算确认时拒绝 NULL；若项目允许无参考价先开展业务，应有正式补价审批流程。未知金额不应默认为 0。
5. **完成量独立性**：`completion_records` 可以在 draft 结算上确认，`v_scope_progress` 只汇总 confirmed 结算的完成量。需要统一“工程已验收”和“财务结算已确认”的统计边界，避免暂未结算导致已实施量被隐藏。
6. **结算数量 vs 验收数量**：`settlement_items.quantity_scaled` 是本次结算申报量，`completion_records.quantity_scaled` 是实际验收量，必须分开定义并分别约束，不能算作两次实施。
7. **关闭快照与后续核对**：关闭记录应在同一事务中冻结累计完成、净结算、已核对费用、未完成工作量清单；关闭前存在草稿/待审批业务要阻断，关闭后事件变更须显式复核。
8. **批准版本历史**：一份新结算应绑定创建时有效的批准版本，而已确认结算应维持旧版快照；不能自动重定向到最新版。
9. **SQL 可读性**：`reference_price_catalog.operation_id` 存在重复 `ON DELETE RESTRICT`；应清理，但不影响本轮核心失败结论。

## 四、必须保持的既定裁决

- 不恢复检修计划或计划预算表；由结算单及结算明细驱动费用事实。
- 子项目可不关联执行协议，但仍必须从年度框架额度中扣减相应占用；已关联协议须属于同一框架。
- 不增加必填或持久化档距长度字段。
- 标准作业对象、需求多物资、审批快照、部分实施与部分结算两轴状态，继续保留。
- 实际费用、核定结算、费用核对、银行实际付款是四种不同业务事实；没有得到授权不新增银行付款模型。
- 项目关闭剩余量只允许明确取消或延期，不自动转移至另一正式项目。

## 五、复验清单与修正顺序

**第一批（P0）**：B01～B04、B06、B09——堵住超额项目、结算篡改、关闭后写入、批准金额直接改写。
**第二批（P0）**：B05、B08、B10——统一冲销净额、材料数量、费用核对口径。
**第三批（P0/P1）**：B07、版本连续性、终结结算条件、批准金额未知、关闭事务与进度汇总语义。

应纳入数据库反例测试的典型用例：

- 框架 10,000 分内拒绝直接插入预算 20,000 分批准项目。
- 结算 8,000 分→冲销 5,000 分→再结算 6,000 分应当允许（净额 9,000）。
- 确认结算后新增任何结算明细、改挂项目或批准版本必须拒绝。
- 两个正式项目争抢同一需求必须拒绝。
- 物资 1,000 单位批准，不允许实际累计消耗 20,000。
- 未确认结算不能用于最终费用核对。
- 关闭项目后所有新增业务事实应阻断，关闭审计不可改写。
- 金额上限、完成量与冲销必须在并发和异常事务回滚后仍成立。

**验收结论：候选 Schema 113 结构可创建，核心业务模型方向合理，但存在已验证的 P0 设计缺陷，必须修订候选 SQL 并重跑反例测试后才能定版。运行 Schema 112 保持原状。**
