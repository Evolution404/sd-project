# Schema 113 第八轮：取消检修计划及施工流程，收敛为多次结算

> 业务裁决日期：2026-11-07。实施范围：候选 Schema 113 SQL、隔离数据库契约测试和对应设计文档；**未修改运行 Schema 112、后端、前端、真实数据或附件**。

## 1. 已确认的业务规则

1. **没有检修计划实体**。之前“四层结构”里的检修计划已被当前最终裁决取代，需求仍归子项目，不能借删除计划丢失需求来源和批准范围。
2. **没有施工或实施完成这个独立业务阶段**。不计算“施工完成量”“施工结束”“剩余施工量结项处置”，也不存在“先施工结项、以后再财务结清”的双流程。
3. **只有一次次结算**。一张子项目结算单核定本次费用；同一子项目可以建立多张独立的结算单，每张单内可以核定多种费用树末级科目。跨单据通过实际费用和结算的最终核对持续结清，直至全部费用处理完成。
4. **费用不受预算硬上限限制**。预算与预计工作量只用于应用层对比；实际费用更正、核减、不同结算期金额变化保留完整历史，不覆盖原始记录。
5. **最终的子项目关闭是财务结清**。以该项目所有仍有效实际费用、批准的各次结算及最终核对记录为事实依据，而非施工量或物资使用量。

## 2. 本轮实施的数据库精简

| 删除对象 | 数量 | 理由 |
| --- | ---: | --- |
| `completion_records`、`completion_revisions` | 2 张表 | 施工完工及完工修订不是业务对象 |
| `project_closure_dispositions` | 1 张表 | 无施工剩余量，自然不存在剩余施工量处置 |
| `v_completion_current` | 1 个视图 | 不再存在完工事实 |
| 对应施工/处置不可变、序号和跨表保护 | 9 个触发器 | 原始业务对象删除后无使用价值 |
| 完工反向索引、处置索引和完工附件索引 | 4 个索引 | 无被引用的实体 |
| `evidence_links.completion_record_id` | 1 个强类型外键字段 | 不再允许归属已取消的完工对象 |
| `project_close_guard` 中施工量完成和剩余量处置逻辑 | 一组检查 | 财务结清只核对真实费用与各期结算 |

**仍保留** `materials` 与 `material_versions` 的唯一物资主数据、需求物资和项目正式批准物资清单。`material_usage_records` / `material_usage_revisions` 是另一条独立的**物资领退追溯流水**，没有施工状态，也不参与财务结清门槛；是否需要保留独立领退流水，可在后续业务确认后进一步精简，不能将它自动当成一次结算。

## 3. 真实的财务对象关系

- **年度框架** → **子项目**（可选通过执行协议关联资金历史）
- **专业需求与批准范围** → 子项目的需求依据（仍保留真实批准版本和物资版本证据）
- **子项目** → **多层费用树** → 多笔 `cost_entries` / `cost_versions` 真实费用
- **子项目** → **多张 `settlements`** → 每张完整 `settlement_versions` → 每张本次金额的 `settlement_item_versions`
- `cost_reconciliation_versions` 将实际费用份额和本次结算核定金额按历史版本逐笔核对；最新有效且 `is_final=1` 的记录用于财务结清。原单据修订、注销、核减和金额更正仍可追溯。
- `project_closures` 保存全部费用结清的正式审核事实。不得依据需求预计量、工程进度或某笔结算的“最终结算”字样推断结清。

## 4. 专项反例与质量验证

- 候选 SQL 可独立加载，且不含 `executions`、`execution_items`、`completion_records`、`completion_revisions` 和 `project_closure_dispositions`。
- 有批准需求范围但**没有施工完成记录**的子项目，仍可按已最终核对费用正式结清。
- 已批准的结算明细只记录**本次金额**；同一笔费用可跨费用版本、多张独立单据逐步核对，旧结算版本被正式更正时不重复统计。
- 有真实费用尚未最终核对，或有一张已批准结算单未最终核对，不得伪造财务结清；有合法核减、费用向下更正时保留实际历史并标识异常。
- **候选结构最新统计：73 张 STRICT 表、24 个事实视图、210 个触发器、76 个显式索引、697 个字段。SQLite 独立契约测试 289/289 通过。** 运行中的应用仍是 Schema 112。

## 5. 后续待核实事项

- **物资领退业务是否独立需要**：当前保留物资主数据和领退历史，是为了避免擅自删去之前要求的物资管理能力；但此项不作为施工实施。若业务实际上只需要每次结算的物资金额，而不管理真实领退流水，则后续可以继续收敛。
- **费用双分类是否必要**：`cost_entries.cost_node_id` 与 `cost_versions.category_id/category_snapshot` 可能代表费用树及另一套财务分类。需要区分独立会计维度和冗余分类后才可删减，不可无依据消除历史。
- 跨子项目正式变更需求归属、关闭后重新开启和真实 PMS/附件恢复仍需按独立业务规则与正式授权处理。

**结论：已根据最新裁决删除与实际业务不符的施工完成对象。剩余结构以费用事实、分次结算和最终财务核对为核心；Schema 113 仍是候选数据库，未切换运行库。**
