## 1. 本轮已经执行的更改

- **持续按用户明确裁决精简数据库**：取消检修计划、施工完成及独立领退料流水和更正历史。保留需求与批准物资清单、物资主数据完整版本、子项目真实费用与多张分次结算、最终核对、资金和附件历史。
- **从数据库 DDL 移出 13 个应用层业务分析/展示视图**：

  1. `v_scope_progress`：需求实施与结算状态、完成率、超额率
  2. `v_settlement_workflow`：结算单面向页面的状态汇总
  3. `v_material_variance`：项目物资预计／实际偏差、超量率
  4. `v_material_usage_by_master`：同一物资跨项目汇总
  5. `v_project_variance`：子项目预算、实际和差额
  6. `v_agreement_variance`：执行协议预支、发生和差额
  7. `v_framework_variance`：年度框架资金汇总、超限额
  8. `v_cost_reconciliation_freshness`：核对记录是否需要复核的业务提示
  9. `v_settlement_item_variance`：单条结算与完工量差额
  10. `v_post_close_activity`：项目结项后新增的业务事实汇总
  11. `v_project_close_recheck`：关闭后复核提示状态
  12. `v_funding_historical_actuals`：资金版本对应历史金额聚合
  13. `v_project_approved_amount_comparison`：正式批准总预算与范围合计对比

- **此前额外尝试的 4 个按月／季度分析视图也已撤回**：`v_framework_monthly_cost`、`v_framework_quarterly_progress`、`v_project_monthly_cost`、`v_project_quarterly_cost_contribution`。
- **第十四轮正式关闭含需求解决与费用双维度**：`project_close_guard` 仍防止绕过最新批准和未决正式审批，但**不要求需求实际解决量和批准量相等，也不要求费用与结算核对到100%**。各次结算的有效需求解决结果由 `v_effective_demand_resolutions` 派生，费用仍严格保留不重复核对的写账约束。
- **避免数据库结项规则依赖页面工作流状态**：未完结算检查直接关联 `settlements`、最新版 `settlement_versions` 和正式 `v_settlement_review_status`，而非 `v_settlement_workflow`。
- **验收保持业务闭环**：不生成独立施工完工事实；新的业务闭环以子项目批准→记录真实费用→多张结算单→逐笔最终核对→费用结清为准。

## 2. 23 个保留视图的性质

保留的视图不负责界面展示、告警阈值或财务比例计算，仅统一读取**一个业务对象当前生效的历史版本**，或供完整性约束识别有效事实。

| 业务领域 | 当前正式事实／版本读取 |
| --- | --- |
| 需求、物资与定义主数据 | `v_demand_current`、`v_demand_material_current`、`v_dictionary_current`、`v_operation_current`、`v_work_object_current`、`v_reference_price_current`、`v_organizational_unit_current` |
| 资金与项目基线 | `v_framework_current`、`v_agreement_current`、`v_project_current_approval`、`v_project_funding_current`、`v_project_management_current` |
| 项目批准 | `v_approval_scope_current`、`v_approved_material_current` |
| 结算及审核 | `v_settlement_review_status`、`v_settlement_effective_versions`、`v_settlement_approval_timeline`、`v_effective_settlement_items` |
| 真实费用与财务核对 | `v_cost_current`、`v_cost_reconciliation_current`、`v_project_cost_node_current`、`v_effective_cost_reconciliations`（不再有独立分摊视图） |

这些视图是数据库对不变业务版本的只读投影，不保存第二份实际金额或新一套状态。**今后如果前后端新写入层可以直接保证业务查询的一致性，也可继续评估这些视图是否必要；不得为了删视图而取消现有完整性约束。**

## 3. 应用层必须接管、不能遗漏的能力

| 应用层业务能力 | 数据库已保存的原始事实 |
| --- | --- |
| 每月、季度发生额和年度进度 25/50/75/100% | `frameworks.fiscal_year`、`framework_versions.limit_fen`、`cost_versions.occurred_on`、`cost_versions.amount_fen`、`v_cost_current` |
| 滞后项目识别与预警阈值 | `projects`、`project_management_versions` 中的计划期间、正式预算与有效成本事实 |
| 各子项目需求范围的已结算金额与费用项分期余额 | `project_approval_scope_versions`、`settlement_item_versions`、`cost_entries`、`cost_reconciliation_versions`，核对有效版由事实视图提供 |
| 同种物资跨框架/子项目的需求预计和批准数量 | `materials.id`、`demand_material_version_items`、`project_scope_materials.material_id`、`project_approval_material_items`；不再有实际领退料数量 |
| 当前协议的预算使用与历史协议的费用归属 | `project_funding_versions`、`settlement_versions.funding_version_id`、`cost_versions.funding_version_id` |
| 结算与费用版本发生变化后的复核提示 | 完整历史结算版本、费用版本、原核对 `cost_reconciliation_versions` |
| 费用结清后晚录或更正费用的复核事项 | `project_closures.closed_at`、实际费用与核对正式版本的登记时间 |
| 项目预算与批准需求明细合计不一致的报告 | `project_approval_versions.approved_budget_fen`、`project_approval_scope_versions.approved_amount_fen`（NULL 为未核定） |

**特别说明**：这些业务功能尚未在新的应用层实现；仅完成数据库职责分离。数据库结构变更不是对用户业务功能的删除授权。

**第十四轮结算口径**：每张独立结算单正式版本记录本次费用明细和本次真实解决的专业需求及数量；应用层分别计算未完成/超量需求与费用未结/超预算。`is_final` 继续属于费用核对的独立审核事实，**不再是项目关闭前必须全部为真的条件**。不引入独立施工阶段或施工结项。

## 4. 核心设计边界不变

1. **功能完备优先**：完整对象、审批范围、物资清单、实际发生、历史审计和追溯证据保留；不能为了字段精简删除合理业务快照。
2. **稳定物资身份 `materials` 与不含外部映射的正式 `material_versions` 定义分离**；需求物资与批准快照引用确切的主数据版本，但项目批准物资快照仍是独立正式业务事实。
3. **所有预算与工作量预计均是软基准**，不得因实际超额而拒绝合法发生；真实费用核对不得重复计入同一笔成本。
4. **不引入检修计划、独立施工完成或领退料实体**；实际材料成本通过费用树叶子记录，各次结算版本同时带有独立需求解决结果。`closed` 是正式项目结束审核，允许需求或费用有经认可的剩余及超额，并非“所有费用百分之百核对”。
5. **数据库只保留不可缺少的写入约束**：真实引用、业务身份、版本连续性、状态不回退、事实金额不重复核对、正式结项不可绕开；报表、阈值、提示、权限交互属于应用层。

### 4.1 费用树是唯一科目，不再重复录入费用分类

`cost_entries.cost_node_id` 锁定末级费用科目身份，`cost_versions.cost_node_version_id` 冻结确认时的正式科目定义。`settlement_items`、`settlement_item_versions` 对本次结算采用相同的双层身份/历史引用。删除 `cost_versions.category_id/category_snapshot` 和附属索引后，**用户不需要再同时选择一个费用树节点和一套重复的费用类别字典**；应用层只需要按所选费用节点派生科目名称及父级路径，并在详情页面保留独立的真实费用事项标题、金额和凭据。科目更名、禁用、恢复和结算更正均从不可变版本历史还原。

## 第十一轮：合并重复的金额归属历史

基于多次独立结算这一已明确的模型，删除 `cost_allocations` 与 `cost_allocation_versions`；费用与已批准结算的正式关系仅由 `cost_reconciliation_versions` 记录。材料费/人工费不另建分摊账。暂定分配在结算草稿中处理，不能算入正式已结算金额。

仍保留两个不可互相替代的业务金额：`reconciled_cost_fen`（已核对实际费用份额）与 `reconciled_settlement_fen`（结算核定额），支持合法核减。结算单修订后的旧核对可追加原值撤销，不使旧金额重新生效。

**第十一轮历史快照**：当时为 **69 张表、22 个视图、198 个触发器、71 个索引、659 个字段，301/301 SQLite 专项测试通过**；最新结果见第十二轮。


## 第十二轮：项目、组织、资金和主数据全面治理

- **项目身份与档案归一**：`projects` 仅保留不可变项目编码及框架归属和阶段同步投影；项目名称、类别/类别正式版本、责任人、单位、目标日期和初估值一律保存在 `project_management_versions` 的完整历史中。界面展示当前名称、类别和组织名称由现行事实视图取得；历史结算仍可还原原始定义。
- **组织管理也保持可追溯**：`organizational_units` 为稳定编码，`organizational_unit_versions` 保存完整正式更名、上级关系及启停版本，`v_organizational_unit_current` 提供最新版本。子项目归口单位通过 `managing_unit_id` 与 `managing_unit_version_id` 关联组织稳定身份及正式定义版本，避免旧项目随组织名称调整而回写旧历史。
- **资金只保存正式归属，预算为软基准**：年度框架、执行协议、项目资金关联和立项核定分别保存完整、不可倒签的版本，不增加累计占用字段，也不禁止超预算的真实费用和分次结算。
- **每一个定义/金额的版本有序**：项目批准、结算、审核、费用、标准作业对象、操作、字典、参考价采用连续版本和真实登记时间；已有版本不变更，不制造没有实际内容变化的重复历史。
- **运行基础事实可审计**：重复需求的人工处理意见不能被无痕覆盖，接口幂等回执须有真实操作者 FK、参数 SHA256 和不可变结果，电压等级编码/名称不允许无痕改写。
- **第十二轮历史验收快照**：70 张 STRICT 表、23 个视图、209 个触发器、71 个显式索引、666 字段；数据库契约 **362/362** 通过，另新增 `schema113_structure_audit.py` 对真实 DDL、矩阵、触发器、外键、索引、视图执行全结构比对。

详见[第十二轮全量结构与历史一致性审计](Schema113_第十二轮全量结构历史一致性审计_2026-11-07.md)。运行 Schema112 与所有用户数据均未变更；对应的应用层重写、权限与真实数据验收尚待执行。


## 2026-11-08：归口单位而非实际执行单位

`project_management_versions.managing_unit_id` 是**子项目归口管理单位**，`managing_unit_version_id` 精确锁定该单位当时的组织定义版本。原 `responsible_unit_*` 在候选库中统一更名，避免误将其作为施工单位、实际作业单位、结算主体或供应商。一个项目管理版本最多归口一个单位，允许暂未分配，跨项目可共用同一归口单位。若变更归口，追加项目完整管理版本；不增加执行单位表或结算单位表。


本次归口单位术语与三个专项回归用例落地后，**当前数据库隔离契约 365/365 项通过**；正文此前轮次的 362/362 是当时验收快照。归口单位更名不要求增加新业务表、应用权限触发器或费用分摊。

## 第十四轮当前设计（2026-11-08）

**当前候选 70 表、24 个视图、217 触发器、71 个显式索引、674 字段；406/406 隔离 SQLite 契约通过。** 此文较早各轮70表以前的数据及财务100%结清要求都是当时历史快照，以本节和[第十四轮设计文件](Schema113_第十四轮_防鸟装置数量计价_需求完成与结算关联_弹性结项_管理员理由可选_2026-11-08.md)为准。

- `reference_price_versions` 通过 `pricing_mode`、`base_fee_fen` 和 `quantity_brackets_json` 表达同塔一基固定费、件价及数量分档；参考价格的筛选、计算、金额舍入、冲突提示属于应用层。
- `project_approval_finalize_guard` 已确保正式立项关联实际专业需求；`settlement_scope_results` 按结算正式版本唯一记录每项本次解决的需求数量，`v_effective_demand_resolutions` 只投影当前生效事实，不将材料费和人工费数量重复计为需求完成。
- 项目关闭时应用自动计算需求的批准、已解决、未解决和超量，以及确认费用、核对、未结和超预算差异，并将当时审核口径写入 `project_closures.close_snapshot_json`；**数据库不保存另一个不断更新的进度汇总字段**，也不负责余额重算。
- `reason`、`change_reason`、`decision_reason`、`addition_reason` 对管理员不强制填写；数据库统一支持留空，而真实操作人、时间、版本与正确业务关系仍然必需。非管理员权限及相关说明规则应在服务端执行。
- 在一个写事务中完成结算版本、全部费用明细、全部专业需求解决明细和审核事件。不得因为缺少理由伪造业务内容，也不得把未结差异偷偷改写为零。


## 第十五轮：需求关联时即占用，释放靠正式历史，不新增运行态缓存

**当前候选：71 表、25 视图、224 触发器、71 显式索引、681 字段；432/432 数据库业务契约通过。**

- 需求 `v_demand_current.status` 继续由 `demand_lifecycle_events` 表达四个独立业务状态；项目独占归属由 `project_demand_link_events` 推导 `v_project_demand_binding_current`。该事实投影视图不是累计进度报表，也不复制存储当前状态。
- `project_demand_scopes` 创建时自动建立真实首条绑定事件，第二项目在绑定创建时即被阻止；显式解绑事件后才能转交。首创者、当前事件操作者、历史日期和历史不可变由 SQLite 强制校验。
- 如果项目正式批准范围仍有效包含某需求，则需应用先提交真实范围变更后才可解绑；若项目已经正式关闭，仍应由授权用户显式释放，而不是结项自动释放。绑定事件只变更当前归口，不覆盖原项目批准与结算事实。
- `proposal_status` 与实际绑定事件状态重复，已从项目需求关系根表移除。页面根据事实投影展示“当前关联项目／可关联”，权限由服务端判定，不维护第二套占用字段。
- 正式批准继续要求已确认有效的需求，草稿不能添加已解除关系的范围；未来应用层须实现范围变更审批、解绑操作、抢占冲突和跨项目历史追溯。

## 第十六轮最新职责划分（2026-11-08）

**当前候选：77表、27视图、249触发器、74显式索引、734字段；472项隔离 SQLite 契约通过。**

- 正式操作定义保存统一价格特征引用，实际专业需求逐位置保存具名真实现场条件及数量，价格规则版本保存可核查的作用域、模型、完整参数与适用条件。作业对象 `work_objects` 与具体物资 `materials` 永不混为一张主数据表。
- 正式需求版本原子发表 `demand_version_work_locations`，项目批准版本按 `project_approval_work_locations` 明确本次承接的每基塔/档距数量。数据库要求它们的签署总量一致，不替用户编排项目、计算费用或决定预算。
- `reference_price_evaluations` / `reference_price_evaluation_lines` 保存正式已核算事实，数据库仅保证真实需求版本/项目范围引用、同一位置与费用覆盖不重复、正式报价完整、精确价格规则版本、时间身份及历史不可变；不把JS/Python、定额匹配、金额算法放入触发器。
- 项目正式参考价应由**应用层**读取 `project_approval_scope_prices` 选用的已确认需求报价及 `project_reference_price_charges`，确认所有范围都有价格，计算总额并清楚报告部分已计价小计与未计价清单。无需在需求/项目根记录重复的可变 `total_reference_fen`。
- 单独的项目批准预算、材料清单与真实费用/结算金额、需求的分期真实解决量仍是各自不同事实；参考价与预算不相等不要求强制改写。`project_demand_scopes.reference_price_version_id` 原单规则引用已移除，项目需求当前归属的link/release历史和正式批准独占规则保持不变。
