# Schema 113 第七轮：结项与历史核对一致性治理

日期：2026-11-07
范围：**仅数据库候选结构、SQLite 专项测试与设计文档**。运行 Schema 112、前后端、`data/` 和真实附件均不变。

## 1. 真实缺陷及修复

原 `project_close_guard` 将“费用完成最终核对”限定为 `cost_reconciliation_versions.cost_version_id` 等于**当前** `v_cost_current.id`，并直接累计 `v_cost_reconciliation_current`。这不符合结算业务的历史语义：

1. 同一笔实际费用 V1 已正式核对一部分，V2 正式调增后又通过新的独立结算单核对余额；旧判定忽略 V1 核对，**错误拒绝真正结清的项目**。
2. 某已批准结算单的完整新版本替换旧版后，旧核对仅是历史证据；旧判定未连接当前有效结算版本，**可能把已失效金额误当作结项依据**。
3. 如果所有实际费用都已核对，但另有一张有效的、已批准但未核对真实费用的结算单，旧判定仅检查费用一侧，**可能漏掉额外结算负担**。
4. `is_final` 是最终核对的独立审核事实，不能因为核对金额等于发生额就自行标记最终完成。正式核减时双方金额可能不同，但最终核对范围可以覆盖全部实际费用。

修改后的唯一结项校验：读取 `v_effective_cost_reconciliations`，以稳定 `cost_entries.id`（核对视图的 `entry_id`）按历史费用版本汇集**有效且最终审核**的 `reconciled_cost_fen`；逐笔与当前生效费用金额相等，再对每条有效批准结算明细核验最终审核的 `reconciled_settlement_fen` 与本次核定金额相等。它们是**数据库有效事实一致性约束**，不会写入冗余累计金额，也不将预算作为硬上限。

## 2. 增量验收案例

| 场景 | 验证结论 |
| --- | --- |
| 一笔费用 V1 为 30 元，V2 更正为 35 元；另开第二张结算单 | 跨 V1、V2 的有效核对合计 35 元允许结项，不限于“当前费用版本” |
| 第一张结算单由 30 元正式修订成 25 元 | 原 30 元核对只保留历史，不再凑当前结项金额；新版 25 元须重新核对 |
| 第一张 25 元、第二张 5 元、第三张 4.50 元 | 费用份额共 35 元、最终核定金额共 34.50 元；核减 0.50 元有正式依据，不视为费用欠结 |
| 第三张已核对但 `is_final=0` | 不允许把“金额刚好匹配”推断成“已经最终核对”，需补正式核对版本 |
| 各费用份额已最终核对完，另有批准的额外 0.25 元结算单且没有对应费用 | 阻止子项目正式结项，避免只验费用而漏验结算 |
| 额外结算单形成新批准的 `void` 版本 | 当前有效余额自动排除该单，老批准明细和审核证据仍能追溯 |
| 材料实际费用更正从 55 元降低到 40 元，但有效已核对 45 元 | **允许真实费用更正入账**，保留 -5 元待复核异常；拒绝继续追加超额核对，不做自动删账或虚构退款 |

本轮独立 SQLite 契约测试从 **281 项增加至 292 项**，全部通过。表、视图、索引、触发器和数据字典字段数量没有增加：**76 / 25 / 80 / 219 / 725**。`PRAGMA integrity_check` 为 `ok`，`foreign_key_check` 无错误。

## 3. 结清状态的三个独立指标

未来应用层必须从已有事实计算，不能再落表重复保存：

- **实际费用尚未最终核对的份额**：当前有效实际费用合计－有效且 `is_final=1` 的 `reconciled_cost_fen`。这是费用份额覆盖口径。
- **已批准结算单尚未最终核对的金额**：每张有效批准结算单本次金额－其有效且 `is_final=1` 的 `reconciled_settlement_fen`。这是结算核定额覆盖口径。
- **正式核减／增减差异**：最终核对的真实费用份额－最终核定的结算金额；必须保留合法证据，不能把差异直接当成待结金额或银行付款。

费用调整可能产生负余额，表示历史需复核异常而不是可以静默自动平账。用户可以调整预算、真实费用和结算金额；必须经正式版本记录，绝不强迫记录和预算相等。

## 4. 待用户裁决的设计冲突

**P0-A：检修计划是否为独立业务对象？** 先前已批准的`年度框架 → 子项目 → 检修计划 → 专业需求`架构要求多个检修计划分批承接同一子项目需求；但当前 Schema 113 统一设计明确`不引入检修计划实体`。这两种设计不可能在正式业务实现中同时成立。若仍需按停电窗口、多批次计划、计划结算进度和释放未执行量管理，就应保留独立计划及其真实引用；不能只以 `completion_records` 或项目范围替代。

**P0-B：正式子项目关闭与费用最终结清是否同一步？** 当前 Schema 113 候选 `project_close_guard` 实际强制所有有效实际费用和批准结算均最终核对后才能正式关闭；然而同日 `统一结构设计` 原 `4.1` 曾记载“不把结清全部费用强制写成结项门槛”。本轮已把这一冲突标为待裁决。选择允许先实施结项、后财务结清时，需要把“实施完结”与“财务结清”建成不同的真实业务事件/状态，而不是在 SQLite 中自行删除必要约束。

**P1-C：费用树与费用字典之间的关系。** 当前 `cost_versions.category_id/category_snapshot` 与 `cost_entries.cost_node_id` 同时承载费用分类，需确认前者是独立会计分类还是遗留重复维度；在明确之前不擅自删列，也不生成两份相互矛盾的分类统计。

## 5. 继续实施约束

1. 在上述 P0 业务选择前不宣布 Schema 113 冻结、不启动应用层重写，不直接变更 Schema 112 或真实业务数据。
2. 数据库只保留对象、引用、真实事实、必要版本历史和不可绕过的完整性约束；所有金额汇总、余额展示、流程提示、异常解释归未来应用层。
3. 保留专项契约测试覆盖的历史核减、费用下调、结算修改及分次结算；不能为了“消除负余额”阻止真实费用更正或覆盖历史。
