# 系统开发规范

当前执行版本为独立Schema113。历史检修计划、施工执行与领退料示例属于旧版讨论，当前实体范围以Schema113接入报告和权威SQL为准。涉及旧税率口径的讨论已由用户的完全移除裁决废止。

**最新 UI/架构约束：** 以《技术债治理实施计划_G0-G7_2026-10-30.md》为准。Element Plus 为业务 UI 唯一组件库；当前开发阶段不做任何旧版数据库、旧 API 或旧 UI 技术兼容。业务版本、批准依据、审计及历史凭证必须按现行规则留存，不属于技术兼容负担。

生效日期：2026-10-30。依据：用户明确要求“所有数据都应该能增、删、改、查；特殊情况无法实现让我授权审核”。本条为强制交付要求，适用于当前整改和后续全部开发。与旧文档冲突时，按用户最新裁决处理；涉及尚未批准的特殊限制，提交用户审核，不自行扩大旧规则为豁免。

## 1. 完整增删改查是默认能力

覆盖基础台账、需求、项目框架、协议、子项目、检修计划、物资、费用、结算、参考价、系统字典、配置、附件、用户以及历史和审计数据。系统内置内容不是禁止编辑或删除的理由。

每一种用户管理的数据对象，应具备：

| 能力 | 最低交付标准 |
| --- | --- |
| 新增 | 具备界面和服务端校验；系统可生成的信息不要求用户重复填写 |
| 查询 | 可按业务条件检索、查看详情；逻辑删除记录有明确的历史查询入口 |
| 修改 | 可修改业务内容；影响已确认事实时，采用版本/更正流程并说明影响，不静默覆盖 |
| 删除 | 有明确入口和确认反馈；正常列表移除、不再供新增业务选用，已有引用有完整处理方案 |

不得以“只能停用”“只能取消”“系统内置”“有外键”等提示代替删除功能并标记完成。停用和删除是不同操作，状态、列表及交互须明确区分。

## 2. 删除与修改的关联处理

无引用的数据可直接删除，并留下操作依据。有引用的数据应优先设计逻辑删除、引用迁移、版本式更正等可行方式；逻辑删除须同步约束所有正常列表、可选项、详情写入及批量接口，并允许查询删除记录。原始位置、工作量、价格、批准依据及费用不能因删除字典而漂移。

删除前展示关联和影响；在提交事务内重新检查版本与引用，防止预览后出现的新引用被误删。未经明确授权，不自动级联删除需求、项目、费用、结算或历史记录，不把逻辑删除偷换成永久清除。

系统预置数据删除后，启动、升级、初始化补齐及导入不得擅自恢复该项。用户明确再次新增同名内容，是新的录入行为，应使用新的稳定标识。

权限须由服务端校验。“支持增删改查”不代表所有账号无差别拥有权限，但相应能力必须能通过被授权的用户完成。

## 3. 特殊情况须经用户授权审核

遇到确实无法提供某项能力的情况，必须形成具体审核材料：

1. 对象、字段/状态、缺少的操作及当前入口。
2. 技术或业务原因，实际数据关系及可复现的限制。
3. 可实施的替代方案、操作步骤、对金额/历史/引用的影响。
4. 验收标准、待用户批准的范围，以及未批准时保留的整改项。

应先完成与该裁决无关且已授权的工作，再把可审查的方案提交用户。用户没有回复不等于授权。旧代码、数据库触发器、文档或开发者判断本身均不构成豁免授权。

现状与授权记录见《增删改查_待授权审核清单.md》。用户于 2026-10-30 已明确授权其中 R01–R05 采用“保留原始事实，补齐更正/撤销或逻辑删除及历史查询”的处理方向，无需重复申请同一方向。功能仍须实施并通过验收，不属于免做增删改查的豁免。普通功能缺失属于待实现，不应包装成无法实现的特殊情况。

## 4. 当前字典实现口径

内置词条和自定义词条统一支持增删改查。无引用时直接删除；有业务、配置、草稿或历史引用时逻辑删除，保留关联记录，正常列表与新增选项不再提供该词条。“已删除”筛选用于查询删除记录；不能从普通编辑/启用接口恢复已删除记录。

删除操作留存审计，并记录删除方式及引用依据；内置补齐读取删除决定，重启不会复活。此实现不需要重建当前 SQLite 数据库。

## 5. 交付门禁

每个数据模块在验收前列出新增、查询、修改、删除的界面与 API。验证正常操作、角色权限、有关联时的处理、并发冲突、删除历史查询以及重启一致性。仅菜单占位或仅后端接口不算完成。

如仍有功能缺失、被数据库规则拦截或待用户审核的例外，必须在进展和交接中明确列出，不能宣称该模块已完整满足本规范。

## 6. 2026-11-03 UI门禁与操作定义补充

业务UI只能使用完整加载官方样式的Element Plus组件。禁止用ElInput的原生date、number、file等type绕过组件约束；全部ElForm禁用浏览器原生表单校验。新增组件时同步注册官方CSS，上传内部file输入必须不可见。`npm test`、`check:ui`及`check:ui:strict`均检查这些要求；不得提高旧数量基线或让浏览器测试适配原生select来绕过。

操作类型必须定义自己的固定计量单位和唯一作业对象。新录入先选择操作，单位和对象自动带出；Excel中留空可按定义补齐，显式冲突必须修正后提交。数量不自动换算。定义修改采用配置版本，不覆盖任何已有业务采用的单位、对象、数量和快照；旧配置不完整时保留原数据并提示维护，不自动补造。


## 2026-11-03 操作类型的作业位置与录入模板约束

- 操作类型必须关联固定单位、唯一作业对象、允许的作业位置及范围内默认位置；共用物理杆塔只允许杆塔定位。只允许一种位置时自动带出，允许两种时需求只在定义范围内选择。
- 默认部位、建议每项数量、完成标准、提示和专用附加字段作为可维护模板；具体线路/杆塔/档距、实际数量、问题事实、来源及日期不由操作定义固定或补造。
- 维护使用Element Plus四页签弹窗：基本定义、录入模板、附加字段、影响与预览；错误可定位到所在页签，保存/取消在窄屏可达。
- 在线录入、行编辑、Excel预检和提交共用约束。切换到不支持当前定位的操作须确认后重新选位置，取消保留原内容；更改已保存需求的操作时服务端必须校验其原位置适用性，不自动搬迁历史需求。
- 配置版本保存operation_profile，启停、排序、逻辑删除不能丢失配置；旧配置未定义位置时由管理员明确维护，不在启动时推断或改写用户数据。详见《操作类型维护界面与字段联动_2026-11-03.md》。

## 2026-11-08 Schema113 接入补充

本次整体重写使用独立 schema113.sqlite，结构只来自 server/database/schema/schema113.sql。用户补充要求系统完全不处理税率。未批准草稿的删除采用有真实审计的撤回，正式核价、范围和证据历史保留。设备台账删除与设备真实运行状态分别记录。金额执行口径、源码目录、验收及Windows平台边界见 docs/implementation/Schema113_重写交付与验收_2026-11-08.md。

## 最终治理门禁

业务层与HTTP通过Repository及应用用例访问数据。单条实体删除检查使用isDeleted按身份查询，列表可一次取得删除集合，不能在循环内反复全量扫描审计。来源当前投影按需求真实关联查询，已有正式采用的物资版本随需求历史保留。

SQLite预编译语句采用256条LRU上限。测试覆盖淘汰、事务内可见性和回滚后复检。npm test同时执行严格UI门禁，TypeScript检查未使用声明。无税务模型检查纳入check和Windows打包。

构建输出固定dist/web，发布包采用校验后的临时ZIP替换，入口与结束均检查Git清洁和提交号。test:package读取实际ZIP并重建前端验证包保留，随后验证生产依赖、源码一致、登录、持久化、附件与备份恢复。Windows实机状态单独记录。

生产安装使用omit=dev和omit=optional，防止Vue的可选同级依赖TypeScript进入离线包。ExcelJS的uuid覆盖固定为已验证的11.1.1，依赖更新必须保留CommonJS及工作簿往返回归，并使用提供安全公告接口的官方源审计。

## 2026-11-09 独立业务与输入字段评估

系统独立管理全部业务，任何专用外部编码、一次性专用导入、映射、别名及兼容设计均已废止。现行依据为 docs/decisions/2026-11-09_系统独立_自动编码_最少录入.md。历史文档仅供审计。

新增每个用户输入字段前，先记录其真实业务含义，再核查能否服务端生成、从已选对象关联或从正式关系推导。可生成的技术身份、单位、作业对象及定义版本自动处理。仅将无法推导的真实事实和授权判断交给用户。不能从数据库必填列直接推导界面必填项。

全部内部编码由服务端创建，客户端提交的技术编码不能决定新对象身份。已有稳定身份保持不可修改。普通杆塔一次保存建立物理实体、逻辑回路及关联，共塔必须明确选择，同号歧义不能自动合并。整基更换保留旧实物、回路历史和真实操作者的更换审计。维护 Excel 允许隐藏保护身份和版本，新建 Excel 不要求手工身份。永久门禁 check:independent-input、专项 API、Excel 和浏览器测试随 check 与发布执行。
