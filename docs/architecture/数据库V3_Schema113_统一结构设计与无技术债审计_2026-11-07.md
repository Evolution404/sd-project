## 数据库与应用层分工（最新设计裁决）

**第一优先级：业务对象和原始业务事实完整。第二优先级：消除真正冗余的字段与存储。** 不允许为了减少表、字段而删除必要业务事实、责任关系、身份、历史快照或审计依据。

- **数据库负责**：统一且完整的业务对象身份及字段、主从关系、真实外键、唯一性/非空/取值范围、必要的跨对象数据完整性、不可变的已确认历史、事务原子性、持久化与查询所需索引。历史批准、需求、结算的“版本”是数据库保存的业务事实；统一物资主数据采用稳定身份 `materials` 与不可变 `material_versions` 完整历史定义。
- **应用层负责**：需求与项目状态机的业务操作组织及权限授权、审批流程、计划进度及滞后判定、季度 25% 目标对比、月度/季度统计、预警、看板、报表、金额计算与差异说明、UI 字段展示、导入清洗任务及人员操作流程。应用从数据库读取原始与正式记录计算，不把报表当成数据库存储对象。
- **允许有限的数据库投影视图**：仅为避免历史有效版本取错、确保同一事实有确定的读取语义；不在数据库实现经营分析、项目进度预警、用户操作流程及决策逻辑。此前发现的指标/差异/报表类视图已移到未来应用层；数据库只保留当前事实与正式版本的必要只读投影。
- **必要的数据约束不算应用功能**：例如真实外键、同笔费用不可重复计账、已确认记录不可改写；其职责是保护存储一致性，而不是替代应用层的业务审批服务。
- **本轮已撤回**尚未确定数据层边界前新增的月度、季度及子项目季度分析视图与相关测试，之后仅在应用层规划这些能力，不在数据库扩充统计视图。

## 1. 已生效的设计裁决

- **最终裁决：没有检修计划、施工完成和独立物资领退概念。** 候选数据库不包含 `executions`、`execution_items`、`completion_records`、`material_usage_records` 及各自更正流水；子项目只保留正式需求及物资批准、费用事实、一次次部分结算和财务结清。物资主数据与批准物资清单不是领退记录。
- **执行协议可选**：每个项目只属于一个年度框架，执行协议可不关联；关联和变更由 `project_funding_versions` 记录，允许 `agreement_id IS NULL`。
- **金额和预计物资可以超预算调整**：预算、需求预计物资与批准数量都是软基准；真实费用、已批准的结算金额可以超出预计，由正式版本记录及应用层提示，不设真实费用与预算相等的硬限制。
- **统一物资主数据允许版本化（最新裁决）**：一物一码，`materials` 只存稳定身份、编码及计量单位；`material_versions` 连续追加完整名称、型号、规格、类别和状态的正式版本。需求版本物资、项目批准物资清单均引用确切物资主数据版本；批准快照仍独立保留。
- **财务事实独立**：真实费用、各次结算金额、费用核对和实际付款不是同一业务对象；一次次结算、金额核减、更正均保留独立正式历史。不存在施工及领退料双轨流程，银行付款暂不建模。
- **专业需求原则上只能由一个正式子项目承接**，但同一子项目可分多笔结算；未经明确授权不跨子项目二次正式承接。
- **档距仅存输电中心管辖长度**：`line_spans.transmission_center_length_mm` 为可空整数毫米，0 与未知 NULL 严格区分，`line_span_history` 冻结其历史；不存档距总长度的冗余字段。
- **前后端未来整体重写**，数据库模型不迁就既有程序的接口、菜单或部署兼容性。

## 1.1 数据库与应用层职责边界（2026-11-07 最新裁决）

**第一目标是业务功能完备；数据库完整、可信地存储必要对象与业务事实。在不破坏功能、审计和历史追溯的前提下，才精简真正冗余的字段。**

| 数据库层负责 | 应用层负责 |
| --- | --- |
| 业务身份、编码、主外键、关联一致性 | 需求录入流程、页面表单、数据交互和业务服务编排 |
| 原始来源、设备台账、主数据、正式批准版本、结算与实际发生的明细 | 工作流操作、业务授权判定与交互反馈；数据库保留必需的越权与非法状态兜底约束 |
| 原子事务、不可变正式历史、幂等键、数据类型、有效引用 | 按月、按季度汇总，25% 目标分析，滞后判定和预警推送 |
| 当前业务事实的可靠查询接口（确有必要的最低限度投影视图） | 各种进度百分比、预算／物资偏差、项目排行、统计图表及动态报表 |
| 记录计划期间、实际发生日期、预算批准额、实际金额等基础数据 | 根据业务可调整的目标、统计周期、筛选条件和判断阈值计算分析 |

**禁止把应用层功能固化进候选建库 SQL。** 例如 `v_framework_monthly_cost`、`v_framework_quarterly_progress`、`v_project_monthly_cost`、`v_project_quarterly_cost_contribution` 这类统计视图不应创建。数据库应保存 `cost_versions.occurred_on`、`cost_versions.amount_fen`、`frameworks.fiscal_year` 和版本化的框架额度等所需原始事实，应用层计算月度、季度及项目贡献。

**当前职责分离**：数据库仅保留 23 个必要的现行事实和不可变版本投影视图（含 `v_material_current`）；已移出数据库的统计视图、独立施工完工及物资领退流水不再恢复。财务结清仅核对费用与各次结算的最终核对。

**判断冗余的标准是事实重复且产生维护冲突，而不是多个字段看上去相似。** 批准时的物资名称／数量快照、结算正式版本、实际费用和审计记录都属于不同时间和不同业务目的的必要事实，不能为了减少字段删除。物资主数据版本和项目批准快照分别保留，它们不是重复字段。

### 3.1 统一物资主数据及不可变正式版本（2026-11-07 最新裁决）

**物资主数据可以版本化，且本轮已实施到候选 SQL。** 统一物资对象只存在一个稳定身份：

- `materials`：`id`、大小写不敏感的唯一内部物资编码 `code`、`unit_id`、创建人和创建时间。根表不可 UPDATE/DELETE，不重复保存当前名称、型号、状态或外部 PMS 编码。单位决定历史数量语义，不能在原物资身份上静默改单位；真实单位不同应另立物资身份。
- `material_versions`：`id`、`material_id`、连续 `version_no`，可修订的外部 `pms_material_code`、名称、型号、规格、分类、启停、说明、修订原因、责任人、登记时间。当前 PMS 外部编码在不同物资之间不得重复（忽略大小写），历史记录不因外部编码纠错而改写。全文版本只能追加，不能覆盖或删除；分类必须是物资分类字典、版本号连续、登记时间不倒序、内容相同不得伪造新版本。
- `v_material_current`：把物资根身份与其**最新正式主数据版本**做只读投影。未形成 V1 的草稿根身份不得作为新增需求或项目物资使用。首次登记时应在同一个写事务创建根身份与 V1。
- `demand_material_version_items.material_version_id` 和 `project_approval_material_items.material_version_id` 强制引用确切的不可变主数据版本，不能无依据改挂其他物资。未修改的需求历史物资清单继续继承上一版本的物资主数据版本；明确修订物资时锁定当时正式最新版。
- `project_approval_material_items` 除了引用 `material_version_id`，继续冻结本次项目正式批准的物资名称、型号、规格、计量单位和批准数量。这是**项目批准审计证据**，不能因为有主数据历史就删除。
- `evidence_links.material_version_id` 可以通过强类型外键关联某个物资主数据的确切历史版本；证据关联仍只能有一个业务归属。

根据最新业务裁决，**不记录独立领料、退料或耗用流水**，不建立 `material_usage_records`、`material_usage_revisions` 或其统计视图；子项目实际材料费用进入费用树对应的末级费用项，随独立真实费用和各次结算进行正式核对。新需求不允许引用已停用的物资，已经批准的历史物资身份及数量快照继续保留，且不会被主数据变更改写。

**功能边界**：物资主数据与批准物资清单并不等于仓储采购系统。库存余额、采购订单、供应商往来和实际银行付款未在本模型中假定已经具备。

### 3.2 最新数据库技术债治理（2026-11-07）

**上一轮审计已证实的 P0、P1、P2 设计缺陷已逐项整改，并补上可重复的 SQLite 反例验收。** 具体清单另见 [Schema113_数据库技术债整改验收_2026-11-07.md](Schema113_数据库技术债整改验收_2026-11-07.md)。

- **全部 70 张表使用 `STRICT`**：主键非空，金额和数量不允许写入任意文本或小数，历史身份使用真实外键。
- **85 个日期字段增加 CHECK**：时间点统一为 UTC 毫秒级 `YYYY-MM-DDTHH:MM:SS.SSSZ`，业务日期为 `YYYY-MM-DD`；拒绝非法格式和真实不存在的日历日期。
- **需求真实历史**：`demand_versions(demand_id, version)` 是不可变的正式需求版本，创建需求自动形成 V1，后续 `demand_revisions` 追加版本；项目需求与项目批准范围都通过复合外键引用有效版本。原始需求根记录和已批准的原始需求物资不得无痕覆盖。
- **项目批准草稿**：预算、需求范围、物资清单在草稿阶段可编辑，正式批准时重新校验真实需求版本、业务范围和物资主数据，批准后不可修改；未审核草稿不能遮盖已生效批准。
- **物资管理**：唯一编码 ASCII 大小写不区分，同一个项目需求范围同一种物资只有一个稳定身份；计划外实际消耗必须填写原因；已停用物资不可在新需求中选用，但不抹除过去的真实消耗；**物资稳定根身份与正式完整版本分别保存**。
- **费用核对累计**：同一已确认真实费用、同一历史结算明细的全部有效核对合计不可超过其真实金额；对同一个核对记录更新版本不会双计。它不是预算硬限制，实际费用仍允许超出项目预算。
- **资金归属历史**：结算与成本版本保存 `funding_version_id`，历史资金事实由 `project_funding_versions` 和 `cost_versions`、`settlement_versions` 查询。跨协议历史金额聚合由应用层执行，不能改写原始归属。
- **状态机**：已关闭项目不能直接恢复为批准态或私自新建结算。数据库保留关闭后的真实补报事实及记录时间；应用层据此计算复核提示，不在数据库中实现复核报表。
- **统计职责分离**：原项目、框架、协议及物资偏差视图、历史资金汇总及核对复核视图已移出数据库，应用层基于权威历史数据计算，不在 SQLite 保存统计镜像。

### 3.3 SQLite 运行约定

全新数据库创建流程要求 SQLite 3.37.0+，每个连接开启 `PRAGMA foreign_keys=ON`、配置 `busy_timeout`、采用 WAL；多项批准和结算写入必须在一个事务中原子完成，建议以 `BEGIN IMMEDIATE` 申请写锁。项目资金预算仍是软基准，不因超预算拒绝真实记录。**只有项目预计金额/数量对比报表，没有存储冗余汇总金额。**

### 3.4 第二轮结构治理：对象完整性和来源追溯（2026-11-07）

本节继续修复“数据冗余、对象元素缺失、双重数据来源”问题；[详细审计及测试说明](Schema113_结构冗余与对象完整性治理_2026-11-07.md)。

1. **完整需求对象**：`demands` 负责唯一业务身份和首次登记；`demand_versions` 保存完整正式定义（作业位置、对象、操作、数量、单位、问题描述等），`demand_lifecycle_events` 保存独立状态事件，`v_demand_current` 从最新正式版本与状态事件派生当前有效需求。`demand_material_version_items` 保存每一正式需求版本的完整预计物资清单；统一 `materials` 与 `material_versions` 分别保存身份及定义历史。
2. **需求修订的实际时间顺序**：每次需求修订的记录时间不能早于前一正式版本，生命周期事件的记录时间不能逆序；已取消需求不得悄悄追加新定义。停用物资不能首次加入新需求版本，但已经在旧需求中出现的物资可保留或延续，以免抹去真实历史。
3. **项目范围单一权威**：`project_demand_scopes` 的 `proposed_*` 仅为拟承接基线。正式值只取最新已批准的 `project_approval_scope_versions`；项目关闭时数据库直接核对实际费用和各期已批准结算的正式最终核对；应用层计算财务余额，未知金额保持 NULL。
4. **设备与项目生命周期**：线路、物理杆塔、逻辑杆塔采用数据库自动形成且不可覆盖的完整台账历史；项目入库、立项、结项的状态由 `project_stage_events` 及权限校验推进。`project_management_versions` 承载项目名称、类别正式版本、负责人、**子项目归口单位**及其历史定义（并非实际执行单位）、计划期间、初估值；`projects` 只保存稳定编码与年度框架、阶段事件投影，不重复保存当前名称、类别或最近状态时间。
5. **原始来源和当前归属不是同一事实**：`demands.batch_id` 说明需求来源于哪一次导入；`demand_sources` 管理需求与各来源记录的多对多引用；`batch_demand_sources` 是当时**真实导入过程的不可变三元来源断言**，不是第二份当前归属。该断言必须关联需求真实所属批次；已关联的 `source_records` 不得原地篡改/删除。`demand_batches` 已提交正文亦不可改写。
6. **PMS/Excel 溯源**：`source_records` 包括来源系统、外部记录号、来源文件、工作表、行号、原始摘要；已有索引按实际来源身份去重，不再追加同义索引。增加批次和需求来源不可变约束，防止“查重时同一数据有多个来源真相”。
7. **严格区分软预算与账实唯一性**：项目预算、物资预计与工程预计都不是实际发生的硬上限。批准总预算与范围金额的差异、未定价范围数由应用层计算；未知金额不能被零或旧提案替代。

**去冗余原则**：批准快照、原始导入证据和真实业务更正具有不同的历史含义，不应仅因字段相似而删除。仅删除重复保存的动态事实、无业务意义的汇总镜像和完全等价索引。

### 3.5 本轮结构治理续审：消除多重权威、补齐证据对象（2026-11-07）

本次以**对象是否完整、事实是否有唯一权威源、审批与历史版本是否真实关联**为核查目标，执行候选数据库结构整改。详细记录见 [Schema113_数据对象与冗余续审_2026-11-07.md](Schema113_数据对象与冗余续审_2026-11-07.md)。

- **需求修订补丁与权威完整快照**：`demand_revisions.snapshot_json` 是本次具体修改的字段补丁；通过 `json_patch` 合并上一有效定义，再从**合并后的完整快照**提取数量、操作、对象和单位，写入 `demand_versions`；未改物资自动继承上一版本的 `demand_material_version_items`，修改物资时则以明确的完整物资清单发布。所有数据可追溯，不能出现“文字修改却必须重复提交全部字段”的冗余输入。
- **费用核对稳定业务身份**：`cost_reconciliation_versions.record_id` 对应的核对事实，其后续版本只可对应**同一实际费用记录**和**同一结算明细身份**。核对金额可以引用同一费用的新版 `cost_versions`，不能把核对编号偷偷转给另一个费用业务对象。
- **导入批次最终状态**：`demand_batches.draft_json` 必须是 JSON，`payload_sha256` 必须满足 64 位小写十六进制摘要格式；未提交草稿可按版本递增编辑，`submitted` 后整个批次和来源身份冻结，不能再改回草稿或删掉导入证据。
- **来源事实分层**：`demands.batch_id` 记录首次导入批次，`demand_sources` 管理认可的来源关联，`source_records` 保留原始 PMS/Excel 证据；`batch_demand_sources` 作为不可变的真实导入断言保留，不等同于当前来源归属。
- **项目批准金额审查交给应用层**：数据库分别保留正式项目批准总预算、范围明细和 NULL 未知金额；应用层计算二者差异，不强制相等、不误用旧值。
- **历史附件的真实业务归属更完整**：`evidence_links` 新增需求完整版本和版本物资清单的复合外键，以及需求状态、项目阶段、项目责任、资金版本、批准物资、真实费用、正式核对、档距历史等强类型证据目标。一个关联仍须**恰好对应一个**业务对象，不能跨多个实体或形成孤儿引用。
- **物资主数据已增加正式版本**：`material_versions` 记录完整物资定义历史；需求版本物资与项目批准物资快照通过真实外键记录当时引用的物资版本。
- **没有引入检修计划层，也没有设预算或物资超额硬上限**。统计差额与数据库关系完整性是两个不同问题。

## 4. 项目批准必须整体生效

1. 新建 `project_approval_versions(status='draft')`，业务批准版本号连续，后续版本须来自同项目正式批准的项目变更单。
2. 填写该版本完整的 `project_approval_scope_versions` 与 `project_approval_material_items`；零物资合法，但正式项目批准范围不能为空。
3. 在一次写事务末尾执行草稿→正式批准，并记录批准人及时间。只有 approved 版本参与预算和范围统计。
4. 正式批准后不允许新增/修改该版本的范围与物资；后续修改重新提交整版项目批准快照。
5. 未批准的新版本绝不遮盖仍有效的上一批准版本。最新批准范围若明确移除了某需求，则当前范围视图也不得回退显示旧需求。

`project_scope_materials` 为每个子项目需求范围与统一物资主数据建立稳定关联；项目批准物资明细以 `project_approval_material_items` 的历史版本存储批准数量、规格和原始名称。最新批准范围更新后，旧批准物资不再计入当前批准视图，但历史完整保留。**没有独立领料、退料累计量或所谓实际用量**；实际材料费用作为 `cost_entries` 的材料费用叶子项记录。

### 4.1 子项目多次部分结算（2026-11-07 已确认业务规则）

**一个子项目可有多张结算单；每张结算单只记录本次结算的一部分实际费用；持续结算，直至全部应结算费用处理完毕。**

- `settlements.project_id`：每张独立结算单都归属明确的子项目；同一子项目可有任意多张结算单。
- `settlement_versions`：每张结算单的正式修订采用完整版本；历史版本不会因为复核、调整或作废而被直接覆盖。
- `settlement_item_versions.amount_fen`：记录当前这张结算单**本次结算的金额**。**没有累计金额标志、预付款/进度/最终结算强制类型，也没有另存“累计已结算”“未结算余额”等字段**。
- `cost_entries` / `v_cost_current`：真实费用先发生，可以独立于结算登记。`cost_reconciliation_versions` 将相应实际费用金额与某次已审核结算明细关联；对同一笔真实费用的有效核对不能超过该费用自身金额，对某个结算明细的有效核对不能超过本次结算金额。
- 应用层按有效真实费用和有效已审核核对记录计算**已结算、未结算**，并按子项目汇总展示；结算单变更时只取同一结算单最新正式生效版本，避免重复计算历史版本。
- **已裁决**：没有施工完工这个结项条件，子项目只有一次次结算直到费用全部处理完毕。`project_close_guard` 仅以有效费用与每期结算的最终核对作为财务结清门槛。

**示例：** 子项目实际费用 10 万元，第一次结算 3 万元、第二次 4 万元、第三次 3 万元，则有效已结算 10 万元、剩余 0 元。它们是三张独立结算单，不需要构造“最终结算金额 10 万元”重复入账。



### 4.2 子项目树状费用与按费用项结算（2026-11-07 新增）

一个子项目维护一棵可多级扩展的费用分类树，根节点、人工费、材料费及更细的人工工序或材料分项，均使用稳定的 `project_cost_nodes.id`；`parent_id` 只表达本项目内的层级关系。父级只用于分类及应用层求和，正式实际费用和结算明细只关联末级节点。节点身份与父子归属不可直接覆盖，名称与启停通过不可变的 `project_cost_node_versions` 连续修订；在确认实际费用或创建结算明细时，所采用费用定义的准确版本冻结在正式记录的 `cost_node_version_id`，后续改名不会改写历史凭证。

- `cost_entries.cost_node_id` 绑定子项目费用树的具体叶子节点；当前实际应结金额从 `v_cost_current` 中**各稳定费用记录最新、有效的版本**读取，不把费用历史版本或父级类别重复累加。

- **唯一费用科目口径**：`cost_entries.cost_node_id` 与 `cost_versions.cost_node_version_id` 是费用科目的**稳定身份 + 确切历史定义**。已删除 `cost_versions.category_id`、`cost_versions.category_snapshot` 及重复类别索引，**不再维护第二套费用字典**，避免材料费节点与另一个类别字段相互矛盾。`cost_versions.title` 是某笔实际费用的**业务明细标题**（如具体材料结算事项），不是重复费用分类；实际金额、发票、税率、发生日期、证据和更正理由仍是独立事实。
- **层级与时点保护**：费用树的父节点必须与子项同属于该子项目、从父级到根的**整条路径均已有启用定义**且未作为末级真实费用或结算明细被使用；父子关系不可更改以免历史重新归类。节点定义的版本号连续、登记时间不得倒退、名称与状态均不变时不能伪造新版本。每次实际费用或结算明细锁定的节点版本，不能晚于该次真实费用确认/结算版本登记；后续改名或停用不覆盖旧账。任意祖先停用都禁止在其子树新建实际费用身份、结算明细或新子项，既有历史保留，可按正式版本继续追溯。

- `settlement_items.cost_node_id` 绑定该结算单所选的费用叶子节点；一张结算单允许选择多种费用，一项费用也可在多张结算单分期结清。`project_scope_id` 对可对应批准作业范围的费用可填写，对共同人工、间接费等可为空；没有范围的结算行不虚构作业数量。
- `settlement_item_versions.amount_fen` 是当前结算单该费用项**本次**金额，不是已结算累计额。费用类别与实际费用必须属于同一子项目、同一末级费用节点；其他子项目的费用项、上级汇总节点及跨类别金额不能错误关联。
- `v_effective_cost_reconciliations` 只投影对应仍生效的最新正式结算明细、且实际费用仍有效的核对记录。历史结算版本及原核对不被删除；正式结算版本更正或作废后，旧核对不得继续抵扣当前余额；同一稳定费用记录跨费用版本也不能重复超额结算。

- **唯一正式金额归属**：删除 `cost_allocations`、`cost_allocation_versions`、`v_cost_allocation_current`。这些平行对象原先与 `cost_reconciliation_versions` 同时记录费用到结算单的金额关系，且前者不需要批准即可存在，容易形成“两本账”。当前只用正式核对记录的 `reconciled_cost_fen` 和 `reconciled_settlement_fen` 表达真实费用份额与本次结算核定金额，支持正式核减；报表和财务关闭不累计草稿里的暂定分摊。
- **历史撤销与重新核对**：当前有效金额必须与最新批准结算明细相符。单据正式修订或作废后，旧核对虽然不再贡献当前余额，仍允许向原核对追加 `status='voided'` 的不可变撤销版本，其费用版本、结算明细版本和双金额必须与前一版本一致，且不得标记为最终核对；不得重复撤销已撤销的核对或倒签核对历史。不存在独立的撤销金额或新的财务分摊表。

- **应结、已结及剩余余额在应用层计算**，先按各费用叶子求和，再逐级汇总父级和整个子项目，数据库不保存可派生的父级金额、累计结算额或剩余金额。预算仅用于对比，不作为实际费用或分期结算的硬上限。
- **核对金额须两套口径**：`reconciled_cost_fen` 表示已核对的真实发生费用份额，`reconciled_settlement_fen` 表示该份额在结算单中核定的金额；正式核减可以使二者不同，但这不自动代表尚欠款。`is_final=1` 是最终核对的人工审核事实，不能从金额一致反推。
- **结项一致性**：当前候选触发器按稳定的 `cost_entries.id` 跨费用版本累计**仍有效且已最终核对**份额，要求与当前真实费用金额一致；同时逐条检查最新批准结算明细的核定金额均已最终核对。过期结算版本、非最终核对和被正式注销的核对均不能虚增结清金额。费用向下更正使原核对暂时超额时保留真实记录，再以正式更正或注销处理。


## 5. 结算作为完整版本历史，而非金额差补丁

- `settlements` 和 `settlement_items` 只保存稳定业务身份；`settlement_drafts` 支持未提交的草稿。
- 每次正式提交形成完整的 `settlement_versions` 和全部 `settlement_item_versions`；审核提交、退回、批准、拒绝形成独立不可变 `settlement_review_events`。
- **每份结算只有一个最新批准的完整版本参与净结算**；未通过审核的新版本不能改变已生效旧版；版本作废后净结算为 0，但原始实际费用、批准物资和结算正式历史仍存在。
- 费用核对固定引用当时的 `settlement_item_version_id`；新版生效时，原核对记录仍可查询，并标注当前版或 historical。当前费用金额由实际费用最新正式版本及最新有效结算核对分别确定，不能重复累加历史版本；批准物资历史只表达当时批准数量，不表示真实耗用。
- 金额用 INTEGER 分，数量用放大 10,000 倍的 INTEGER；任何超出预算/预计的真实发生仍保存并统计。单笔真实费用的内部重复分摊或超余额冲销则属于记账错误，另行阻止。

## 6. 档距历史与设备来源

- `physical_towers` 和 `logical_towers` 保留物理与逻辑身份分离，共塔多回不会被混成一个资产。线路、物理杆塔和逻辑杆塔的完整变更自动保留不可变历史；不可通过直接更新根记录跳过版本。
- `line_spans` 每次端点或状态变化必须递增版本、写变更人及依据，并自动新增 `line_span_history`；历史需求通过 `(span_id,span_version)` 复合 FK 指向当时的真实拓扑。
- 不引入 `span_length`、`jurisdiction_length` 等长度列；坐标不齐时仅参考距离未知，不影响需求、项目及结算。
- `source_records`、`demand_sources`、`demand_batches` 等保留原始台账来源与清洗追溯；来源修改不能替换已经批准的历史需求或物资快照。

## 7. 证据文件不再使用无外键的通用业务引用

`evidence_files` 保存不可变 SHA-256、字节数、原始文件名、MIME、内容寻址路径与上传责任人。`evidence_links` 使用明确的可选强类型外键和组合外键，强制**恰好一个**业务归属，支持具体需求版本、需求版本物资、需求状态事件、项目阶段、项目责任和资金版本、正式批准物资、真实费用、结算与审核、最终核对、档距历史、财务结清等；不会出现 `entity_type + entity_id` 无法验证的孤儿引用。

附件放在 `data/objects/sha256/`。文件存在性及哈希需要将来的运行层在写入和备份恢复时核实；SQLite 外键只管数据库引用，不能假装已经验证文件系统。

## 8. 一次次结算直至实际费用全部结清

`project_closures` 是子项目**费用结清的独立审核事实**，不是施工结束或检修计划完结。`project_close_guard` 检查正式项目批准、无未决结算和变更，以及每笔有效实际费用、每张有效结算单的金额是否被正式最终核对覆盖。费用份额与结算金额可以因正式核减而不同；有历史更正时保留原始凭据，由应用层提示复核。

**没有施工完成、物资领退及剩余工作量处置实体。** 项目批准范围及批准物资只作为需求和预算历史的正式依据；真正发生的材料费用随费用与结算明细核对，不能从批准数量推导真实耗用。

## 9. SQLite 部署与工程约束（供以后实现）

- 单机 SQLite + WAL；所有连接开启 `PRAGMA foreign_keys=ON`，设置 `busy_timeout`。
- 批准、结算确认、历史修订及关闭操作须在一个写事务内原子提交；建议 `BEGIN IMMEDIATE`。全部临时库可新建，**不设计旧 Schema 112 兼容迁移逻辑**。
- 只存真实可核验的来源、引用、版本、审计证据；不保存汇总状态或重复预算镜像。金额未知用 NULL，不能臆造零元。
- 业务生效日期与系统登记时点是两个独立事实。所有时间用规范 UTC ISO 8601 由统一数据库写入层处理，历史审计不能回填伪造曾经已知的数据。
- 数据库文件和证据对象均位于持久化 `data/`，不能启动时清空；备份用 SQLite 一致性备份加证据清单校验，不应直接在 WAL 写入期间生拷数据库。
- 多用户只通过未来服务进程统一写入数据库，不以 FTP/共享文件直接多主写 SQLite。

## 11. 不视为本版技术债的明确边界

2. 银行实际付款和供应商账款不是结算及费用核对的同义词，当前未纳入数据领域。
3. 全量跨线路拓扑版本及关闭后正式重开流程，必须依据实际业务进一步裁决；当前已覆盖杆塔名称、物理关系和档距拓扑历史、关闭后晚录事实标识。

## 12. 最新结算裁决与数据库边界

已确认：**每次结算只核定本次部分费用，多次结算直到实际费用全部结清**。`settlement_versions` 已移除曾被误加的 `kind`、`amount_basis` 字段；所有有效结算明细只有本次金额，不将单据历史版本当作重复结算。应用层基于真实费用、有效结算与费用核对记录计算未结算余额。

物资内部 `materials.code` 不变，外部 PMS 编码与名称规格等由 `material_versions` 形成完整历史。当前不同物资的外部 PMS 编码必须唯一，历史编码纠错与正式重映射不抹除旧定义。编码首尾空白禁止写入。

## 13. 第十二轮全量结构与正式历史完整性审计

**当前权威候选结构：70 张 STRICT 表 / 23 个现行业务事实视图 / 209 个触发器 / 71 个显式索引 / 666 个字段。已执行 362 项隔离 SQLite 契约测试并全部通过。** 以上为第十二轮结果，正文此前轮次的规模和部分阶段说明只属于当时设计历史，不得拿旧数字代表当前结构。

### 13.1 项目身份与完整档案只设一份可变权威

- `projects` 根表仅保留稳定项目 ID、业务编码、所属年度框架、阶段事件同步投影和创建事实；禁止覆盖编码、框架身份或删除根记录，移除无正式历史保护的 `name`、`category_id` 以及与阶段事件重复的 `updated_at`。
- `project_management_versions` 现在是**完整不可变的项目档案版本**，包含项目名称、类别字典 ID 与具体版本、责任人、负责单位及其精确历史版本、计划起止、初估值和正式变更理由。只改项目名称也发布完整新档案版本，不新增平行“项目名称历史”表；空改版与倒签均不可接受。
- `v_project_management_current` 仅展示最新正式项目档案，旧结算/批准时的项目档案可按原始正式版本还原。首版档案必须在项目进入正式阶段前于同一事务中完成；空项目身份不能通过阶段事件擅自进入入库状态。

### 13.2 组织层级本身必须可追溯

- `organizational_units` 只保存不变编码，`organizational_unit_versions` 连续记录正式名称、上级组织、状态、原因、责任人及登记时点。`v_organizational_unit_current` 是唯一当前定义投影。
- `project_management_versions.managing_unit_version_id` 与组织稳定身份形成复合 FK，确保子项目归口管理关系使用**当时选中的组织定义**，不会因班组改名、调整上级单位而被重新解释。
- 组织不允许形成循环，版本必须连续、登记时点有序、内容有真实变化；新组织或正式项目档案引用的具体定义不得从未来倒用。

### 13.3 资金、审批、结算和全部主数据历史时点

- 年度框架与执行协议的版本必须有真实额度、合同或状态内容变化，不得倒签，也不得登记在对象根身份建立之前；其额度继续为软预测基准，不拒绝合法超出原预算的费用或结算。
- 子项目资金关联、项目档案与批准历史、真实费用、更正、结算完整版本和审核事件全部要求连续版本及有序时间，保留每张独立结算单本期金额、原成本双金额核对和正式撤销历史；不建立第二套费用分摊或余额累计字段。
- 字典、标准作业对象、操作类型、参考价格的正式版本均不允许早于各自根身份或既有历史；对字典和作业对象还禁止制造无实质内容变化的空版本。
- `ledger_requests` 的操作者有真实 FK，参数指纹为合法小写 SHA-256，返回结果为 JSON 且不可覆盖/删除；`demand_duplicate_reviews` 的人工处理决定一经登记不可改写或擦除，复核须增加新审核事实。`voltage_levels` 的等级编码及名称保留稳定身份。

### 13.4 严格的业务与实现边界

数据库内不引入施工、检修计划、实物领退、额外分摊账、软预算硬上限、季度预警/进度汇总或用户角色判权。全部资金占用、协议额度对比、财务余额及归类只能由应用层对**有效、已经批准的事实**按稳定 ID 汇总。历史字段的增加仅为保存原本会被可变根值冲掉的**真实业务历史**，不是复制当前字段。

完整结构差异、逐字段冗余审计、全场景测试和明确留待实际环境验证的事项见[第十二轮全量审计报告](Schema113_第十二轮全量结构历史一致性审计_2026-11-07.md)。


## 14. 2026-11-08 归口单位业务语义确认

**用户明确裁决**：原先设计中的“责任单位”专指**子项目归口单位**，不是现场实际作业单位、施工单位、供应商或结算单位。

为消除编码层的歧义，`project_management_versions` 原 `responsible_unit_id` / `responsible_unit_version_id` 在尚未投产的 Schema 113 候选库中分别改名为 **`managing_unit_id` / `managing_unit_version_id`**。此处英文 managing unit 的唯一业务含义是“子项目归口管理的组织单位”。

- 一个子项目的一个完整管理档案版本**最多一个归口单位**，允许尚未指定；同一个归口单位可以归口多个子项目。
- 若更换归口单位，新增完整项目管理版本，不修改或删除旧版本；归口组织改名或调整上级也不覆盖原项目归口版本。
- `organizational_units` + `organizational_unit_versions` 继续维护组织稳定身份和完整定义版本；归口单位的两个字段通过复合 FK 绑定同一个组织及选定历史定义，避免引用未来组织版本。
- 归口单位与实际工作/施工单位、合同相对方、费用归属、结算接收人无推导关系；现阶段**不新增**作业单位、付款主体或二次分摊表。
- 同步更名归口单位反向查询索引 `idx_project_managing_unit`，测试、字典、权威设计和 AGENTS 均应使用新名字。只改变候选 Schema 113 语义与字段命名，运行 Schema 112 不受影响。


**最新候选核对（2026-11-08）**：归口单位语义及字段更名后，验收扩展至 **365 项 SQLite 契约**，且业务对象规模保持 70 张表、23 个视图、209 个触发器、71 个显式索引、666 个字段；此前第十二轮 362 项为历史快照。没有修改运行库 Schema 112。
