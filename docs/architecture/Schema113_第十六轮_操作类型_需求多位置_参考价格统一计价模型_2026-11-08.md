# Schema 113｜第十六轮：操作类型、需求多位置和参考价格统一计价模型

> **当前最高优先级数据库设计裁决，2026-11-08。** 用户明确授权依前轮方案实施。仅修改尚未接入运行应用的 Schema 113 候选 SQL、隔离验收和架构文档，不触碰 Schema 112 运行库、正式前后端及实际数据。此前第十五轮“需求与子项目独占关联，只有显式解绑才可重新承接”、第十四轮“逐结算需求结果、可超/未完结项、管理员原因可选”等裁决继续生效。

## 1. 业务抽象：操作类型—需求—参考价三方统一，标准作业对象和物资独立

**标准作业对象**（`work_objects / work_object_versions`）回答“做什么对象”，例如绝缘子串、防鸟装置；**物资主数据**（`materials / material_versions`）回答“使用什么具体型号材料和设备”，两者绝不能共用一张表或强制一一对应。检查、清障类需求可以零预计物资；此轮**不创建**强制的“操作类型→物资推荐表”，推荐属于可选后续能力。

**操作类型**（`operations / operation_versions`）定义具体作业：安装、防腐、更换、检测等；单操作类型版本有唯一作业对象和正式默认单位、允许的作业位置，并新增不可变 `pricing_features_json`。该数组声明统一的 `dictionary_types.id='price_factor'` 字典特征的稳定身份、正式定义版本、`required` 和 `source=asset/manual/either`。**操作类型不包含单价、基础费和计价系数**。

**专业需求**每条只关联一种操作类型，但正式版本可以包含多个物理杆塔、逻辑杆塔或档距作业位置；每个位置各自拥有计划数量、停电方式及真实现场价格特征值。需求现场因素 `site_features_json` 和参考价适用谓词 `additional_conditions_json` 均沿用同一价格特征字典的**编码、正式定义版本和类型**，不得出现两套相互不兼容的字段或另造临时因素。

**参考价格**定义“对哪些操作/现场条件、按何种费用作用域、使用什么计价模型”，不复制特定需求编号或实际位置，不提前写入业务真实需求数量。正式匹配和运算属于未来统一计价应用模块，不下沉为 SQL 触发器执行。

## 2. 需求逐位置工作量：完整事实与历史可溯源

原本一条专业需求的 `quantity_scaled` 和单个根位置不能表达 #15 塔 3 套、#16 塔 2 套、#17 塔 4 套的**不同数量和不同基位费**。

- `demands.initial_work_locations_json`：首次来源记录允许一条需求包含完整的位置清单；若未提供，默认按现有真实原始位置生成唯一位置。根记录一经创建不可覆盖。
- `demand_versions.snapshot_json.work_locations`：正式需求版本的全部位置清单作为完整不可变版本快照；`demand_version_work_locations` 是由正式版本插入事务自动投影出的强类型完整位置记录，含复合真实外键、位置类型、各自 `quantity_scaled`、`work_mode`、价格因素及位置识别快照。不得单独新增/修改/删除位置以伪造业务历史。
- 一条需求版本内部相同物理塔、逻辑塔或档距各只能出现一次，避免基位费重复。严格核验 **版本总工作量 = 各位置计划数量之和**。根原始数量及已签版本的总量是核对依据，不是第二套可任意修改的“当前数量缓存”。
- `demand_revisions` 新版完整重建本版位置明细：单位置仅改数量的修订自动同步到该位置，多位置数量调整应明确提交新版完整 `work_locations`，旧位置事实保留。
- 真实设备台账仍是位置引用的权威，需求版本的识别说明和计价输入快照冻结其**当时**依据；不以今后的设备重命名或塔型变化重新解释旧正式报价。

**举例**：安装防鸟装置 V1 共 9 套：
  物理塔 #15 = 3 套；#16 = 2 套；#17 = 4 套。假定每塔基位费100元、每套20元，逐塔参考价分别 160/140/180 元，**原始完整需求参考价480元**。不能把9套先合并后只收一次100元基费，错误得到280元。

## 3. 正式价格规则：可扩展但不在数据库执行公式

`reference_price_versions` 保留统一的、不可变、能追溯操作定义版本和正式单位的价格规则：

| 计价模式 | `pricing_mode` | 例子 |
| --- | --- | --- |
| 固定金额 | `fixed` | 某一次标准检查固定价：`unit_price_fen` 作为该作用域一次固定金额 |
| 按数量 | `per_unit` | `quantity × unit_price`，不得同时设置位置基费 |
| 基费＋数量 | `base_plus_unit` | 每个位置一次 `base_fee` 加逐套费用 |
| 整批单档 | `quantity_bracket` | 按当前作用域总数量选唯一档，整批使用该档基费和单价 |
| 累进阶梯 | `progressive_bracket` | `calculation_params_json.tiers` 明确边际阈值及各档单价 |
| 按组收费 | `group` | `group_size_scaled` 单组容量，`group_fee_fen` 每组金额，由应用层向上取整组数 |
| 费率计价 | `rate` | `rate_basis` 明确计费基数，`rate_basis_points` 表示万分率，防止百分比口径混淆 |
| 多项费用组成 | `composite` | 在该**不可变价格版本**内用 `fee_components_json` 定义多个费用覆盖项、模型与参数 |

所有参考价规则还可在 `calculation_params_json` 设置非负 `min_amount_fen / max_amount_fen`；结构校验拒绝上下界倒置、分档乱序、无定义费率、零组容量及组合相同费用覆盖键。费用组成 JSON 和正式价格版本绑定，**不能事后通过新添一行费用改变已发布的价格版本**。

`pricing_scope` 明确规则的收费作用域：`work_location`（单个作业位置）、`work_batch`（一次作业批次）或 `project`（整个子项目）。**一基塔的基费按该塔算一次**；需要按批次或项目统一收的运输、机械进场等，不得附到每项需求里重复计费。

`work_mode` 明确停电、不停电或不限制；需求各位置实际停电条件不明时，不允许拿仅适用于停电的规则确认正式价格。价格版本的其他电压等级、塔型、规格、字典特征、价格有效日等依然必须在统一应用计价模块中完整匹配，出现匹配重叠时不得默认随便选第一条。

**没有在 SQLite 中实现计算公式/税率匹配/金额舍入/项目统计。** 正式计价引擎必须使用定点数/Decimal 及显式舍入规则，版本化测试覆盖比例、累进、整批、量价与项目级费用。不可把应用未实现的部分标记为已经开发完毕。

## 4. 需求独立报价与项目正式批准报价：分别保留可解释的历史

- `reference_price_evaluations`：一次针对“独立完整需求版本”或“**一个明确的项目批准需求范围版本**”的报价会话。带 `draft/final`、价格适用日期、版本化计价引擎编号、输入快照、真实操作/确认人及时点。任何一个独立需求可以在不被项目关联时试算和形成正式报价。
- `reference_price_evaluation_lines`：该报价的每一位置、费用覆盖范围、采用的精确 `reference_price_versions.id`、计价数量、实际结果（人民币分）、`calculation_inputs_json` 和 `calculation_trace_json`。同一位置同一费用覆盖不可重复；“综合价 `main`”不可与人工/材料等分项同位置叠加。正式确认报价必须覆盖**全部**需要报价的位置，否则禁止伪造“已完整计价”，允许真实结果明确为0元。
- `project_approval_work_locations`：对一个正式项目批准范围，明确本项目实际承接需求的**哪些作业位置、分别多少数量**，而不是只存一条需求总量；单位置自然初始化，多位置由应用在未批准草稿阶段完整指定。正式批准时总和必须和 `project_approval_scope_versions.quantity_scaled` 一致，且批准后不能改写。
- `project_approval_scope_prices`：一项已批准需求范围若选择正式报价，必须引用与该范围**完全同版**、已 `final`、不可变的 `reference_price_evaluations`。不为每个项目需求关系强制存单个 `reference_price_version_id`，因为每个位置及费用组成可以使用不同规则；已移除原 `project_demand_scopes.reference_price_version_id` 及其反向索引。
- **报价未齐**：未匹配到正式规则的范围 `project_approval_scope_prices` 不存在，事实视图 `v_project_approval_reference_basis_current` 显式返回 NULL；这与金额真实等于零元不同。立项本身可以拥有尚未计价的需求，但**不得向使用者声称有完整项目参考价**；可显示已报价的小计、已报价/未报价清单。
- `project_reference_price_charges`：一个批准版本下的独立批次/项目级参考费用，`charge_scope_key` 唯一，真实金额及完整计算依据不可在项目批准后覆盖，防止重复加入运输、进退场等全局费用。
- `v_demand_reference_quote_current`：只显示**需求当前正式版本**的最新已确认独立报价，未重算新需求版本时保持无结果，而不是继承旧版报价。
- `v_project_approval_reference_basis_current`：提供当前批准范围和精确选用的报价身份，没有 SQL SUM/统计缓存。

**项目参考总价（只有当每项正式承接需求均完整计价时才成立）**：

  `Σ(本次批准需求范围选择的正式计价明细金额) + Σ(正式批准的批次/项目独立费用金额)`

应用层对数据进行完整性/计价口径复核后汇总。正式批准预算 `project_approval_versions.approved_budget_fen`、具体需求价格结果、真实发生费用和分次结算继续独立，**不存在实际费用/参考价/预算必须相等的硬约束**。

**例子**：原需求9套480元；本项目只批准#15塔3套和#16塔2套，即**300元**，不能用 `480×5÷9` 按比例分摊；再承接另一条需求参考价200元，统一运输50元，项目**完整参考价550元**；该项目独立批准预算可以是1200元，与550元不等不是数据库错误。全部价格均仅为演示假设值，不是官方工程定额。


- **已确认报价与立项草稿量价一致性**：选用正式报价以后，作业位置不可暗中追加；尚未批准时可先取消报价选用、修改位置和数量，再重新核价。**正式立项批准时必须二次核对已选报价的需求版本、逐位置集合及每位置准确数量**，旧报价即使被重新勾选也不得冒充本次有效价格；未报价范围仍允许存在并须由应用报告“未完整计价”。

## 5. 一致性与精简治理结果

- `operations`/`work_objects`/`materials` 保留独立稳定身份；操作类型的一版只关联一种标准作业对象，具体预计物资继续通过独立的 `demand_material_version_items`、正式批准物资版本管理，零物资合法，不增加虚构领退料或施工完成表。
- 真实业务新增6表：`demand_version_work_locations`、`project_approval_work_locations`、`reference_price_evaluations`、`reference_price_evaluation_lines`、`project_approval_scope_prices`、`project_reference_price_charges`；新增2个**非统计**事实视图；必要触发器与3条唯一作业位置索引。复用现有 `price_factor` 字典和原参考价/批准历史，未增加独立匹配算法表或物资推荐冗余主数据。
- 工作位置明细并非独立“施工完成记录”：它们只表示正式**需求版本及项目批准版本的计划工作量**，实际已完成需求仍从各次 `settlement_scope_results` 获得，历史关系不可混用。
- 正式计价结果没有在需求根、项目根或批准版本根增加可变的汇总金额；价格项目汇总为应用层逻辑。原项目批准基准、结算财务、需求实际解决和项目弹性结项完整保留。
- 对一条作业位置只允许一次完整“综合价”或互不重叠的费用组成；确认正式报价后，任何一项金额、定位、计价版本和覆盖范围均不能无痕改写。项目未批准可重建报价草稿；已批准只能正式变更生成新批准版本。
