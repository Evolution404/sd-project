## 一、总体裁决

现有系统已形成台账、需求、项目、计划、预算、费用、结算等基础能力，但“功能多”不等于“能顺畅完成项目管理”。主要问题：操作类型新规则与本机已配置数据脱节，领域关系部分只由服务端解释而不是由 Schema 保证，SQL 和事务被散放在大量业务文件，项目/需求/计划呈现集中在巨大 App.vue 页面中，前端虽采用 Element Plus 仍缺少统一业务页面的交互语言。

下一阶段必须按 **数据定义 → 数据存取边界 → 业务流程 → 业务页面** 的顺序治理，而不是继续零散增页。已有真实业务事实、批准版本、不可变凭证和历史审计必须保留；旧技术实现和多余兼容层无需保留。当前 Mac 数据库不得静默重建。

**双视角：**
- 管理线：年度框架 → 子项目 → 检修计划（停电/不停电）→ 该计划承接的专业需求。
- 资金线：年度框架 → 执行协议 → 子项目 → 检修计划 → 费用、结算及未来独立付款事实。
专业需求只存一份，由多个计划引用项目批准范围；工程量、费用、结算、实际付款不能互相替代。

## 三、P0：操作类型的业务模型

### 1. 唯一录入定义

每个操作类型必须包含：
- 操作名称/编码；
- 固定计量单位（唯一有效单位，按四位小数进行工程量计算）；
- 唯一作业对象：线路侧设备 line 或共用物理杆塔 physical，不允许 both；
- 允许的作业位置种类：杆塔 tower、档距 span，可以一项或两项；物理杆塔对象只允许 tower；
- 允许范围内的默认作业位置；
- 可选处理部位/默认数量/完成标准/操作专用附加字段/录入提示。

**作业对象**指业务实体归属，**作业位置**指定位方式，**处理部位**是需求中具体维修对象描述；三者不要并成一个字段。操作决定“做什么、在哪类位置、用什么单位”；具体线路、杆塔/档距、数量、发现日期、问题依据属于逐条需求。

在线与 Excel 必须调用同一服务端校验。界面先选操作，自动确定固定单位和对象，若只允许一种位置则免去第二次位置选择；批量选择位置后逐行录入实际数量及部位，再做提交预检。改变定义仅新增配置版本，不改动已有需求、项目、计划、费用、结算所采用的数量/对象/单位/位置快照。

### 2. 当前真实配置断点

本机 14 个启用操作名称为更换绝缘子、清扫绝缘子、安装防鸟装置、更换防鸟装置、更换防振锤、更换金具、导线修补、地线修补、更换导线、更换地线、杆塔防腐、更换杆塔、更换接地装置、更换拉线。单位和对象已有值，但当前版本的 operation_profile.default_location_kind 全部缺失（14/14）。

应在“系统管理 → 操作类型”提供 **待完善 14 条**的批量编辑视图，逐条呈现“操作名称／作业对象／固定单位／允许位置／默认位置／当前使用情况”，管理员逐行核实后一次预检并明确提交各自的新配置版本。可给出待审建议，但不能仅凭操作名称擅自决定杆塔/档距，不能在程序启动时悄悄写库。完成后立即验证需求在线、导入、修订、参考价能统一使用。

### 3. Schema 不变量缺失

- server/schema.sql 中 dictionary_items.work_target_type 仍允许 both；服务层 operationDefinition() 只允许 line/physical。数据库层和业务层存在不一致，必须在新 Schema 收口 CHECK。
- 当前定义的单位、对象在 dictionary_items 的可更新列，位置配置只在 dictionary_item_versions.snapshot_json 内。这增加查询和约束成本。建议为操作定义设置稳定 ID 和不可变定义版本，固定单位/唯一对象/位置范围属于同一版本事实源；JSON 仅承载非核心扩展表单配置。
- demands 要求所有位置均有 logical_tower_id，即便档距位置由 span_id 表示也必须指定一个杆塔锚点。新完整 Schema 应使用 tower_id 与 span_id 的互斥引用及位置快照，既保证 FK 又符合用户所认知的“杆塔作业/档距作业”。
- 不可将定义变更回写已批准工程范围。业务快照和历史版本是必要业务事实，不是需要删除的历史技术兼容层。

## 四、P0：数据库层独立与领域边界

### 1. 现状

server/db.mjs 目前集中连接、SQLite WAL、BEGIN IMMEDIATE、one/all/exec、事务等基本调用，方向正确，但远未达到“所有数据库操作封装到一个模块”的目标：约 25 个服务模块直接导入 DB 工具，大约 31 个 .mjs 文件内有 SQL 字符串，多个模块直接 db.prepare；server/server.mjs 约627行同时处理 HTTP 路由、验证、SQL 和文件业务。

server/schema.sql 711行、52表，整体约束并非都完整。attachments 采用 owner_type + owner_id 多态指向来源/需求，没有具体所有者外键（已从 PRAGMA 外键检查证实）；可能出现孤立业务附件。开发用 pms_import_issues / pms_import_runs 仍嵌于正式 schema，与此前“PMS 治理仅作开发导入、不作为业务系统菜单”的裁决应进一步隔离。

数值模型应保留：quantity_scaled = 实际工程量×10000，金额整数分，BigInt 控制运算精度；对不同单位的工程量仅分组汇总，不直接相加。并发、版本、幂等、不可变批准/结算历史都是优点，应保留。

### 2. 目标目录（数据库模块不应置于 API 下）

    server/
      app/                 # 启动、生命周期、组合装配
      http/routes/         # 请求、授权和响应映射：不含 SQL
      domain/
        operations/        # 定义和版本，不变量
        assets/            # 线路、杆塔、档距、共塔
        demands/           # 录入、核实、来源、修订
        projects/          # 储备、入库、立项、变更
        plans/             # 计划、工作量、完成
        finance/           # 框架、协议、预算、成本、结算
      storage/             # 唯一允许访问 SQLite 和持有 SQL 的模块
        database.mjs       # 连接、事务、WAL、关闭、备份
        schema.sql         # 唯一当前版本完整 Schema
        repositories/      # 每个领域的 CRUD/归档/版本操作
        read-models/       # 分页列表、聚合统计 SQL
      services/            # Excel/文件及外部基础设施
    web/src/
      app/                 # Session、导航、布局、路由
      modules/{demands,projects,plans,finance,ledger,settings}/
      components/ui/       # 公共页面模板
      styles/              # 唯一品牌 token + Element Plus

禁止 HTTP routes、Vue 层及纯领域规则直接调用数据库；所有数据库 SQL 只在 storage/repositories 和 read-models；业务 services 组织跨表事务、权限/版本复核与审计，禁止用自由拼接 SQL 做通用 CRUD。**集中管理模块不等于将全部 SQL 变成一个数千行 db.mjs**。

在新版完整 Schema 中使用 NOT NULL、CHECK、FOREIGN KEY、UNIQUE 和必要的不可变触发器守住关键约束；查询采用有界分页/SQL 聚合，计划和财务按真实 251/6051/5669 的设备规模和 5000 条导入压测。SQLite 可以继续作为内网服务的唯一事务库，先有测量再考虑换数据库；同步 Node SQLite 的长查询/导入需要检查事件循环阻塞。

### 3. 数据保护规则

现有 ~/.local/share/sd-project/business.sqlite 是当前 Mac 的真实数据目录，不得自动删除、清空、结构升级、强行覆盖、复制危险 WAL 快照。开发新 Schema 时使用单独 DATA_DIR 初始化全新测试库。旧技术兼容不做，但现有业务数据后续如需进入新结构，须另做经过审核的保留事实导出/导入工具，而不是隐式迁移。正式产品必须新建空业务库、不能打包 PMS 测试数据；SQLite 在线备份、恢复演练、权限隔离要专门验收。

## 五、项目管理流程应这样简化

| 阶段 | 用户主操作 | 后端关键约束 |
| --- | --- | --- |
| 需求录入 | 选操作、位置、数量、问题与来源，保存草稿/提交 | 固定单位和对象；逐条位置合法；来源完整；Excel与在线相同 |
| 需求核实 | 查看待核实清单，确认/退回/修订 | 未核实需求不可纳入批准项目；历史、版本、证据留存 |
| 项目储备 | 从有效需求池选承接量，指定框架、估算及物资意向 | 需求只存一份；估算缺价不能视为零 |
| 入库/立项 | 明确类别、协议、价格依据和批准预算 | 协议与项目属于同框架；正式同一需求原则上仅被一个子项目承接 |
| 计划安排 | 在项目中建停电/不停电计划，分配批准范围 | 已完成量 + 在途有效预留量不得超批准量；同需求可以分多计划 |
| 施工完成 | 记录核定完成数量、验收与实际费用 | 项目预算/计划预算与实际费用不同事实；超额保留差异，不篡改预算 |
| 结算核对 | 结算凭证/冲销、费用核对和项目闭环 | 结算与付款独立；四状态由实施和净结算推导，未完成不自动结项 |
| 月季分析 | 年度框架→协议→项目→计划的多口径统计 | 季度25%等预警应先裁决“预算发生”统计口径，不混用批准/费用/结算/付款 |

完成检修计划后，未完成工作量按已批准规则释放，**并不自动释放计划已核定预算**；减额另行审批并保留历史。跨子项目分担例外、特殊关闭、预付款的付款归集尚未完整裁决，不应假设已有授权。

## 六、业务 UI 全面重构方案

已有 ApplicationShell、Element Plus 和系统管理蓝白视觉基础可直接保留，不必引入新组件库。旧 README 还写“深绿色主色”，与当前实际蓝白主题冲突；现有主题 token #3478f6 / #2463d5、背景 #f5f8fc 是当前标准。

**信息架构**：
- 工作台：我待处理的核实、入库审批、计划、结算提醒及预警，点击直达对应实际任务。
- 需求：需求列表、新建/Excel导入共享批次工作台、草稿、需求详情。
- 项目：储备、已入库、已立项；详情内用“概况/需求范围/检修计划/预算费用/结算/历史”清晰区分。
- 实施：检修计划清单，计划详情内“安排/完成/费用/结算”，不用反复钻入多层项目弹窗。
- 资金：框架、协议、预算、费用/结算各口径统计；参考单价归到估价辅助。
- 基础数据及系统管理：管理员设备台账、操作类型、单位及其他数据字典、权限、日志。

**统一页面模板**：页头（名称+主要操作）→状态/关键指标→筛选区→业务数据表→详情主体。新增/修改用 ElDialog，详情在主内容区自然流呈现，不使用固定详情抽屉。表格主要动作常显，次要操作收纳但可发现。页面要有明确“下一步”，不用将开发约束或冗余长提示写进用户界面。危险操作弹窗需业务影响和确认。

**样式治理**：消除局部硬编码品牌色和组件重复 CSS，建立字号、间距、边框、按钮、状态、空态和错误信息标准。当前 style.css、styles/dictionary.css、LedgerWorkspace.vue、application-shell.css 存在多个 10px/11px 字体，需调整：正文/核心表格建议不低于 13–14px，辅助说明至少 12–13px，重要数值20px以上。统一多端 1500/1280/960/760px 布局，不只看是否溢出，还检验表格对齐、弹窗操作可达、文字可读和任务完成路径。

**前端代码**：App.vue 875 行，集中状态和需求/项目/计划详情，且大量 Record<string,any>。应拆成领域路由页面、业务状态 composable 与 API DTO；遵循唯一 Element Plus UI 门禁，避免隐藏在页面内的冗余表单。保留线路/杆塔搜索 filterable、详情主文档流、批量需求草稿和历史快照等已经批准的行为。

**优先改造三个入口**：操作类型维护（待完善批量复核）、新建需求（先选操作→自动单位/位置规则→逐行编辑）、项目详情（需求范围/计划/预算/结算分区，计划直接可达）。

## 八、推进顺序（每阶段完成后必须验收）

**G0：保护工作现场。** 本地72项未提交修改来自现有开发；不直接覆盖、重置、自动提交。固定当前基线；继续运行 npm run check、npm run test:browser。区分“编码完成/自动验证/用户易用/发布验收”。

**G1：恢复关键业务可用性。** 操作类型“待完善”批量配置与明确复核，形成新版本，验证 Excel、在线录入、参考价和已保存需求的历史不漂移。
