## 已完成：数据库结构与约束

1. **树状费用**：子项目 `project_cost_nodes` 可有多层父子节点，人工费、材料费以及任意子费用均为真实节点；父级只分类，末级才允许产生实际费用或结算明细。
2. **费用历史**：`project_cost_node_versions` 保存不可变版本；`cost_versions` 和 `settlement_item_versions` 各自引用采用的定义版本，名称更改不影响过去正式记录。
3. **实际费用**：`cost_entries` 是真实费用稳定身份；`v_cost_current` 只取每笔费用最新有效版本；实际金额可能超预算，预算是管理基准而非数据库硬限制。
4. **多次部分结算**：一个子项目可建立多张 `settlements`；每张 `settlement_items` 可选择若干末级费用，每条 `settlement_item_versions.amount_fen` 只记录本次金额。共同费用不强制编造项目需求范围。
5. **对账与历史**：`cost_reconciliation_versions` 记录真实费用与结算明细的正式核对历史；`v_effective_cost_reconciliations` 排除被后续正式结算版本取代的旧核对。同一实际费用的跨历史版本核对也不得重复超额。
6. **数据库/应用边界**：父级金额、应结、已结、剩余结算余额、预算偏差、季度进度和预警不在数据库里维护冗余聚合，均交由未来应用服务按有效事实计算。

示例已验证：人工费 90 元、材料费 50 元；第一单人工 30 元＋材料 20 元，第二单人工 60 元＋材料 10 元，第三单材料 20 元，两项均结清。随后正式增加材料费 5 元，产生新的待结余额，而历史结算不变。

| 优先级 | 待治理项 | 边界 |

| P1 | **实际环境验收** | 真实 PMS 台账、附件恢复、Windows 内网、多用户并发与浏览器全链路尚无 Schema 113 正式验收 |
| P1 | **财务语义** | 本次结算不等于银行实际付款；费用向下更正后如果已结大于应结，差额需要后续正式更正/核对流程处理 |

**需保留的边界**：当前候选禁止已记账的末级费用直接变成父级，以免历史发生额重复计数；若以后允许对已结费用再拆分，需要独立的正式费用重分类记录和变更历史，而不是改写父级身份。

## 仓库收口方法与复核

- 旧路径删除和新模块路径新增是既有**结构性重组**，不是可直接清理的垃圾；禁止 `git clean -fd`、`git reset --hard` 造成成果丢失。
- 不提交 `data/`、生产 SQLite、附件、`node_modules/`、`dist/`、`test-results/` 及缓存。
- 以**候选 SQL + 自动验收 + 逐字段字典 + 对象矩阵 + 触发器清单**为数据库权威资料；历史日期化文档保留追溯，不再视为当前唯一标准。
- 在仓库根目录运行 `npm run check`、`node --test tests/database/*.test.mjs`、`python3 -B docs/architecture/schema113_database_acceptance.py` 复核。
