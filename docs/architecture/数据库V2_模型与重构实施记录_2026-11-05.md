## 总目标及业务不变量

1. 项目唯一数据库模块：`server/database/`。Schema、初始化、事务、查询和所有 SQL 的最终归属在此模块；HTTP/Application/Domain 不能长期持有 SQL/SQLite 原始对象。
2. 面向用户的主路径是“操作类型 → 具体设备 → 数量”，单位、作业对象、允许定位方式和版本从操作定义自动继承；同一事实不重复输入。系统不能替代入库、立项、费用确认等正式审批。
3. 专业设备一物一号：`transmission_lines` 线路、`logical_towers` 线路节点、`physical_towers` 共用实体、`line_spans` 档距分别稳定标识；更换物理塔不能伪装为单回路关联纠正。位置变更不能漂移已有历史快照。
4. 一条专业需求正常只有一个正式承接子项目，一个子项目可有多个检修计划，计划可分次承接相同批准范围；有效完成量 + 未结束计划预留量 ≤ 已批准量 ≤ 核实需求量。计划结束后未完成工作量释放，**计划预算不自动释放**。
5. 年度框架 → 子项目 → 检修计划为管理视角；年度框架 → 执行协议 → 子项目 → 检修计划 → 结算为资金视角。参考价、批准预算、计划预算、实际费用、结算、实际付款不同事实、不同状态与版本，绝不能混成一个“发生金额”。
6. 需求重复由人工判定，来源/证据可以并入原需求但数量不叠加。经确认的事实仅通过更正、撤销或新的批准版本处理，不能覆盖原始历史。
7. 金额使用整数分、工作量使用 10,000 倍整数；事务控制并发与幂等；外键 CHECK 和业务服务双重约束。
8. 新结构从空的隔离数据库创建；禁止偷偷升级、覆盖或删除旧版真实数据库。发布 ZIP 在根 `dist/`，SQLite/WAL/附件/备份固定在根 `data/`，发布包不包含运行数据。

## 已落地：数据库结构第一批

- Schema 版本从 109 经 110 提升为 **111**，新实例只按当前版本完整建库；旧版数据库版本不匹配即拒绝启动，不实现旧版兼容层或自动删库。
- 旧单体 `server/database/schema.sql` 已拆成唯一权威源：
  - `server/database/schema/tables.sql`：业务表及关系
  - `server/database/schema/indexes.sql`：索引
  - `server/database/schema/views.sql`：当前有效事实视图
  - `server/database/schema/constraints.sql`：跨表触发器、历史保护
- `server/database/bootstrap.mjs` 按固定顺序在同一初始化事务中加载四部分 SQL。
- 生产 Schema 移除了开发专用 `pms_import_runs`、`pms_import_issues`；其建表仅在 `scripts/import-pms/dev-audit.sql` 供开发导入工具显式创建，不存在正式空业务库中。
- 当前操作位置能力从最新版 `dictionary_item_versions.snapshot_json.operation_profile` 的运行时解析，迁到带外键、强 CHECK 的 `operation_location_settings`；历史快照仍是不可变的旧版本事实，**不是当前配置的第二个读源**。
- 位置配置限制允许杆塔/档距不能为空、默认位置属于允许范围、共用物理杆塔不能按档距定位。非法跨表改对象在 SQLite 触发器处拒绝，即使业务 API 校验被绕开仍不接受。
- 需求位置现要求“杆塔时无档距关联/版本快照，档距时存在有效档距与版本快照”；物理杆塔作业不可标记为档距。数据库继续保护原始工程量与历史记录。
- 字典和操作类型的创建/修订持久化已抽到 `server/database/repositories/dictionaries.mjs`；操作位置读写由 `server/database/repositories/operation-profiles.mjs` 集中处理，更新在同一写事务内。
- 新增数据库约束反例测试；业务/数据库/前端自动化测试已持续扩充，具体通过数量以最新完整测试报告为准。

## 目标实体边界（下一批实施前需逐项验证）

| 领域 | 权威数据实体与关系 | 使用者需要输入的最小事实 |
| --- | --- | --- |
| 身份与审计 | 用户/权限、会话、IP、不可变事件、请求幂等键 | 登录和必要授权 |
| 通用字典 | 单位、电压、来源、项目/费用分类；代码和有效状态 | 管理员仅维护确需更改的基础项 |
| 操作定义 | 独立 `operations` / `operation_versions` / 位置规则 / 字段模板 | 管理员一次维护；业务录入只选“做什么” |
| 设备台账 | 线路、物理塔、逻辑塔、档距、实体关联更换及历史 | 现场位置，必要纠错依据 |
| 需求 | 需求、来源、位置、数量、核实记录、人工重复判定、版本 | 操作、设备、工作量及真实问题依据 |
| 项目 | 框架、协议、储备、需求承接、入库版本、批准版本、变更单 | 选择需求、估算依据和有权限的确认 |
| 计划/实施 | 检修计划、批准范围预留、工作量分配、有效完成与更正 | 分批安排及实际完成确认 |
| 物资 | 物资目录、计划/需求用料、出库、实耗、回退留痕 | 核实物资规格数量；审批细则待裁决 |

| 文件/导入 | 附件实体、真实所有者外键、来源记录、正式 Excel 批次 | 选择文件并核对差异，不反复填写派生字段 |

**设计边界：**“操作类型完全独立于通用字典”和“需求不再保存冗余位置类型/杆塔锚点”是下一批真正的结构重构，**尚未实现**。当前 `operation_location_settings` 仍以 `dictionary_items` 为所有者；不得假称已彻底完成独立操作类型建模。

## 下一批必须完成的数据库改造（按依赖顺序）

1. **操作实体独立**：从 `dictionary_items` 分离 `operations` 和独立版本表，固定单位与作业对象，消除“操作型字典 + 专用字段 + 独立位置表”跨类型依赖。API/字典界面和所有需求、参考价外键同步切换，禁止长期并行两套操作定义来源。
2. **设备定位归一**：需求具体关联逻辑塔、共用物理塔或档距；消除“档距需求必须另填杆塔锚点”的不自然设计；对当前关联和历史位置作强外键与互斥约束，不要求用户选择可以自动推导的位置类型。
3. **项目与计划的批准量守恒**：项目需求范围、批准版本、计划分配、完成确认与余量释放统一明确引用和事务，消除各种状态复制与不必要 JSON。
4. **预算/费用/结算/实际付款拆分**：各自独立的确认与撤销版本及有据可查的归集。付款政策尚未裁决，不创建能被误认为已经实施的真实付款凭据。
5. **附件外键（已完成）**：附件需求/来源归属二选一强外键已在 Schema 111 实施，禁止无效归属。
6. **全 SQL 收口（第三阶段已完成）**：HTTP/Application 直接 SQL 已全部迁入数据库模块，并通过递归 CI 架构门禁保护；后续需精简数据库 index 中通用 SQL 的公开出口。
7. **读模型与索引复核**：主链路按线路、操作、日期、项目、计划、预算、费用、结算使用单一清晰查询；必要时使用视图，避免冗余不可维护的累计字段。
8. **发布与数据隔离验收**：独立库、外键检查、全部回归、Chrome UI、5000 行导入、Windows ZIP 构建/离线运行校验；当前已批准业务历史不可损失。

## 验收要求

- 每一批改造必须同时提供：结构定义、字段说明、合法/非法 SQL 约束、事务并发、正式 API 业务测试、简化用户操作流程的浏览器验收。
- 版本号变更只代表一个新的 Schema 初始化契约；用户现有 109、110 及更旧数据库必须拒绝隐式升级并完整保存。真实数据正式迁移方案必须另经核实与备份后执行。
- 不因增加关联表、版本表而增加用户操作步骤；明细当前状态应由唯一权威事实推导。必要人工输入/审批必须说明为何不可自动化。
