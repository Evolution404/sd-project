## 二、本轮新增治理及验证

1. **需求历史时间正序**：正式需求修订时间不得早于上一版，需求状态事件的记录时间不得逆序，终止状态不允许隐式重开。正式版本和状态是不同业务事实，二者均不可原地覆盖。
2. **停用物资新增的准确规则**：物资初次出现在新版需求时必须处于启用状态；历史曾选中的物资即使后来停用，也允许保留在同一需求后续正式清单中。主数据本身始终不建版本表。
3. **来源证据拆分**：`demands.batch_id` 是批次归属，`demand_sources` 是需求来源关联；`batch_demand_sources` 只有在需要追溯*当时导入的批次与原始来源断言*时才存储，不作为第二份当前关联。已提交批次、已关联的原始来源和原始导入三元事实不可被无痕篡改。
4. **原始导入批次 FK**：`batch_demand_sources.batch_id` 必须等于该需求真实所属批次，不允许把其他批次的来源当成这一需求的导入证据。
5. **去除重复来源索引**：沿用已有 `uq_pms_source_record` 和 `uq_excel_source_row`，避免对同一 PMS 编号或同一 Excel 行建立两组等价唯一索引。其他表的完全重复索引检查无异常。
6. **完善来源不可变性**：`source_records` 在被需求、批次或仅被导入三元断言引用后都不能直接更改或删除。需求确认后原始来源关联亦不可被删除；修改需要创建新的可追溯来源事实。

## 三、需要区别对待的“重复数据”

- **应该消除的重复**：根表和正式批准版本分别维护“现行预算”；把批准量从旧提案字段 `COALESCE` 回补；同一来源的两组唯一索引；并列保存同一份当前材料统计数量。
- **合法且必需的历史快照**：需求当次正式确认的完整物资清单、项目批准时的物资名称型号单位、结算提交时的完整明细及审核事件、真实原始导入批次。这些描述不同时间点的事实，不等同于“冗余”。
- **业务边界**：`materials` 的名称、型号、规格直接在单张主数据表维护。需求版物资清单和项目批准版物资快照属于相应**需求及项目业务历史**，绝不建设物资主数据版本表。

## 四、按优先级继续检查的边界

| 优先级 | 对象 | 定版验收口径 |
| --- | --- | --- |
| 高 | 项目关闭 | 最新正式批准范围、已验收量、剩余量及书面处置必须一致；不准通过更改提案字段跳过关闭校验 |
| 高 | 项目批准 | 正式批准金额 NULL 不得用旧提案金额伪装；预算与已定价范围合计不同时只报告、不阻止超预算 |
| 高 | 需求修订 | 任何正式更新必须保留工作位置、作业类型、对象、数量、单位、物资清单的完整最终定义 |
| 中 | 真实台账 | 台账当前字段与各自历史必须由同一数据库事务生效；禁止只增历史或只改当前 |
| 中 | 来源导入 | 外部记录号、来源文件、工作表和行号逐级追溯；后续来源补充应有独立证据而不是覆盖旧来源 |
| 中 | 统计性能 | 隔离小数据集测试不能代表全量 PMS / 多框架运行性能；以后做真实数据规模的 `EXPLAIN QUERY PLAN` 及索引评估 |
