# Schema 113 第十四轮：多装置计价、结算需求完成事实、弹性结项、管理员理由可选

> 2026-11-08。**当前业务裁决及候选数据库设计说明**。Schema113 是尚未切换运行应用的候选库；不修改运行 Schema112、前后端或真实数据。第十三轮关于“没有独立施工/检修计划”的裁决继续有效，本轮仅增加必要的**结算内需求实际解决结果**。

## 一、四项用户裁决

1. 同一基物理杆塔一次安装 1、2、3 或更多防鸟装置，参考计价必须支持**按件、每基固定费加件价、按数量区间定价**，不能强制线性倍乘，也不能把“一基塔”的基费重复乘以装置数量。
2. 项目范围的**批准需求工作量**和每张结算单的**实际解决数量**是两种事实；真实解决可小于或大于批准数量，实际费用、已结算金额、批准预算各自独立。项目可以在实际需求未全部完成、费用仍有待核对余额、或者实际发生超预算时**经正式审核结项**。
3. 每次项目正式立项必须有至少一项有效且已确认的专业需求范围；每张**非作废的结算单正式版本**必须清晰列出本次解决哪些已批准的需求范围、各解决多少。不再从材料费、人工费等多个结算成本明细的计价数量推断需求完成量。
4. 管理员任何业务操作无需强制填写理由，但仍必须提供合法业务身份、操作人、登记时间、真实变更版本以及需要的审批、金额和证据等必要事实。数据库**不冒充应用层的角色判权**。

## 二、同塔防鸟装置的计价

每一条 `reference_price_versions` 均属于一个准确的 `operation_id + operation_version` 操作及计量单位版本，原有电压等级、塔型、停电方式和扩展适用条件仍成立；新增三个正交字段：

| 字段 | 定义 |
| --- | --- |
| `pricing_mode` | `per_unit` 按件、`base_plus_unit` 每个作业位置一笔固定费再逐件计价、`quantity_bracket` 根据本次该位置数量选一档 |
| `base_fee_fen` | 单个作业位置只计一次的固定费用；按件和分档模式应为零 |
| `quantity_brackets_json` | 结构化有序完整分档数组；每档必须有最小数量、最大数量（末档可用 JSON null 表示无上限）、本档固定费和件单价；默认空数组 |

原有 `unit_price_fen` 为每件单价。对于一基实际物理杆塔上的本次装置数量 `n = quantity_scaled / 10000`：

- **按件**：`amount_fen = n × unit_price_fen`；
- **基础费 + 件价**：`amount_fen = base_fee_fen + n × unit_price_fen`；
- **数量区间**：找到唯一一档 `min_quantity_scaled ≤ n×10000 ≤ max_quantity_scaled`，在这**一档**中计算 `amount_fen = band.base_fee_fen + n × band.unit_price_fen`。这是**整批适用一档**，不是逐档累进征价。末档 `max_quantity_scaled=null` 为无上限。

所有金额都以整数分保存。若计量数量可能带小数，应用层必须用确定的十进制运算和明确舍入政策，不能使用浮点误差累积到业务金额。应用按“**一条作业位置 × 本次该位置数量**”生成费用，不把一基塔的基础费乘以装置数。一次作业覆盖多基塔时，应当对每个作业位置分别计算，并把实际数量归到对应需求/位置。

**仅用于证明模型表达能力的测试价格（不是实际工程定额或报价）：**

| 装置数量 / 同一基塔 | 按件（200分/件） | 每基500分+120分/件 | 数量分档示例 |
| --- | ---: | ---: | ---: |
| 1 | 200分 | 620分 | 700分 |
| 2 | 400分 | 740分 | 900分 |
| 3 | 600分 | 860分 | 1,050分 |
| 5 | 1,000分 | 1,100分 | 1,300分 |

分档规则还可组合输电电压等级、实体塔型、地形、塔高等条件。SQLite 限定数值不为负、JSON 数组完整、各档上下限合法且按数量递增无重叠，禁止普通按件模式冒充固定基础费。价目一经发布不可覆盖；若价格或数量区间调整，新增正式价格版本。**规则匹配、金额试算、处理多条匹配冲突、同塔多回准确位置和税务显示仍由新版应用层实现**，不能把专项 SQL 契约通过称为计算引擎已上线。

## 三、立项需求与结算需求：正式一对多关联

既有 `project_approval_finalize_guard` 在正式批准 `project_approval_versions` 前已经要求至少一条 `project_approval_scope_versions`，并检查其来源需求处于有效确认状态；无须再建一张平行的立项-需求关联表。

新增一个真正独立的业务事实表 `settlement_scope_results`（6 个字段）：

| 字段 | 含义 |
| --- | --- |
| `id` | 本次结算需求解决记录的唯一身份 |
| `settlement_version_id` | 归属于**某一张结算单某一次完整正式版本** |
| `project_scope_id` | 本次实际解决的**子项目承接需求范围** |
| `approval_scope_version_id` | 本次结算所依据的同项目正式批准范围精确版本 |
| `resolved_quantity_scaled` | 本次**新增**实际解决数量（乘10000的整数），允许为零（仅对已完成需求补结费用），也不设批准数量上限 |
| `evidence` | 与本次解决结果有关的可选备注；真实附件可通过证据关联附上 |

- 结算明细 `settlement_items` / `settlement_item_versions` 继续记录费用树科目、计价数量、实际金额；这些可能包括相同需求的材料费、人工费和其他费用，因此其 `quantity_scaled` **只属于该费用明细的计价量，不是需求完成量**。
- `settlement_scope_results` 对同一 `settlement_version_id + project_scope_id` 唯一，保证一次结算对同一需求**只记一个实际解决数量**，不会因两项不同费用重复计算完成量。
- 每个非作废正式结算单版本在提交和批准时都至少要关联一条实际对应的需求。**如果只结算此前已解决需求的费用，本次新增解决数量必须填 0，不能虚增工作量；NULL 不表示合法已确认数量。**带明确 `project_scope_id` 的每条费用明细，都必须有同版本的对应需求解决结果；共同费用仍可 `project_scope_id = NULL`，但这张结算单整体仍要关联实际解决的需求。
- 需求结果严格校验同子项目、同结算所引用的批准版本。不得错挂其他项目、不得先提交再补填、不得覆盖/删除已登记的正式需求解决历史。发生修订时，必须生成新版**完整结算需求结果和完整费用明细**。
- `v_effective_demand_resolutions` 仅显示各独立结算单**当前有效已批准版本**中的需求解决结果。正式作废、版本更正会改变现行汇总但不删除历史。可以按 `project_scope_id` 汇总已解决数量；新的 `idx_settlement_scope_results_scope` 支持反向查询。
- `evidence_links.settlement_scope_result_id` 允许照片、复核依据等附件锁定本次具体需求解决结果，并由外键校验身份。

例如需求 A 批准 10 套，本次解决 12 套；需求 B 批准 30 套，本次解决 5 套。结算单内 A 有人工、材料两条收费行，但需求完成仍是 **A=12 套**，不会误算 24 套。下一张独立结算单又完成 B 10 套，B 现行完成量为 **15 套**，未达到批准的 30 套也仍是合法事实。以上超量、欠量无需在数据库伪造新的预算或必须先把真实数量调整为预计值。

## 四、正式项目结项：需求与财务都允许存在差异

此前 `project_close_guard` 只有所有实际费用和每个正式结算明细的**最终核对份额恰好100%**才能关闭项目；这与用户本轮裁决矛盾，现已取消两个100%强制条件。

**仍保留结项必要的正式性**：
- 必须已有 `project_closures` 独立结项事实，指向子项目最新已批准项目范围和预算；结项人、结项时间以及已批准项目阶段历史仍需真实。
- 未核定的结算单、未决项目范围变更单、已批准却未落实的项目变更及未完成项目批准草稿，仍不能绕过直接关闭（这属于**未结束正式审批**，不等于要求所有真实需求和费用完全解决）。
- 费用历史、结算明细、双金额核对仍保持原有真实外键、可撤销正式历史与**防重复计账上限**。不能因为允许业务超预算就允许同一笔真实费用被重复核对超过原金额。

**不再强制**：
- 全部需求的实际解决数量等于批准数量：可以为零、低于或超过批准数量。
- 每笔真实费用都已经结清，或每条正式结算明细都已最终核对：未决余额可以保留；不应人为伪造收支、核减或未来施工记录。
- 全部实际发生低于批准总预算；批准预算是软基准。

`project_closures.close_snapshot_json` 继续承载当次正式关闭的结构化审核快照。应用应在同一写事务内依据**当前生效批准版本、当前真实费用、各张有效结算单和 `v_effective_demand_resolutions`**计算、展示，并冻结：
- 逐需求的批准量、实际解决量、未完成量和超量；
- 已确认实际费用、已审核结算金额、已核对金额、未核对余额与超预算差额；
- 结项审批人、时间及其它正式审批依据。

这些报表数字**不另设独立累计余额列，也不存为不断更新的事实表**；结项 JSON 是当时人工批准时的**不可变决策证据**。SQLite 只要求合法 JSON 对象和真实审核身份，不冒充应用层的最新余额计算或完整快照内容校验。实际 UI 应自动汇总并要求用户审核确认，管理员**不需要另外输入解释理由**。关闭后历史仍不可删除；若有晚录费用，必须在应用层提示结项复核而非偷偷修改原关闭事实。

## 五、管理员不用填写理由，但不能无审计

全部原来强制非空的 `reason` 字段调整为 `TEXT NOT NULL DEFAULT ''`；设备 `change_reason` 默认 `''`，取消非空理由写入闸门；正式变更 `decision_reason` 可留空；现场新增实际物资 `addition_reason` 可留空。

**保留**：真实操作者和角色身份（应用层）、UTC 时间、连续版本、原始事实、审批关系、不可变正式历史、费用及需求结果与实际证据。管理员可直接点击确定完成正常管理操作，不用为了通过数据库约束输入“无”“同意”“调整”等无信息量文本。数据库不会从请求自报的 `role` 判断是不是管理员；对非管理员某些动作是否要求补充说明由服务端授权逻辑或 UI 决定。

**实施边界**：本轮只修改 Schema113 候选 SQL、隔离测试及说明。参考价格计算引擎、完整需求解决报表、结项审核界面、管理员权限 UI、真实 PMS 清洗后的单次导入、Windows 生产级并发与文件备份恢复，均需在后续新版应用实施，不应宣称已经完成。
