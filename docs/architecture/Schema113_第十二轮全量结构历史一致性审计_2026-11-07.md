> 2026-11-07。**仅候选数据库设计**：DDL、独立 SQLite 合约、结构核对脚本、设计文档。运行中 Schema 112、前端、后端、真实数据及附件均未修改。全部测试用独立 SQLite 内存/临时环境，不借助旧版迁移层。

## 一、最新裁决与目标

以“功能完备优先、再去除重复结构”为原则，候选业务链固定为：

**年度框架（软额度）→ 子项目（完整项目档案/正式需求和批准物资）→ 统一费用树的真实费用 → 多张独立本次结算单 → 双金额最终核对 → 财务结清**。

不引入检修计划、施工/完工、独立物资领退、平行费用分摊账，也不在 SQLite 计算季度目标、预算余额、已结算累计金额或应用操作权限。真实发生及实际结算可以超出年度框架和执行协议额度，超额是应用层需要解释的业务事实，不能因“预测金额不足”丢失记录。

## 二、全量业务对象审计与本轮真实整改

### 为什么本轮新增一张组织版本表

不是重复保存一个当前组织名称。原来有 5 字段的 `organizational_units` 同时负责稳定编码和可变的名称、上级、状态，无法还原旧项目曾由哪一个正式组织定义负责。现在根表 2 字段，新表 9 字段，新增的是**有独立历史含义的正式定义事件**，没有在 `projects` 额外再加可变归口单位或重复组织路径。当前查询仅由 `v_organizational_unit_current` 取得最新定义。

## 四、可复现的全结构审计，不只检查测试计数

新增 `schema113_structure_audit.py`，在完全独立的 `:memory:` SQLite 中装载实际候选 SQL：

1. 逐表检查 `STRICT`、全部外键指向实际存在的表且 `foreign_key_check` 无异常。
2. 对 `Schema113_业务对象完整性矩阵.md` 的**全部 70 张表逐项**核对每表字段数、外键分量数；缺失、重复、过时或虚构对象均报错。
3. 对 `Schema113_触发器约束责任清单.md` 的**全部 209 个触发器逐个**核对真实存在、唯一名字、正确所属表，统计职责分类。
4. 校验 **23 个保留视图每个均可 SELECT**；检查所有显式索引，拒绝可由另一个非部分索引同前缀覆盖的冗余普通索引。
5. 确认不出现已取消的施工完成、独立物资领退和重复费用分摊实体、视图，`cost_versions` 无平行费用分类，`projects` 根无重复可变档案列，组织版本和项目正式档案关系齐全。
6. `PRAGMA integrity_check=ok` 且 `PRAGMA foreign_key_check` 无遗漏。

本轮结果：**70 STRICT 表、23 个视图、209 个触发器、71 个显式索引、666 个字段，362 项隔离数据库专项测试全部通过，字段字典 0 个未解释字段**。另有运行版应用自动化回归，但 Schema 113 还未接入运行服务，该结果不能当作真实业务端到端验收。

## 五、全量审计后仍需实际实施阶段验证的事项

本轮没有发现需新增另一套金额历史或仓储流水的合理理由，但要区分**结构已能独立验收**和**生产能力已经具备**：

- 真实 PMS 线路、档距、杆塔、物资 Excel 原始数据的**全量导入、数据清洗和差异对账**尚未运行于 Schema 113。
- Windows 内网多客户端并发/断电演练、真实证据附件的 SHA256 读取与恢复、数据库在线备份和对象存储联合恢复，仍需在新运行服务上执行真实端到端测试。
- 新 Schema113 服务的数据库访问封装、应用权限判定和全部 UI 操作流程尚未开发/切换；不能把运行版 Schema112 的自动化通过宣称为新版前后端已完成。
- 付款、供应商应付账款不是多次结算的同义词，当前未建模，不能由核对记录捏造出真实银行付款事实。
- `demand_related_logical_towers` 和外部线路别名 `line_source_aliases` 目前属于辅助关联。若用户将来要求“每次关联调整都必须以正式历史版本追溯”，需先明确其业务审核流程，不应为了纯粹追求版本数量主动制造新的正式审计对象。

**结论**：本轮全量候选结构审计完成了明确可验证的关系与历史缺陷治理，所有候选数据库检验通过，保留后续生产实施及具体业务边界的真实限制，不宣称数据库已正式冻结上线。


### 补充：全表删除权限漏洞复核

在所有 70 张表的当前触发器和外键保护检查中发现：从未被需求引用的已发布 `operation_versions` 仍可通过 DELETE 直接抹除；没有线路关联的 `voltage_levels` 也能被删除。这两个情形不应因“暂时没人引用”而失去历史身份。本轮通过先重现再添加 `immutable_operation_version_delete`、`voltage_identity_immutable_delete` 两项必要约束，专项契约增至 **362 项**。应用账号、允许 IP、草稿和临时会话等仍按其业务生命周期管理，不为其强行赋予历史版本语义。


### 进一步确认主数据版本无空修改

操作类型 `operation_versions` 和参考单价 `reference_price_versions` 此前仅具备版本号递增与新增加的时间约束，仍可通过“只改更正原因”制造没有实际内容变化的正式版本。本轮对二者完整可编辑业务定义逐项作 SQL 等值对比，拒绝无变化的新版本，同时保留正当更价、作业对象、单位或作业方式调整。对从未被引用的正式操作定义与电压等级身份直接 DELETE 也进行了反例复现与实际阻断。最终数据库契约 **362/362** 通过，触发器总数 **209**。


## 2026-11-08 补充裁决：归口单位的准确业务含义

用户确认前述“责任单位”即**子项目归口单位**，不是施工单位或各次结算的具体执行主体。候选字段已统一规范为 `project_management_versions.managing_unit_id` / `managing_unit_version_id`，可为空，单个正式项目档案版本仅能指定一个归口单位，同一单位可归口多个子项目。历史更换通过下一管理版本、组织更名通过下一组织定义版本，保留全部原始归口历史。`idx_project_managing_unit` 为对应反向索引；不扩增业务表。


**该语义裁决的独立补充验收（2026-11-08）**：已校验可暂不设归口单位、同一归口单位关联多个子项目、归口变更后历史归口保持不变，以及精确单位版本复合外键；数据库专项验收总数从第十二轮历史快照的 `362` 项增加到 **365/365**。字段总数和数据库对象数量均不变。
