# Schema 113 第十轮：费用树唯一科目与历史版本一致性治理

> 日期：2026-11-07。范围：**仅候选 Schema 113 数据模型、独立 SQLite 合约、设计文档**。运行中的 Schema 112、前后端、真实数据库与附件保持原样。

## 1. 费用树是唯一费用科目来源

子项目的费用归类严格由 `project_cost_nodes` 的不可变父子身份与 `project_cost_node_versions` 的正式版本确定。费用末级可以是材料费、人工费、分项材料费等任意多级，**不再维护平行的费用类别字典**。

- `cost_entries.project_id + cost_node_id` 固定费用归属项目及具体叶子；复合外键保证节点确属该项目。
- `cost_versions.cost_node_version_id` 保留**实际费用确认时采用的准确科目版本**，后续科目改名、停用不改写历史金额和分类。
- `settlement_items.cost_node_id`、`settlement_item_versions.cost_node_version_id` 同样固定每张结算单每条费用明细的末级科目及当时定义。
- `cost_versions.title` 是实际费用**事项标题**，并非第二份费用科目文字；金额、税率、凭证、费用发生日、资金归属、确认人和更正历史依然完整独立。
- `cost_reconciliation_versions` 只能在**同一个末级科目、同一个子项目**内把真实费用份额核对到各次已批准结算，不允许把材料费误挂人工费。

实际费用版本删除两个冗余字段：`category_id`、`category_snapshot`；对应索引 `idx_cost_versions_category` 同时移除。其他领域自己的业务分类（项目类别、物资主数据类别）依然独立保留，不误删。

## 2. 费用树版本治理

沿用现有完整性触发器并强化其边界，没有增加新的对象表：

1. **不可变树结构**：节点父子关系不得覆盖，子节点与父节点必须属于同一子项目；新子节点只能挂在**从父级到根节点整条路径均已有启用定义**的上级科目下，不能挂在尚未定义或已停用上级科目下。
2. **不能把已入账的叶子变成汇总科目**：一旦末级节点已有真实费用或任何结算明细身份，就不能再给它增加子节点；由此避免历史父级金额和子级金额重复入账。
3. **正式定义版本**：`project_cost_node_versions` 只能连续编号、登记时间不早于节点创建时间和上一版本的登记时间；名称与状态都没变化不能伪造空版本。
4. **历史时点一致性**：`cost_versions` 与 `settlement_item_versions` 不可引用晚于该费用确认时间或该结算版本登记时间才发布的费用定义。
5. **停用与恢复**：停用节点**连同整棵子树**禁止**新建**实际费用和结算明细身份；可通过新正式版本恢复启用，已有实际费用、审批结算和旧分类版本保留且可追溯。

费用树多级父级总计、各叶子实际费用、分次已结算与未结算余额均由应用层按当时有效事实查询聚合。数据库不新增累计金额、不要求实际发生额必须低于原预算。

## 3. SQLite 合约与结果

相较第九轮新增 **17 项**专项合约：无第二费用类别字段及索引、空版本/提前或倒序定义、不得引用未来科目版本、历史科目快照保持不变、无定义/停用父级不能新增子级、恢复启用允许后续真实节点、停用科目及任意层级祖先禁用时拒绝新费用、新结算和新增子项；恢复祖先有效状态后可正常新增，旧历史持续可追溯。保留既有真实费用跨历史版本、三张结算单逐次部分结清、核减、正式注销、超结复核、费用分类错挂和多级末级约束。

## 4. 设计边界及后续审核

- **费用树只承担业务费用分类**。如以后确有独立会计科目编码或税务核算分类，应先提出具体会计场景并另行裁决；不能把原先的重复 `category_snapshot` 恢复为随意输入的平行分类。
- 需求物资、批准物资、费用树的材料费用项是不同业务对象；依最新裁决，不建立领退料流水，也不从物资批准数量推导实际用量。
- 父级费用分类、结算累计和费用余额始终从叶子事实计算；不再新增冗余数据表字段。
- Schema 113 仍是候选结构，实际运行版仍是 Schema 112。
