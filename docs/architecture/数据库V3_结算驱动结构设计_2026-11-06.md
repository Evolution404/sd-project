## 最新裁决：预算和材料允许超预期，必须如实统计

> **2026-11-06 补充（覆盖本文旧限额表述）**：年度框架、执行协议、项目预算、批准需求数量与物资预计数量，均为**管理基准**，不是数据写入的硬上限。实际结算、费用、完成数量、材料消耗可以高于基准；系统计算正负偏差、超出数量、超出金额、进度百分比及使用率，**不得以超额为理由拒绝合法业务事实**。审核记录仍不能覆盖，跨项目关联仍须正确。

## 一、最终设计裁决

| 最新裁决 | 结构落地 |
| --- | --- |
| 取消检修计划 | 新设计不再有 `executions`、`execution_items`、`plan_budget_drafts`、`plan_budget_versions` |
| 全部改为结算，以结算推动费用 | 结算单 `settlements` → 结算明细 `settlement_items` → 完成量／物资消耗／费用与核对 |
| 子项目可以不关联执行协议 | `projects.agreement_id` 可空，**批准、关闭也允许为空**；未关联项目直接占用所属框架可用额度 |
| 档距长度不是关键数据 | `line_spans` 不增加长度和管辖长度字段，不要求录入；如需要显示，仅依据坐标计算参考距离 |
| 标准作业对象 | `work_objects` 独立维护，操作类型固定关联一个对象，需求自动继承并保留快照 |
| 需求物资明细一对多 | `demand_material_items` 允许零项或多项，批准时冻结到 `project_approval_material_items` |
| 四状态反馈应区分部分完成 | 四状态仍是概览，实施与结算分别自动计算 none／partial／full 和准确比例，不手工维护 |
| 子项目可正式关闭 | `project_closures` 记录审批与证据，`project_closure_dispositions` 记录未完成量取消或延期 |

## 二、数据关系与业务链路

`frameworks`（年度项目框架）
→ `projects`（子项目）
→ `project_approval_versions`（项目批准版本）
→ `settlements`（结算单）
→ `settlement_items`（结算明细）
→ `completion_records`（实际完成）／`settlement_material_consumptions`（实际材料）
→ `cost_entries`、`cost_versions`、`cost_allocations`（实际费用及分摊）
→ `cost_reconciliation_versions`（实际费用与结算核对）。

专业需求为独立需求池：`demands` → `project_demand_scopes`（批准项目范围）→ 多次 `settlement_items`。一个需求原则上只由一个正式子项目承接，可分多次结算，**不创建中间的检修计划实体**。

资金为并行约束：年度框架可创建多个执行协议，但子项目始终直接属于年度框架。执行协议是**可选的资金分配关系**，而不是项目组织父节点。

## 三、主要表定义与约束

| 实体 | 权威字段／关联 | 设计原则 |
| --- | --- | --- |
| `work_objects` | ID、编码、名称、line／physical／both、状态 | 作业对象独立标准化 |
| `operations` | `work_object_id`、`default_unit_id`、允许杆塔／档距、版本 | 作业对象和计量单位只在操作定义中确定 |
| `demands` | 三选一设备定位、`operation_version`、`work_object_id`、`work_object_snapshot` | 不重复录入对象；旧需求快照不可追写 |
| `demand_material_items` | 需求 ID、物资名、型号、规格、数量、单位 | 0:N；物资数量与作业工作量分离 |
| `project_approval_material_items` | 批准版本、批准需求范围、物资规格及批准数量 | 审批版本固定且不可变 |
| `projects` | 框架 ID 必填、`agreement_id` 可空、批准预算 | 无协议仍可入库、立项与关闭 |
| `project_demand_scopes` | 需求 ID、批准数量、参考价格、`approved_amount_fen` | 用一个范围连接需求、结算、费用 |
| `settlements` | 子项目、批准版本、结算号、预／进度／终结性质、状态、证据、确认人 | 唯一结算业务主实体 |
| `settlement_items` | 结算单、批准范围、结算数量、金额、快照 | 一条明细不能跨项目 |
| `settlement_adjustments` | 明细 ID、正负金额增量、更正／冲销、原因、时间 | 不覆盖已确认原金额 |
| `completion_records` 与 `completion_revisions` | 结算明细、实际数量、验收依据及更正历史 | 完成量以当前有效版本求和 |
| `settlement_material_consumptions` | 结算明细、批准物资明细、实际用量 | 按批准物资口径核销 |
| `cost_entries`、`cost_versions` | 结算单、费用类别、实际金额、确认版本 | 费用不等于结算金额 |
| `cost_allocations` | 费用版本、同结算单的明细、分摊金额 | 分摊总额不能超过费用确认额 |
| `cost_reconciliation_versions` | 费用版本、结算明细、核对额、确认状态 | 保持核对历史 |
| `project_closures`、`project_closure_dispositions` | 关闭版本、责任人、处置剩余量及证据 | 关闭必须有明确、可追溯依据 |

### 三类位置仍互斥

线路侧杆塔需求引用 `logical_tower_id`；共用物理杆塔需求引用 `physical_tower_id`；档距需求引用 `span_id`。档距不额外写入虚构的起点杆塔锚点。保留主支线接入合法性、物理杆塔与逻辑杆塔历史。

**不设计**档距实测长度、管辖长度等主数据；参考距离不是结算工作量的默认依据。

## 四、资金与结算约束

- 所有金额均为整数“分”；所有业务数量均为放大 10000 倍的整数。
- 框架额度、协议额度、子项目预算均是**对比基准**。协议预留额度、项目批准预算、实际费用和净结算可能高于基准，仍可入库；统计原始基准值、最新实际值、正负差额、超出额、占比，不篡改预算来掩盖超支。
- 已选协议仍必须属于子项目所属的年度框架；没有协议的项目同样允许正式批准、结算及关闭。**同框架外键强制，额度不强制**。
- 每条结算明细都必须引用正确的项目批准范围及对应批准版本；金额与数量可以高于批准预计，不因此拒绝合法结算。
- 实际完成量、物资实际消耗和净结算金额均可以高于原需求数量、批准物资用量和项目批准金额；超额只形成偏差指标。
- 实际完成量与净结算金额互不推导，可以先结算、后实施；比例允许显示 100% 以上，而不截断为 100%。
- 正向结算、冲销、实际费用、费用核对是**四种不同事实**。结算不等于银行付款；本版不新增未经批准的真实付款模块。
- 结算确认后不得直接改写明细，通过 `settlement_adjustments` 追加更正或冲销；完成量和费用同样保留不可变历史版本。
- 停电／不停电可作为参考价 `work_mode` 的适用条件，**不是检修计划或独立计划流程**。

## 五、四状态与准确进度

`v_scope_progress` 从结算、完成量的当前有效版本推导，不增加需要用户编辑的进度字段：

| 维度 | 计算结果 |
| --- | --- |
| 实施进度 | none（0）／partial（0＜已完成＜批准数量）／full（已完成达到批准数量） |
| 结算进度 | none（0）／partial（0＜净结算＜批准额）／full（达到批准额）／unknown（价格缺失） |
| 实施比例 | 已确认完成量 ÷ 批准工作量 |
| 结算比例 | 净结算金额 ÷ 批准金额 |
| 概览四状态 | 已实施已结算、已实施未结算、未实施已结算、未实施未结算 |

例如批准 10 套、完成 3 套、批准金额 100 元、有效结算 40 元：概览为“已实施已结算”，同时明确显示**实施 30%、结算 40%，均为部分完成**。若实际完成 15 套、净结算 130 元，则显示 **实施 150%／超出 5 套；结算 130%／超出 30 元**，且照常保存。绝不能只凭发生过一笔记录就认为 100% 完成，也不能将 150% 截断为 100%。

### 偏差统计视图（不另建可手填的重复事实表）

| 只读视图 | 基准与实际 | 输出字段 |
| --- | --- | --- |
| `v_framework_variance` | 框架额度 vs 协议分配、未绑定协议项目预算、净结算、实际费用 | 预留超额、净结算超额、实际费用超额 |
| `v_agreement_variance` | 协议额度 vs 子项目批准预算、净结算、实际费用 | 已批准预算差额及超额、结算及费用差额 |
| `v_project_variance` | 子项目批准预算 vs 有效净结算与当前有效费用版本 | 结算差额、费用差额、超出金额、超过 100% 的进度 |
| `v_scope_progress` | 需求批准量与金额 vs 实际完成量和净结算 | 两轴完整状态、正负差额、超出量、超出金额、超 100% 比例 |
| `v_material_variance` | 每个批准物资版本的预计量 vs 实际领用量 | 实际量、数量差额、超领数量、耗用比例 |
| `v_settlement_item_variance` | 结算明细申报数量 vs 实际验收数量 | 实施量差额，独立于实际结算金额 |

**偏差统计不能成为拦截原因。** 唯一继续限制的数字关系是防止业务记账重复（例如一项已确认费用的明细分摊总额不能超过该笔费用自身的真实总额、冲销不能超过同笔原始余额）；这与“实际费用超过预算”完全不同。

## 六、正式关闭子项目

关闭前由数据库检查：项目已批准并具备关闭审计；没有未确认结算单和未决项目变更；所有有效需求范围已完成，或对未完成剩余量逐项记录确切数量和取消／延期依据；实际费用已完成要求的最终核对。

关闭记录存 `project_closures`，未完成量归入 `project_closure_dispositions`，以后不允许删除历史原始事实。**跨子项目转移需求尚未授权，不在本版中设计自动移交**；“延期”不会自动创建第二个项目。

## 七、从 Schema 112 删除或替代的结构

- **彻底删除** `executions`、`execution_items`、`plan_budget_drafts`、`plan_budget_versions`；无“检修计划”作为隐藏的中间层。
- 原 `project_settlement_entries`、`settlement_commands`、`settlement_revisions` 不做简单改名，而由结算单／结算明细／更正冲销独立重新建模。
- 原完成量、费用、分摊和核对表改为直接引用 `settlement_id` 或 `settlement_item_id`，不再引用 `execution_id`／`execution_item_id`。
- 保留原有线路杆塔台账、通用字典、需求池、项目批准版本、附件、审计、权限基础实体；保留对应合法性约束。
- 未授权的跨项目需求转移、银行付款与档距精确长度不得借本轮机会擅自加入。

## 八、设计验证与实施边界

候选 SQL 在隔离内存 SQLite 中通过创建、外键完整性、约束和查询视图验证，并模拟了：

1. 无协议子项目可批准；框架、协议及项目预算超额可如实入库，在偏差视图中显示超额。
2. 一条需求关联两项物资，批准物资可以冻结。
3. 部分实施与部分结算（含冲销）的两轴状态正确计算。
4. 缺少关闭记录或未完成工作量处置时拒绝关闭，补齐处置后允许关闭。
